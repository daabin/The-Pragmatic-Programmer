## 主题 53. 傲慢与偏见

> 你已经让我们高兴够久了。
>
> 简·奥斯汀，傲慢与偏见

<a id="d24e27459"></a>
务实的程序员不会逃避责任。相反，我们乐于接受挑战并让我们的专业知识广为人知。如果我们负责一项设计或一段代码，我们所做的工作就值得我们感到自豪。

**提示 97：签署你的作品**

<a id="d24e27498"></a>
早期的工匠很自豪能在自己的作品上签名。你也应该如此。

<a id="d24e27500"></a>
然而，项目团队仍然是由人组成的，这条规则可能会带来麻烦。在某些项目中，代码所有权的想法可能会导致合作问题。人们可能会变得有领地意识，或者不愿意在共同的基础要素上工作。该项目最终可能会像一群孤立的小领地一样。你会对你的代码产生偏见，而反对你的同事。

<a id="d24e27522"></a>
那不是我们想要的。你不应该嫉妒地保护你的代码免受入侵者的侵害；同样的道理，你应该尊重别人的代码。黄金法则（“己所不欲，勿施于人”）和开发人员之间相互尊重的基础对于使此技巧发挥作用至关重要。

<a id="d24e27524"></a>
匿名，尤其是在大型项目中，可能会滋生草率、错误、懒惰和糟糕的代码。人们很容易认为自己只是车轮上的一个齿轮，在无休无止的状态报告中产生蹩脚的借口，而不是好的代码。

<a id="d24e27528"></a>
<a id="FNPTR-84"></a>
虽然代码必须由个人所有，但它不一定由个人所有。事实上，Kent Beck 的极限编程[[84]](#FOOTNOTE-84) 建议代码的公共所有权（但这也需要额外的实践，例如结对编程，以防范匿名的危险）。

<a id="d24e27558"></a>
我们希望看到所有权的自豪感。 “我写了这篇文章，我支持我的工作。”您的签名应该被视为质量的指标。人们应该在一段代码上看到你的名字，并期望它是可靠的、编写良好、经过测试和记录的。一个非常专业的工作。由专业人士撰写。

<a id="d24e27561"></a>
务实的程序员。

<a id="d24e27563"></a>
