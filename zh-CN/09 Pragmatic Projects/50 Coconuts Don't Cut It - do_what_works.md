<a id="do_what_works"></a>
## 主题 50. 只靠椰子可不行

<a id="d24e26447"></a>
当地的岛民以前从未见过飞机，也从未见过像这些陌生人这样的人。作为使用他们土地的回报，陌生人提供了机械鸟，它们整天在“跑道”上飞来飞去，为他们的岛屿家园带来了难以置信的物质财富。陌生人提到了一些关于战争和战斗的事情。有一天，事情结束了，他们都离开了，带走了他们奇怪的财富。

<a id="d24e26461"></a>
岛民们迫切希望恢复好运，并使用当地材料（藤蔓、椰子壳、棕榈叶等）重建了机场的复制品、控制塔和设备。但由于某种原因，尽管一切准备就绪，飞机还是没有来。他们模仿了形式，但没有模仿内容。人类学家称之为货物崇拜。

<a id="d24e26466"></a>
很多时候，我们都是岛民。

<a id="d24e26471"></a>
<a id="FNPTR-79"></a>
很容易陷入货物崇拜陷阱：通过投资和建造显而易见的文物，你希望吸引潜在的、起作用的魔力。但与美拉尼西亚最初的货运崇拜一样，[[79]](<../10 Postface/README.md#FOOTNOTE-79>) 用椰子壳制成的假机场无法替代真实机场。

<a id="d24e26480"></a>
例如，我们亲眼见过声称使用 Scrum 的团队。但是，经过仔细检查，结果发现他们每周举行一次每日站立会议，四周的迭代通常会变成六周或八周的迭代。他们觉得这没关系，因为他们使用的是流行的“敏捷”调度工具。他们只投资于表面的文物——即便如此，往往只是名义上的，就好像“站起来”或“迭代”是某种迷信的咒语。不出所料，他们也未能吸引到真正的魔法。

### 背景很重要

<a id="d24e26492"></a>
您或您的团队是否陷入了这个陷阱？问问自己，为什么要使用这种特定的开发方法？或者那个框架？或者那种测试技术？它真的适合手头的工作吗？它对你来说效果好吗？或者它被采用只是因为它被最新的互联网推动的成功故事所使用？

<a id="d24e26498"></a>
当前的趋势是采用 Spotify、Netflix、Stripe、GitLab 等成功公司的政策和流程。每个人对软件开发和管理都有自己独特的看法。但请考虑一下背景：你们是否处于同一个市场，具有相同的限制和机会、相似的专业知识和组织规模、相似的管理和相似的文化？类似的用户群和需求？

<a id="d24e26500"></a>
不要上当。特定的工件、表面结构、政策、流程和方法还不够。

**提示 87：做有效的事情，而不是流行的事情**

<a id="d24e26512"></a>
你怎么知道“什么有效”？您依赖于最基本的实用技巧：

<a id="d24e26514"></a>
尝试一下。

<a id="d24e26516"></a>
在一个或一组小团队中试点这个想法。保留看起来运行良好的好部分，并丢弃其他任何浪费或开销的东西。没有人会因为你的组织的运作方式与 Spotify 或 Netflix 不同而降低你的组织级别，因为即使他们在成长过程中也没有遵循当前的流程。几年后，随着这些公司的成熟、转型并继续蓬勃发展，他们将再次做一些不同的事情。

<a id="d24e26522"></a>
这就是他们成功的真正秘诀。

### 一种尺寸不适合任何人

<a id="d24e26529"></a>
软件开发方法的目的是帮助人们协同工作。正如我们在主题 48 [*敏捷的本质*](<../08 Before the Project/48 The Essence of Agility - essence_of_agility.md#essence_of_agility>) 中讨论的那样，开发软件时没有单一的计划可以遵循，尤其是其他公司的其他人提出的计划。

<a id="d24e26536"></a>
许多认证项目实际上比这更糟糕：它们的前提是学生能够记住并遵守规则。但这不是你想要的。您需要有能力超越现有规则并利用可能性获得优势。这与“但是 Scrum/精益/看板/XP/敏捷是这样做的……”等等是一种非常不同的心态。

<a id="d24e26540"></a>
相反，您希望从任何特定方法中获取最好的部分并进行调整以供使用。没有一种方法适合所有情况，并且当前的方法还远未完成，因此您需要考虑的不仅仅是一种流行的方法。

<a id="d24e26542"></a>
例如，Scrum 定义了一些项目管理实践，但 Scrum 本身并没有在技术层面为团队或在项目组合/治理层面为领导层提供足够的指导。那么你从哪里开始呢？

<a id="d24e26547"></a>
<a id="d24e26552"></a>
像他们一样！

我们经常听到软件开发领导者告诉他们的员工，“我们应该像 Netflix（或其他领先公司之一）一样运营”。你当然可以这样做。

首先，给自己准备几十万台服务器和几千万用户……

### 真正的目标

<a id="d24e26557"></a>
当然，我们的目标不是“实施 Scrum”、“实施敏捷”、“实施精益”或诸如此类的事情。我们的目标是能够提供可立即为用户提供一些新功能的工作软件。不是几周、几个月或几年后，而是现在。对于许多团队和组织来说，持续交付感觉像是一个崇高而难以实现的目标，尤其是当您面临的流程将交付限制在数月甚至数周时。但与任何目标一样，关键是始终朝着正确的方向努力。

<a id="d24e26574"></a>
<a id="adelivery_times"></a>
![A graph depicts the delivery time for three entities.](https://panzhongxian.cn/images/the-pragmatic-programmer/delivery_times.png)

图表描述了按周期的交货时间信息。横轴显示实体：多月或一年迭代（瀑布）、固定短迭代（scrum）和持续交付。纵轴显示实体：小时、周和年。图中显示了九个块。前三个水平块代表交付时间（年）的实体。第四到第六水平块代表交货时间（周）的实体。第七至第九水平块代表交货时间（小时）的实体。图中绘制了一条穿过以下块的递减曲线：第一、第四和第九。

<a id="d24e26575"></a>
如果您要在几年内交付，请尝试将周期缩短到几个月。从几个月减少到几周。从四周的冲刺开始，尝试两周。从两周的冲刺开始，尝试一下。然后每天。然后，最后，按需。请注意，能够按需交付并不意味着您必须每天每一分钟都交付。当用户需要时，当这样做具有商业意义时，您就可以交付。

**提示 88：在用户需要时交付**

<a id="d24e26583"></a>
为了转向这种持续开发方式，您需要一个坚如磐石的基础设施，我们将在下一个主题（主题 51，[*实用的入门套件*](<51 Pragmatic Starter Kit - starter_kit.md#starter_kit>)）中讨论这一点。您在版本控制系统的主干而不是分支中进行开发，并使用功能开关等技术有选择地向用户推出测试功能。

<a id="d24e26592"></a>
一旦基础设施井然有序，您就需要决定如何组织工作。初学者可能希望从 Scrum 开始进行项目管理，再加上极限编程 (XP) 的技术实践。更有纪律和经验丰富的团队可能会寻求看板和精益技术，无论是对于团队还是对于更大的治理问题。

<a id="d24e26608"></a>
但不要相信我们的话，亲自调查并尝试这些方法。但要小心，不要做得太过分。对任何特定方法的过度投资可能会让您对替代方案视而不见。你会习惯的。很快就很难再看到其他的办法了。你已经钙化了，现在已经无法快速适应了。

<a id="d24e26610"></a>
不妨使用椰子。
