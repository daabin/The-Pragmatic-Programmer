## 主题 49. 务实的团队

> 在 L 组，斯托菲尔负责管理六名一流的程序员，这种管理挑战大致相当于放猫。
>
> 《华盛顿邮报》杂志，1985 年 6 月 9 日

<a id="d24e25834"></a>
即使在 1985 年，关于放养猫的笑话也已经过时了。到世纪之交第一版出版时，它已经非常古老了。然而它仍然存在，因为它具有真实性。程序员有点像猫：聪明、意志坚强、固执己见、独立，并且经常受到网络崇拜。

<a id="d24e25840"></a>
到目前为止，在本书中我们已经研究了帮助个人成为更好的程序员的实用技术。这些方法是否也适用于团队，甚至是由意志坚强、独立的人组成的团队？答案是响亮的“是！”作为一个务实的个人有很多优势，但如果个人在一个务实的团队中工作，这些优势会成倍增加。

<a id="d24e25842"></a>
<a id="FNPTR-75"></a>
在我们看来，团队是一个小而稳定的实体。五十个人不是一个团队，他们是一群人。[[75]](<../10 Postface/README.md#FOOTNOTE-75>) 成员不断被拉去执行其他任务且彼此不认识的团队也不是一个团队，他们只是在雨中暂时共享公共汽车站的陌生人。

<a id="d24e25856"></a>
务实的团队规模很小，成员数量在 10 到 12 人左右。成员很少来来去去。每个人都非常了解彼此，彼此信任，彼此依赖。

**技巧 84：维持小而稳定的团队**

<a id="d24e25864"></a>
在本节中，我们将简要介绍如何将实用技术应用于整个团队。这些注释只是一个开始。一旦您拥有一群务实的开发人员在有利的环境中工作，他们就会快速开发和完善适合他们的团队动力。

<a id="d24e25866"></a>
让我们从团队角度重新审视前面的一些部分。

### 没有破损的窗户

<a id="d24e25873"></a>
质量是团队的问题。即使最勤奋的开发人员被安排在一个不在乎的团队中，也会发现很难保持解决琐碎问题所需的热情。如果团队积极阻止开发人员花时间进行这些修复，问题会进一步恶化。

<a id="d24e25899"></a>
团队作为一个整体不应该容忍破损的窗户——那些无人修复的小缺陷。团队必须对产品的质量负责，支持理解我们在主题 3 [*软件熵*](<../01 Pragmatic Philosophy/03 Software Entropy - no_broken_windows.md#no_broken_windows>) 中描述的不破窗理念的开发人员，并鼓励那些尚未发现它的开发人员。

<a id="d24e25918"></a>
一些团队方法论有一名“质量官”——团队将可交付成果的质量责任委托给他。这显然是荒谬的：质量只能来自所有团队成员的个人贡献。 Quality is built in, not bolted on.

### 水煮青蛙

<a id="d24e25938"></a>
还记得主题 4 中的“锅中之蛙”吗？[*石汤和水煮田鸡*](<../01 Pragmatic Philosophy/04 Stone Soup and Boiled Frogs - stone_soup.md#stone_soup>)？它没有注意到环境的逐渐变化，最终被煮熟了。同样的情况也可能发生在不警惕的人身上。在项目开发的热潮中，关注整体环境可能很困难。

<a id="d24e25951"></a>
整个团队更容易沸腾。人们假设其他人正在处理问题，或者团队领导必须批准用户请求的更改。即使是最善意的团队也可能会忽视项目中的重大变化。

<a id="d24e25953"></a>
<a id="FNPTR-76"></a>
对抗这个。鼓励每个人积极监控环境的变化。保持清醒并意识到范围扩大、时间尺度缩短、附加功能、新环境——任何不属于最初理解的事物。保持新需求的指标。[[76]](<../10 Postface/README.md#FOOTNOTE-76>) 团队不需要立即拒绝更改 - 您只需要知道它们正在发生即可。不然的话，你就陷入了水深火热之中。

### 安排您的知识组合

<a id="d24e26005"></a>
在主题 6 [*您的知识组合*](<../01 Pragmatic Philosophy/06 Your Knowledge Portfolio - knowledge.md#knowledge>) 中，我们研究了您应该如何利用自己的时间投资于您的个人知识组合。想要成功的团队还需要考虑他们的知识和技能投资。

<a id="d24e26044"></a>
如果您的团队认真对待改进和创新，您需要对其进行安排。试图“只要有空闲时间”就完成事情意味着它们永远不会发生。无论您正在处理哪种待办事项、任务列表或流程，都不要仅将其保留用于功能开发。该团队的工作不仅仅是新功能。一些可能的例子包括：

<a id="d24e26053"></a>
<a id="d24e26062"></a>
<a id="d24e26084"></a>
<a id="d24e26093"></a>
旧系统维护：虽然我们喜欢在闪亮的新系统上工作，但很可能需要在旧系统上完成维护工作。我们遇到过试图将这项工作推到角落的团队。如果团队负责完成这些任务，那就真正地去做。

流程反思和细化：只有当您花时间环顾四周，找出哪些有效，哪些无效，然后进行更改时，才能实现持续改进（请参阅主题 48，[*敏捷的本质*](<../08 Before the Project/48 The Essence of Agility - essence_of_agility.md#essence_of_agility>)）。太多的团队忙于救水，以至于没有时间修复泄漏。安排一下吧修复它。

新技术实验：不要仅仅因为“每个人都在这样做”，或者基于您在会议上看到或在线阅读的内容而采用新技术、框架或库。用原型仔细审查候选技术。将尝试新事物并分析结果的任务列入时间表。

学习和技能改进：个人学习和改进是一个很好的开始，但许多技能在团队范围内传播时会更有效。计划好去做，无论是非正式的棕袋午餐还是更正式的培训课程。

### 沟通团队的存在

<a id="d24e26109"></a>
显然，团队中的开发人员必须相互交谈。我们在主题 7 [*交流！*](<../01 Pragmatic Philosophy/07 Communicate - communicate.md#communicate>) 中提出了一些建议来促进这一点。然而，人们很容易忘记团队本身也在组织中存在。团队作为一个实体需要与世界其他地方进行清晰的沟通。

<a id="d24e26117"></a>
在外人看来，最糟糕的项目团队是那些显得闷闷不乐、沉默寡言的项目团队。他们举行没有结构的会议，没有人愿意发言。他们的电子邮件和项目文档一团糟：没有两个看起来相同，并且每个都使用不同的术语。

<a id="d24e26123"></a>
<a id="FNPTR-77"></a>
优秀的项目团队具有鲜明的个性。人们期待与他们会面，因为他们知道他们会看到一场精心准备的表演，让每个人都感觉良好。他们生成的文档清晰、准确且一致。团队用一种声音说话。[[77]](<../10 Postface/README.md#FOOTNOTE-77>) 他们甚至可能有幽默感。

<a id="d24e26129"></a>
有一个简单的营销技巧可以帮助团队作为一个整体进行沟通：打造一个品牌。当你开始一个项目时，给它起一个名字，最好是一个古怪的名字。 （过去，我们以捕食绵羊的杀人鹦鹉、视错觉、沙鼠、卡通人物和神话城市等事物来命名项目。）花 30 分钟想出一个滑稽的徽标，然后使用它。与人交谈时，请随意使用团队的名称。这听起来很愚蠢，但它为您的团队提供了一个可以赖以发展的身份，并为世界带来了与您的工作相关的令人难忘的东西。

### 不要重复自己

<a id="d24e26163"></a>
在主题 9 [*DRY——重复的弊端*](<../02 Pragmatic Approach/09 DRY - The Evils of Duplication - dry.md#dry>) 中，我们讨论了消除团队成员之间重复工作的困难。这种重复会导致浪费精力，并可能导致维护噩梦。 “烟囱”或“孤立”系统在这些团队中很常见，共享很少，而且功能重复很多。

<a id="d24e26186"></a>
良好的沟通是避免这些问题的关键。我们所说的“好”是指即时且无摩擦。

<a id="d24e26213"></a>
您应该能够向团队成员提出问题并得到或多或少的即时答复。如果团队位于同一地点，这可能就像将头伸出立方体墙壁或走廊一样简单。对于远程团队，您可能必须依赖消息应用程序或其他电子方式。

<a id="d24e26215"></a>
<a id="FNPTR-78"></a>
如果您必须等待一周才能在团队会议上提出您的问题或分享您的状态，这会造成很大的摩擦。[[78]](<../10 Postface/README.md#FOOTNOTE-78>) 无摩擦意味着可以轻松、轻松地提出问题、分享您的进度、您的问题、您的见解和学习成果，并随时了解您的队友在做什么。

<a id="d24e26221"></a>
保持意识停留在DRY。

### 团队追踪子弹

<a id="d24e26227"></a>
项目团队必须在项目的不同领域完成许多不同的任务，涉及许多不同的技术。了解需求、设计架构、前端和服务器编码、测试，所有这些都必须发生。但一个常见的误解是，这些活动和任务可以单独、孤立地进行。他们不能。

<a id="d24e26253"></a>
一些方法提倡团队内各种不同的角色和头衔，或者完全创建单独的专业团队。但这种方法的问题在于它引入了门和切换。现在，不再是从团队到部署的顺利流程，而是有人工的大门让工作停止。必须等待被接受的移交。批准。文书工作。精益人士称之为浪费，并努力积极消除它。

<a id="d24e26269"></a>
所有这些不同的角色和活动实际上是对同一问题的不同看法，人为地将它们分开可能会带来很多麻烦。例如，距离其代码的实际用户两级或三级的程序员不太可能知道他们的工作的使用上下文。他们将无法做出明智的决定。

<a id="d24e26271"></a>
对于主题 12 [*曳光弹*](<../02 Pragmatic Approach/12 Tracer Bullets - tracer_bullets.md#tracer_bullets>)，我们建议开发单个功能，无论最初多么小和有限，这些功能都会贯穿整个系统。这意味着您需要团队内的所有技能来做到这一点：前端、UI/UX、服务器、DBA、QA 等，所有这些技能都能够轻松且习惯于彼此合作。通过跟踪子弹方法，您可以非常快速地实现非常小的功能，并立即获得有关团队沟通和交付情况的反馈。这将创建一个您可以快速轻松地进行更改并调整团队和流程的环境。

### 自动化

<a id="d24e26296"></a>
确保一致性和准确性的一个好方法是自动化团队所做的一切。当您的编辑器或 IDE 可以自动为您完成代码格式化标准时，为什么还要费力地处理代码格式化标准呢？当持续构建可以自动运行测试时，为什么还要进行手动测试？当自动化每次都能以相同的方式、可重复且可靠地完成部署时，为什么还要手动部署呢？

<a id="d24e26312"></a>
自动化是每个项目团队的重要组成部分。确保团队具备工具构建技能，能够构建和部署自动化项目开发和生产部署的工具。

### 知道何时停止添加油漆

<a id="d24e26326"></a>
请记住，团队是由个人组成的。让每个成员都有能力以自己的方式发光。为他们提供足够的结构来支持他们并确保项目交付价值。然后，就像主题 5 [*足够好的软件*](<../01 Pragmatic Philosophy/05 Good-Enough Software - good_enough_sw.md#good_enough_sw>) 中的画家一样，抵制添加更多油漆的诱惑。

- 寻找软件开发领域之外的成功团队。是什么让他们成功？他们是否使用本节中讨论的任何流程？
