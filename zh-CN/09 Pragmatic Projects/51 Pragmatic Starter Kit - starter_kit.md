## 主题 51. 务实的起步工具包

> 文明的进步是通过增加我们无需思考即可执行的重要操作的数量来实现的。
>
> 阿尔弗雷德·诺斯·怀特海德

<a id="d24e26649"></a>
当汽车还是新鲜事物时，福特 T 型车的启动说明长达两页多。对于现代汽车，您只需按一下按钮即可，启动过程是自动且万无一失的。遵循一系列说明的人可能会淹没发动机，但自动启动器不会。

<a id="d24e26663"></a>
尽管软件开发仍然是一个处于Model-T阶段的行业，但我们不能为了一些常见的操作而一遍又一遍地阅读两页说明书。无论是构建和发布过程、测试、项目文书工作还是项目中的任何其他重复任务，它都必须是自动的，并且可以在任何有能力的机器上重复。

<a id="d24e26665"></a>
此外，我们希望确保项目的一致性和可重复性。手动程序让一致性取决于机会；无法保证可重复性，尤其是当该过程的各个方面可以由不同的人解释时。

<a id="d24e26667"></a>
在写完第一版《程序员修炼之道》之后，我们希望创作更多书籍来帮助团队开发软件。我们认为我们应该从头开始：每个团队需要的最基本、最重要的元素是什么，无论方法、语言或技术堆栈如何。因此，实用入门套件的想法诞生了，涵盖以下三个关键且相互关联的主题：

- 版本控制
- 回归测试
- 全自动化

<a id="d24e26718"></a>
这是支持每个项目的三条腿。方法如下。

### 带版本控制的驱动

<a id="d24e26723"></a>
正如我们在主题 19 [*版本控制*](<../03 Basic Tools/19 Version Control - version_control.md#version_control>) 中所说，您希望将构建项目所需的一切都置于版本控制之下。这个想法在项目本身的背景下变得更加重要。

<a id="d24e26727"></a>
<a id="FNPTR-80"></a>
首先，它允许构建机器是短暂的。 [[80]](<../10 Postface/README.md#FOOTNOTE-80>) 构建机器和/或集群不是在办公室角落里放置一台每个人都不敢碰的神圣的、吱吱作响的机器，而是按需创建为云中的现货实例。部署配置也受到版本控制，因此可以自动处理发布到生产环境。

<a id="d24e26745"></a>
这是重要的部分：在项目级别，版本控制驱动构建和发布过程。

**提示 89：使用版本控制来驱动构建、测试和发布**

<a id="d24e26776"></a>
也就是说，构建、测试和部署是通过提交或推送到版本控制来触发的，并构建在云中的容器中。发布到暂存或生产是通过使用版本控制系统中的标签来指定的。然后，发布成为日常生活中更加低调的一部分——真正的持续交付，不依赖于任何一台构建机器或开发人员的机器。

<a id="testing"></a>
### 无情且持续的测试

<a id="d24e26788"></a>
许多开发人员会温和地进行测试，下意识地知道代码会在哪里出现问题并避免弱点。务实的程序员则不同。我们现在就被驱使去寻找我们的错误，所以我们不必忍受别人稍后发现我们的错误的耻辱。

<a id="d24e26805"></a>
寻找错误有点像用网捕鱼。我们使用细小的网（单元测试）来捕捉小鱼，使用大的、粗的网（集成测试）来捕捉杀人鲨。有时鱼会设法逃脱，所以我们修补我们发现的任何漏洞，希望能够发现在我们的项目池中游动的越来越多的滑溜缺陷。

**提示 90：尽早测试、经常测试、自动测试**

<a id="d24e26835"></a>
我们希望一旦有了代码就开始测试。这些小鱼有一个令人讨厌的习惯，它们很快就会变成巨大的食人鲨鱼，而捕捉鲨鱼则相当困难。所以我们编写单元测试。很多单元测试。

<a id="d24e26837"></a>
事实上，一个好的项目很可能拥有比生产代码更多的测试代码。生成此测试代码所花费的时间是值得的。从长远来看，它最终会便宜得多，而且您实际上有机会生产出接近零缺陷的产品。

<a id="d24e26842"></a>
此外，知道您已通过测试可以让您高度确信一段代码已“完成”。

**提示 91：直到所有测试都运行才算完成编码**

<a id="d24e26850"></a>
自动构建运行所有可用的测试。重要的是要以“真实测试”为目标，换句话说，测试环境应该与生产环境紧密匹配。任何缝隙都是虫子滋生的地方。

<a id="d24e26866"></a>
构建可能涵盖几种主要类型的软件测试：单元测试；集成测试；验证和验证；和性能测试。

<a id="d24e26885"></a>
该列表并不完整，一些专门项目还需要各种其他类型的测试。但这给了我们一个很好的起点。

#### 单元测试

<a id="d24e26891"></a>
单元测试是执行模块的代码。我们在主题 41 [*测试代码*](<../07 While Coding/41 Test to Code - test_to_build.md#test_to_build>) 中对此进行了介绍。单元测试是我们将在本节中讨论的所有其他形式的测试的基础。如果这些部件不能单独工作，它们可能也不能很好地协同工作。您正在使用的所有模块都必须通过它们自己的单元测试，然后才能继续。

<a id="d24e26902"></a>
一旦所有相关模块都通过了各自的测试，您就可以进入下一阶段了。您需要测试整个系统中所有模块如何使用和交互。

#### 集成测试

<a id="d24e26907"></a>
集成测试表明，组成该项目的主要子系统能够正常工作并相互配合。有了良好的合同并经过充分测试，任何集成问题都可以轻松检测到。否则，整合就会成为错误滋生的沃土。事实上，它通常是系统中最大的错误来源。

<a id="d24e26919"></a>
集成测试实际上只是我们所描述的单元测试的扩展——您只是测试整个子系统如何履行其合同。

#### 验证与验证

<a id="d24e26924"></a>
一旦你有了可执行的用户界面或原型，你就需要回答一个非常重要的问题：用户告诉你他们想要什么，但这就是他们所需要的吗？

<a id="d24e26933"></a>
是否满足系统的功能需求？这也需要测试。回答错误问题的无错误系统并不是很有用。请注意最终用户访问模式以及它们与开发人员测试数据的不同之处（例如，请参阅有关笔触的故事 [这里](<../03 Basic Tools/20 Debugging - debug.md#stroke>)）。

#### 性能测试

<a id="d24e26954"></a>
性能或压力测试也可能是项目的重要方面。

<a id="d24e26978"></a>
问问自己，软件是否满足现实条件下的性能要求——预期的用户数、连接数或每秒事务数。它具有可扩展性吗？

<a id="d24e26980"></a>
对于某些应用程序，您可能需要专门的测试硬件或软件来真实地模拟负载。

#### 测试测试

<a id="d24e26985"></a>
因为我们无法编写完美的软件，所以我们也无法编写完美的测试软件。我们需要进行测试。

<a id="d24e26991"></a>
将我们的测试套件集视为一个精心设计的安全系统，旨在在出现错误时发出警报。测试安全系统还有什么比尝试闯入更好的方法呢？

<a id="d24e26993"></a>
在编写测试来检测特定错误后，故意引发错误并确保测试会抱怨。这确保了测试能够捕获真实发生的错误。

**提示 92：使用破坏者来测试您的测试**

<a id="d24e27006"></a>
<a id="FNPTR-81"></a>
如果您真的认真对待测试，请在源代码树中建立一个单独的分支，故意引入错误，并验证测试是否会捕获它们。在更高级别上，您可以使用 Netflix 的 Chaos Monkey[[81]](<../10 Postface/README.md#FOOTNOTE-81>) 之类的东西来中断（即“杀死”）服务并测试应用程序的弹性。

<a id="d24e27023"></a>
编写测试时，确保警报在应该响起的时候响起。

#### 彻底测试

<a id="d24e27028"></a>
一旦您确信您的测试是正确的，并且发现了您创建的错误，您如何知道您是否已经足够彻底地测试了代码库？

<a id="d24e27037"></a>
<a id="FNPTR-82"></a>
简短的回答是“你不会”，而且你永远不会。你可能会尝试尝试覆盖率分析工具，在测试期间监视代码并跟踪哪些代码行已执行，哪些代码行未执行。这些工具可帮助您大致了解测试的全面程度，但不要期望看到 100% 的覆盖率。[[82]](<../10 Postface/README.md#FOOTNOTE-82>)

<a id="d24e27049"></a>
即使您确实碰巧击中了每一行代码，但这也不是全部。重要的是您的程序可能具有的状态数量。状态并不等同于代码行。例如，假设您有一个接受两个整数的函数，每个整数可以是 0 到 999 之间的数字：

```
int test(int a, int b) {
  return a / (a + b);
}
```

<a id="d24e27080"></a>
理论上，这个三行函数有 1,000,000 个逻辑状态，其中 999,999 个可以正常工作，一个不能正常工作（当 a + b 等于 0 时）。仅仅知道您执行了这行代码并不能告诉您这一点 - 您需要识别程序的所有可能状态。不幸的是，总的来说，这是一个非常困难的问题。硬如：“在你解决之前，太阳将变成一个冰冷的硬块。”

**提示 93：测试状态覆盖率，而不是代码覆盖率**

#### 基于属性的测试

<a id="d24e27097"></a>
探索代码如何处理意外状态的一个好方法是让计算机生成这些状态。

<a id="d24e27106"></a>
使用基于属性的测试技术根据被测代码的契约和不变量生成测试数据。我们在主题 42，[*基于属性的测试*](<../07 While Coding/42 Property-Based Testing - proptest.md#proptest>) 中详细介绍了这个主题。

### 收紧网络

<a id="d24e27116"></a>
最后，我们想揭示测试中最重要的一个概念。这是显而易见的，几乎所有教科书都说要这样做。但由于某种原因，大多数项目仍然没有这样做。

<a id="d24e27127"></a>
如果错误漏掉了现有测试的网，您下次需要添加新的测试来捕获它。

**提示 94：一次查找错误**

<a id="d24e27138"></a>
一旦人类测试人员发现错误，这应该是人类测试人员最后一次发现该错误。从那时起，应该修改自动化测试以检查该特定错误，每次都无一例外，无论多么微不足道，无论开发人员如何抱怨并说：“哦，这种情况永远不会再发生了。”

<a id="d24e27152"></a>
因为它会再次发生。我们只是没有时间去追踪自动化测试可以为我们发现的错误。我们必须花时间编写新代码和新错误。

### 全自动化

<a id="d24e27161"></a>
正如我们在本节开头所说，现代开发依赖于脚本化的自动过程。无论您使用像带有 rsync 和 ssh 的 shell 脚本这样简单的东西，还是使用 Ansible、Puppet、Chef 或 Salt 等功能齐全的解决方案，都不要依赖任何手动干预。

<a id="d24e27167"></a>
曾几何时，我们在一个客户端站点，所有开发人员都使用相同的 IDE。他们的系统管理员为每个开发人员提供了一组有关将附加包安装到 IDE 的说明。这些说明填满了很多页——充满了点击这里、滚动那里、拖动这个、双击那个，然后再做一次的页面。

<a id="d24e27169"></a>
毫不奇怪，每个开发人员的机器的加载情况都略有不同。当不同的开发人员运行相同的代码时，应用程序的行为会出现细微的差异。错误会出现在一台机器上，但不会出现在其他机器上。追踪任何一个组件的版本差异通常会带来惊喜。

**提示 95：不要使用手动程序**

<a id="d24e27181"></a>
人只是不像计算机那样具有可重复性。我们也不应该期望他们如此。 shell 脚本或程序将一次又一次地以相同的顺序执行相同的指令。它本身处于版本控制之下，因此您也可以检查构建/发布过程随时间的变化（“但它曾经有效……”）。

<a id="d24e27186"></a>
<a id="FNPTR-83"></a>
一切都取决于自动化。除非构建是全自动的，否则您无法在匿名云服务器上构建项目。如果涉及手动步骤，则无法自动部署。一旦你引入手动步骤（“仅针对这一部分......”），你就打破了一个非常大的窗口。[[83]](<../10 Postface/README.md#FOOTNOTE-83>)

<a id="d24e27212"></a>
有了版本控制、严格测试和完全自动化这三个支柱，您的项目将拥有所需的坚实基础，这样您就可以专注于困难的部分：取悦用户。

<a id="d24e27288"></a>
- 您的夜间或连续构建是自动的，但部署到生产环境不是吗？为什么？该服务器有什么特别之处？
- 你能完全自动测试你的项目吗？许多团队被迫回答“不”。为什么？定义可接受的结果是否太难？这会不会让向赞助商证明该项目已经“完成”变得困难？
