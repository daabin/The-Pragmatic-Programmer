## 主题 52. 让用户感到愉悦

> 当你迷惑人们时，你的目标不是从他们身上赚钱或让他们做你想做的事，而是让他们充满快乐。
>
> 盖·川崎

<a id="d24e27315"></a>
作为开发者，我们的目标是取悦用户。这就是我们在这里的原因。不要挖掘他们的数据，或者数他们的眼球，或者掏空他们的钱包。撇开邪恶的目标不谈，即使及时交付工作软件也是不够的。仅此一点不会让他们高兴。

<a id="d24e27353"></a>
您的用户并不是特别受代码驱动。相反，他们有一个需要在其目标和预算范围内解决的业务问题。他们相信，通过与您的团队合作，他们将能够做到这一点。

<a id="d24e27355"></a>
他们的期望与软件无关。他们甚至没有隐含在他们给您的任何规范中（因为在您的团队与他们一起迭代几次之前，该规范将是不完整的）。

<a id="d24e27357"></a>
那么你如何挖掘他们的期望呢？问一个简单的问题：

<a id="d24e27369"></a>
> 你怎么知道我们一个月（或一年）都取得了成功，
> 或其他什么）这个项目完成后？

<a id="d24e27371"></a>
您可能会对答案感到惊讶。一个改进产品推荐的项目实际上可以根据客户保留率来判断；一个整合两个数据库的项目可能会根据数据质量来评判，或者可能会根据成本节省来评判。但真正重要的是这些对商业价值的期望，而不仅仅是软件项目本身。该软件只是达到这些目的的一种手段。

<a id="d24e27377"></a>
现在您已经了解了项目背后的一些潜在价值期望，您可以开始思考如何实现这些期望：

<a id="d24e27381"></a>
<a id="d24e27384"></a>
<a id="d24e27387"></a>
<a id="d24e27397"></a>
- 确保团队中的每个人都完全清楚这些期望。
- 在做出决定时，请考虑哪条前进道路更接近这些期望。
- 根据期望批判性地分析用户需求。在许多项目中，我们发现所说的“需求”实际上只是对技术可以做什么的猜测：它实际上是一个伪装成需求文件的业余实施计划。如果您能够证明这些建议将使项目更接近目标，请不要害怕提出改变需求的建议。
- 随着项目的进展，继续考虑这些期望。

<a id="d24e27399"></a>
我们发现，随着我们对该领域的了解不断增加，我们能够更好地就解决潜在业务问题的其他事情提出建议。我们坚信，接触过组织的许多不同方面的开发人员通常可以找到将业务的不同部分编织在一起的方法，而这些方法对于各个部门来说并不总是显而易见的。

**提示 96：取悦用户，而不仅仅是提供代码**

<a id="d24e27408"></a>
如果您想让客户满意，请与他们建立一种可以积极帮助解决他们问题的关系。尽管您的头衔可能是“软件开发人员”或“软件工程师”的某种变体，但实际上它应该是“问题解决者”。这就是我们所做的，这就是务实程序员的本质。

<a id="d24e27419"></a>
