## 主题 47. 协作共事

> 我从来没有见过一个人愿意阅读 17,000 页的文档，如果有的话，我会杀了他，把他从基因库中救出来。
>
> 约瑟夫·科斯特洛，Cadence 总裁

<a id="d24e25212"></a>
这是那些“不可能”的项目之一，你听到的那种项目听起来既令人兴奋又令人恐惧。一个古老的系统即将报废，硬件将逐渐消失，必须精心设计一个全新的系统来完全匹配（通常没有记录的）行为。其他人的数亿美元资金将通过这个系统，而从启动到部署的最后期限大约是几个月。

<a id="d24e25226"></a>
这就是安迪和戴夫第一次见面的地方。这是一个不可能完成的项目，截止日期也很荒谬。只有一件事使该项目取得了巨大成功。管理这个系统多年的专家就坐在她的办公室里，就在我们扫帚柜大小的开发室的对面。持续提供问题、澄清、决策和演示。

<a id="d24e25228"></a>
在本书中，我们建议与用户密切合作；他们是您团队的一部分。在第一个项目中，我们练习了现在所谓的结对编程或群体编程：一个人键入代码，而一个或多个其他团队成员一起评论、思考和解决问题。这是一种强大的合作方式，超越了无休止的会议、备忘录和冗长的法律文件，这些文件的重要性超过了实用性。

<a id="d24e25267"></a>
这就是我们所说的“合作”的真正含义：不仅仅是提出问题、进行讨论和做笔记，而是在实际编码时提出问题和进行讨论。

康威定律

1967 年，梅尔文·康威 (Melvin Conway) 在 [*委员会如何发明？* [Con68]](<../A2 Exercise Answers/README.md#d6040e240>) 中提出了一个想法，后来被称为康威定律：

> 设计系统受限的组织只能生产这些组织的通信结构的副本。

也就是说，团队和组织的社会结构和沟通途径将反映在正在开发的应用程序、网站或产品中。各种研究都强烈支持这一想法。我们无数次亲眼目睹过这种情况，例如，在团队中根本没有人相互交谈，从而导致了孤立的“烟囱”系统。或者团队被分成两部分，导致客户端/服务器或前端/后端划分。

研究还支持相反的原则：您可以按照您希望代码的外观有意地构建您的团队。例如，地理上分散的团队倾向于使用更加模块化、分布式的软件。

但最重要的是，包括用户在内的开发团队将生产出明确反映这种参与的软件，而不费心的团队也会反映这一点。

### 结对编程

<a id="d24e25324"></a>
结对编程是极限编程的实践之一，它已在 XP 本身之外变得流行。在结对编程中，一名开发人员操作键盘，而另一名开发人员则不操作。两人一起解决问题，并可以根据需要切换打字职责。

<a id="d24e25334"></a>
结对编程有很多好处。不同的人带来不同的背景和经验、不同的解决问题的技巧和方法，以及对任何特定问题的不同程度的关注和关注。作为打字员的开发人员必须关注语法和编码风格的低级细节，而其他开发人员可以自由考虑更高级别的问题和范围。虽然这听起来似乎是一个很小的区别，但请记住，我们人类的大脑带宽只有这么多。摆弄输入编译器勉强接受的深奥单词和符号需要我们自己的处理能力相当多。在任务期间拥有第二个开发人员的完整大脑可以带来更多的精神力量。

<a id="d24e25336"></a>
第二个人固有的同伴压力有助于避免脆弱的时刻和命名变量 foo 等的坏习惯。当有人积极观看时，您不太愿意采取可能令人尴尬的捷径，这也会带来更高质量的软件。

### 群体编程

<a id="d24e25344"></a>
如果两个头脑比一个头脑好，那么让十几个不同的人同时与一名打字员一起处理同一问题怎么样？

<a id="d24e25358"></a>
暴徒编程，尽管有这个名字，并不涉及火把或干草叉。它是结对编程的扩展，不仅仅涉及两个开发人员。支持者报告了使用生物来解决难题的巨大成果。暴民很容易包括通常不被视为开发团队一部分的人员，包括用户、项目发起人和测试人员。事实上，在我们一起完成的第一个“不可能”项目中，常见的景象是我们中的一个人正在打字，而另一个人则与我们的业务专家讨论这个问题。这是一个三人的小暴徒。

<a id="d24e25367"></a>
您可能会将 mob 编程视为与实时编码的紧密协作。

### 我应该怎么办？

<a id="d24e25374"></a>
如果您目前只是单独编程，也许可以尝试结对编程。至少给它两周的时间，一次只能几个小时，因为一开始会感觉很奇怪。要集思广益新想法或诊断棘手问题，也许可以尝试一下群体编程会议。

<a id="d24e25376"></a>
如果你们已经在结对或围攻，包括谁？仅仅是开发人员，还是允许扩展团队的成员参与：用户、测试人员、赞助商……？

<a id="d24e25382"></a>
与所有协作一样，您需要管理其人员方面和技术方面。以下是一些入门技巧：

- 构建代码，而不是你的自我。这不在于谁最聪明，而在于谁最聪明。我们都有自己的时刻，无论好坏。
- 从小处开始。仅由 4-5 人组成的暴徒，或者从几对人开始，在短时间内进行。
- 批评代码，而不是人。 “让我们看看这个区块”听起来比“你错了”要好得多。
- 倾听并尝试理解他人的观点。不同并没有错。
- 经常进行回顾，以便下次尝试改进。

<a id="d24e25400"></a>
在同一个办公室或远程进行编码，无论是单独、成对还是集体编码，都是共同解决问题的有效方法。如果您和您的团队只以一种方式做过，您可能想尝试不同的风格。但不要只是采用天真的方法：每种开发风格都有规则、建议和指南。例如，在群体编程中，你每 5-10 分钟就更换一次打字员。

<a id="d24e25402"></a>
从教科书和经验报告中进行一些阅读和研究，并了解您可能遇到的优势和陷阱。您可能想从编写一个简单的练习开始，而不是直接跳到最难的生产代码。
