<a id="requirements"></a>
## 主题 45. 需求陷阱

> 完美的实现，不是在没有什么可以添加的时候，而是在没有什么可以删除的时候......
>
> 安托万·德·圣埃克苏佩里，《风、沙和星星》，1939

<a id="d24e24372"></a>
许多书籍和教程都将需求收集视为项目的早期阶段。 “聚集”这个词似乎暗示着一群快乐的分析师，在田园交响乐在背景中轻轻演奏的同时，在他们周围的地面上寻找智慧的金块。 “聚集”意味着需求已经有了，你只需找到它们，将它们放入你的篮子里，然后就可以愉快地上路了。

<a id="d24e24381"></a>
但事实并非如此。需求很少停留在表面上。通常，它们深深地埋藏在假设、误解和政治的层层之下。更糟糕的是，它们通常根本不存在。

**提示 75：没有人确切知道自己想要什么**

### 需求神话

<a id="d24e24392"></a>
在软件发展的早期，计算机比使用计算机的人更有价值（按每小时摊销成本计算）。我们通过尝试第一次就把事情做对来节省资金。该过程的一部分是试图准确地指定我们要让机器做什么。我们首先获取需求规范，将其转化为设计文档，然后转化为流程图和伪代码，最后转化为代码。不过，在将其输入计算机之前，我们会花时间进行桌面检查。

<a id="d24e24403"></a>
这花了很多钱。这种成本意味着人们只有在确切知道自己想要什么时才会尝试实现自动化。由于早期的机器相当有限，它们解决的问题范围也受到限制：实际上可以在开始之前理解整个问题。

<a id="d24e24408"></a>
但这不是真实的世界。现实世界是混乱的、冲突的、未知的。在那个世界里，任何事物的精确规格即使不是完全不可能，也是很少见的。

<a id="d24e24410"></a>
这就是我们程序员的用武之地。我们的工作是帮助人们理解他们想要什么。事实上，这可能是我们最有价值的属性。值得重复的是：

**提示 76：程序员帮助人们了解他们想要什么**

### 编程作为治疗

<a id="d24e24425"></a>
让我们把那些要求我们编写软件的人称为我们的客户。

<a id="d24e24446"></a>
典型的客户是带着需求来找我们的。这种需求可能是战略性的，但也可能是战术性的问题：对当前问题的回应。需要可能是对现有系统进行更改，或者可能需要新的东西。需求有时会以业务术语表达，有时会以技术术语表达。

<a id="d24e24448"></a>
新开发人员经常犯的错误是接受这种需求陈述并为其实施解决方案。

<a id="d24e24450"></a>
根据我们的经验，这种最初的需求声明并不是绝对的要求。客户可能没有意识到这一点，但这确实是一个探索的邀请。

<a id="d24e24452"></a>
让我们举一个简单的例子。

<a id="d24e24454"></a>
您在纸质书和电子书出版商工作。您收到了一个新要求：

<a id="d24e24457"></a>
> 所有价值 50 美元或以上的订单均应免运费。

<a id="d24e24459"></a>
停下来想象一下自己处于那个位置。你首先想到的是什么？

<a id="d24e24461"></a>
您很有可能有疑问：

- 50元含税吗？
- 50 美元包含当前运费吗？
- 50 美元是否必须用于购买纸质书，还是订单中也可以包含电子书？
- 提供什么类型的运输？优先事项？地面？
- 国际订单呢？
- 50 美元的限额未来多久会改变一次？

<a id="d24e24483"></a>
这就是我们所做的。当给出一些看似简单的东西时，我们会通过寻找边缘情况并询问它们来惹恼人们。

<a id="d24e24485"></a>
客户很可能已经想到了其中的一些，并且只是假设实施会以这种方式进行。问这个问题只会把这些信息冲掉。

<a id="d24e24487"></a>
但其他问题可能是客户之前没有考虑过的。这就是事情变得有趣的地方，也是优秀开发人员学会外交的地方。

<a id="d24e24491"></a>
<a id="d24e24494"></a>
<a id="d24e24497"></a>
<a id="d24e24500"></a>
<a id="d24e24503"></a>
<a id="d24e24505"></a>
<a id="d24e24508"></a>
您： : 我们想知道总共 50 美元。这包括我们通常收取的运费吗？

客户：：当然可以。这是他们付给我们的总金额。

您: : 这对我们的客户来说很好而且简单易懂：我可以看到它的吸引力。但我可以看到一些不那么谨慎的客户试图利用该系统。

客户：：怎么会这样？

你: : 好吧，假设他们花 25 美元买一本书，然后选择隔夜运送，这是最昂贵的选择。这可能大约是 30 美元，整个订单的价格是 55 美元。然后我们会提供免费送货服务，一本 25 美元的书他们只需 25 美元即可享受隔夜送货服务。

（此时经验丰富的开发人员停下来。提供事实，并让客户做出决定，）

客户： ：哎哟。这当然不是我的本意。我们会因为这些订单而赔钱。有哪些选择？

<a id="d24e24510"></a>
这就开始了探索。您在此的角色是解释客户所说的话并向他们反馈其含义。这既是一个智力过程，也是一个创造性的过程：你正在思考，你正在贡献一种解决方案，该解决方案可能比你或客户单独制定的解决方案更好。

### 需求是一个过程

<a id="d24e24515"></a>
在前面的示例中，开发人员接受了需求并将结果反馈给客户。探索由此展开。在探索过程中，当客户使用不同的解决方案时，您可能会得到更多反馈。这是所有需求收集的现实：

**提示 77：需求是在反馈循环中学习的**

<a id="d24e24537"></a>
您的工作是帮助客户了解其规定要求的后果。您可以通过生成反馈并让他们利用该反馈来完善他们的思维来做到这一点。

<a id="d24e24539"></a>
在前面的例子中，反馈很容易用语言表达。有时情况并非如此。老实说，有时您对该领域的了解还不够具体。

<a id="d24e24541"></a>
在这些情况下，务实的程序员依赖于“这是你的意思吗？”反馈学校。我们制作模型和原型，并让客户使用它们。理想情况下，我们生产的东西足够灵活，我们可以在与客户讨论时改变它们，让我们用“更像这样？”来回应“这不是我的意思”。

<a id="d24e24552"></a>
有时，这些模型可以在一个小时左右的时间内拼凑在一起。显然，它们只是为了传达想法而进行的黑客活动。

<a id="d24e24554"></a>
但现实是我们所做的所有工作实际上都是某种形式的模型。即使在项目结束时，我们仍在解释客户的需求。事实上，到那时我们可能会拥有更多的客户：质量检查人员、运营人员、营销人员，甚至可能还有测试客户群。

<a id="d24e24559"></a>
因此，务实的程序员将整个项目视为需求收集练习。这就是为什么我们更喜欢短迭代；以直接客户反馈结束的。这让我们保持在正轨上，并确保如果我们确实走错了方向，损失的时间可以最小化。

### 设身处地为客户着想

<a id="d24e24570"></a>
<a id="FNPTR-70"></a>
有一个简单的技巧可以深入客户的头脑，但目前使用得并不多：成为客户。您正在为帮助台编写系统吗？花几天时间与经验丰富的支持人员一起监控电话。您正在自动化手动库存控制系统吗？在仓库工作一周。[[70]](<48 The Essence of Agility - essence_of_agility.md#FOOTNOTE-70>)

<a id="d24e24579"></a>
除了让您深入了解系统的实际使用方式之外，您还会惊讶地发现“您工作期间我可以旁听一周吗？”这样的请求如何有助于建立信任并为与客户沟通奠定基础。请记住不要妨碍！

**提示 78：与用户合作，像用户一样思考**

<a id="d24e24593"></a>
收集反馈也是开始与客户群建立融洽关系的时候，了解他们对您正在构建的系统的期望和希望。有关更多信息，请参阅主题 52，[*取悦您的用户*](<../09 Pragmatic Projects/52 Delight Your Users - delight.md#delight>)。

### 要求与政策

<a id="d24e24600"></a>
让我们想象一下，在讨论人力资源系统时，客户说“只有员工的主管和人事部门可以查看该员工的记录。”这个声明真的是一个要求吗？也许在今天，但它将商业政策嵌入到了绝对的声明中。

<a id="d24e24611"></a>
商业政策？要求？这是一个相对微妙的区别，但它将对开发人员产生深远的影响。如果要求表述为“只有主管和人员可以查看员工记录”，则开发人员最终可能会在每次应用程序访问此数据时编写显式测试。然而，如果声明是“只有授权用户可以访问员工记录”，开发人员可能会设计和实现某种访问控制系统。当政策发生变化时（而且确实会发生变化），只需更新该系统的元数据。事实上，以这种方式收集需求自然会引导您获得一个经过精心设计以支持元数据的系统。

<a id="d24e24613"></a>
事实上，这里有一个一般规则：

**提示 79：策略就是元数据**

<a id="d24e24633"></a>
实施一般情况，以策略信息作为系统需要支持的事物类型的示例。

### 需求与现实

<a id="d24e24639"></a>
<a id="FNPTR-71"></a>
在 1999 年 1 月的《连线》杂志文章中，[[71]](<48 The Essence of Agility - essence_of_agility.md#FOOTNOTE-71>) 制作人兼音乐家 Brian Eno 描述了一项令人难以置信的技术——终极混音板。它可以做任何听起来可以做的事情。然而，它并没有让音乐家创作出更好的音乐，或者更快或更便宜地制作唱片，反而成为障碍；它扰乱了创作过程。

<a id="d24e24651"></a>
要了解原因，您必须了解录音工程师的工作方式。他们直观地平衡声音。多年来，他们在耳朵和指尖之间形成了一种天生的反馈回路——滑动推子、旋转旋钮等等。然而，新混音器的界面并没有利用这些功能。相反，它强迫用户使用键盘打字或单击鼠标。它提供的功能很全面，但它们的包装方式却是陌生的、奇特的。工程师所需的功能有时隐藏在晦涩的名称后面，或者通过基本设施的非直观组合来实现。

<a id="d24e24653"></a>
这个例子也说明了我们的信念：成功的工具会适应使用它们的手。成功的需求收集会考虑到这一点。这就是为什么早期的反馈，包括原型或曳光弹，会让你的客户说“是的，它做到了我想要的，但不是我想要的。”

### 记录要求

<a id="d24e24690"></a>
我们相信最好的需求文档，也许是唯一的需求文档，是工作代码。

<a id="d24e24704"></a>
但这并不意味着您可以在不记录您对客户需求的理解的情况下逃脱。这只是意味着这些文件不是可交付成果：它们不是您交给客户签署的东西。相反，它们只是帮助指导实施过程的里程碑。

#### 需求文档不适合客户

<a id="d24e24709"></a>
过去，安迪和戴夫都参与过产生极其详细需求的项目。这些实质性文件扩展了客户最初对所需内容的两分钟解释，产生了充满图表和表格的一英寸厚的杰作。事情已经明确到实施中几乎没有任何歧义的余地。如果有足够强大的工具，该文档实际上可能是最终的程序。

<a id="d24e24723"></a>
创建这些文档是一个错误，原因有两个。首先，正如我们所讨论的，客户事先并不真正知道他们想要什么。因此，当我们采纳他们的说法并将其扩展为几乎是法律文件时，我们正在流沙上建造一座极其复杂的城堡。

<a id="d24e24725"></a>
您可能会说“但是我们会将文件交给客户并由他们签字。我们正在收到反馈。”这给我们带来了这些需求规范的第二个问题：客户从不阅读它们。

<a id="d24e24727"></a>
客户使用程序员是因为，虽然客户的动机是解决高级且有些模糊的问题，但程序员对所有细节和细微差别感兴趣。需求文档是为开发人员编写的，其中包含的信息和微妙之处有时对客户来说难以理解且常常令人厌烦。

<a id="d24e24729"></a>
提交一份 200 页的需求文档，客户可能会掂量它来决定它是否足够重要，他们可能会阅读前几段（这就是为什么前两段总是标题为“管理摘要”），他们可能会快速浏览其余的内容，有时在出现清晰的图表时会停下来。

<a id="d24e24734"></a>
这并没有让客户失望。但给他们一份大型技术文档就像给普通开发人员一本荷马希腊语的《伊利亚特》并要求他们从中编写视频游戏代码。

#### 需求文档用于规划

<a id="d24e24742"></a>
因此，我们不相信单一的、重得足以使牛晕倒的需求文档。然而，我们确实知道必须写下需求，仅仅是因为团队中的开发人员需要知道他们将要做什么。

<a id="d24e24744"></a>
这采取什么形式？我们喜欢可以放在真实（或虚拟）索引卡上的东西。这些简短的描述通常称为用户故事。它们从该功能的用户的角度描述了应用程序的一小部分应该做什么。

<a id="d24e24761"></a>
当以这种方式编写时，可以将需求放在板上并移动以显示状态和优先级。

<a id="d24e24763"></a>
您可能认为单个索引卡无法保存实现应用程序组件所需的信息。你是对的。这就是重点的一部分。通过保持简短的需求声明，您可以鼓励开发人员提出澄清问题。在创建每段代码之前和期间，您正在增强客户和编码人员之间的反馈流程。

### 过度规格

<a id="d24e24777"></a>
生成需求文档的另一个大危险是过于具体。好的需求是抽象的。就需求而言，准确反映业务需求的最简单的陈述是最好的。这并不意味着您可以含糊其辞 - 您必须捕获底层语义不变量作为需求，并将特定或当前的工作实践记录为政策。

<a id="d24e24786"></a>
需求不是架构。需求不是设计，也不是用户界面。要求就是需要。

### 又多了一颗薄薄的薄荷糖……

<a id="d24e24798"></a>
许多项目失败都归咎于范围的扩大——也称为功能膨胀、蠕变特征主义或需求蔓延。这是主题 4 [*石汤和水煮田鸡*](<../01 Pragmatic Philosophy/04 Stone Soup and Boiled Frogs - stone_soup.md#stone_soup>) 中的水煮青蛙综合症的一个方面。我们可以做些什么来防止需求不断增加？

<a id="d24e24822"></a>
答案（再次）是反馈。如果您与客户进行迭代合作并提供持续的反馈，那么客户将亲身体验“再增加一个功能”的影响。他们会看到黑板上出现另一张故事卡，并且他们将帮助选择另一张卡进入下一次迭代以腾出空间。反馈是双向的。

<a id="pglossary"></a>
### 维护词汇表

<a id="d24e24827"></a>
一旦开始讨论需求，用户和领域专家就会使用某些对他们有特定含义的术语。例如，他们可能会区分“客户”和“顾客”。那么在系统中随意使用这两个词都是不合适的。

<a id="d24e24846"></a>
创建和维护项目术语表——定义项目中使用的所有特定术语和词汇的地方。项目的所有参与者，从最终用户到支持人员，都应使用术语表以确保一致性。这意味着术语表需要能够广泛访问——这是在线文档的一个很好的论点。

**提示 80：使用项目术语表**

<a id="d24e24857"></a>
如果用户和开发人员使用不同的名称来调用同一事物，或者更糟糕的是，使用相同的名称来引用不同的事物，那么项目就很难取得成功。
