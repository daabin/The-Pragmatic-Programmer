## 主题 48. 敏捷的本质

> 你一直用这个词，我不认为它的意思是你认为的意思。
>
> 伊尼戈·蒙托亚《公主新娘》

<a id="d24e25436"></a>
敏捷是一个形容词：它是你做某事的方式。您可以成为一名敏捷开发人员。您可以加入一个采用敏捷实践的团队，一个能够敏捷地应对变化和挫折的团队。敏捷是你的风格，而不是你。

**提示 83：敏捷不是一个名词；敏捷是你做事的方式**

<a id="d24e25456"></a>
<a id="FNPTR-73"></a>
当我们撰写本文时，《敏捷软件开发宣言》发布近 20 年了，[[73]](#FOOTNOTE-73) 我们看到许多开发人员成功地应用了其价值观。我们看到许多出色的团队找到了采用这些价值观的方法，并用它们来指导他们的工作，以及如何改变他们的工作。

<a id="d24e25465"></a>
<a id="FNPTR-74"></a>
但我们也看到了敏捷性的另一面。我们看到团队和公司渴望现成的解决方案：Agile-in-a-Box。我们看到许多顾问和公司都非常乐意向他们出售他们想要的东西。我们看到公司采用了更多的管理层次、更正式的报告、更专业的开发人员和更奇特的职位名称，这些职位名称只是意味着“有剪贴板和秒表的人”。[[74]](#FOOTNOTE-74)

<a id="d24e25472"></a>
我们认为许多人已经忽视了敏捷性的真正含义，我们希望看到人们回归基础知识。

<a id="d24e25478"></a>
记住宣言中的价值观：

<a id="d24e25483"></a>
> 我们正在探索更好的发展方式
> 通过做事并帮助别人做事来开发软件。
> 通过这项工作，我们认识到：

<a id="d24e25516"></a>
<a id="d24e25521"></a>
<a id="d24e25526"></a>
<a id="d24e25531"></a>
> - **个人和互动**超过流程和工具
> - **工作软件**优于全面的文档
> - **客户合作** 通过合同谈判
> - **响应变化**而不是遵循计划

<a id="d24e25537"></a>
> 也就是说，虽然上面的物品有价值
> 右边的东西，我们更看重左边的东西。

<a id="d24e25539"></a>
任何人向你推销的东西会增加右边事物比左边事物的重要性，显然他们并不像我们和其他宣言作者那样重视同样的事情。

<a id="d24e25543"></a>
任何向您出售盒装解决方案的人都没有阅读介绍性声明。这些价值观是由不断发现更好的软件生产方法的行为所激发和传达的。这不是静态文档。这是对生成过程的建议。

### 永远不可能有敏捷流程

<a id="d24e25548"></a>
事实上，每当有人说“这样做，你就会变得敏捷”，他们都是错的。根据定义。

<a id="d24e25550"></a>
因为无论是在物理世界还是在软件开发中，敏捷性都是为了响应变化，响应出发后遇到的未知因素。奔跑的瞪羚不会走直线。当体操运动员对环境变化和脚部放置的微小错误做出反应时，他们每秒会进行数百次纠正。

<a id="d24e25552"></a>
团队和个人开发人员也是如此。开发软件时没有可以遵循的单一计划。四个值中的三个告诉您这一点。它们都是关于收集和回应反馈。

<a id="d24e25558"></a>
这些值不会告诉您要做什么。当您自己决定做什么时，它们会告诉您要寻找什么。

<a id="d24e25560"></a>
这些决策始终与上下文有关：它们取决于您是谁、您的团队的性质、您的应用程序、您的工具、您的公司、您的客户、外部世界；数量惊人的因素，有些是主要的，有些是微不足道的。没有固定的、静态的计划能够应对这种不确定性。

### 那么我们该怎么办？

<a id="d24e25565"></a>
没有人可以告诉你该怎么做。但我们认为我们可以告诉您一些有关您这样做的精神。这一切都归结为你如何应对不确定性。该宣言建议您通过收集反馈并根据反馈采取行动来做到这一点。因此，这是我们以敏捷方式工作的秘诀：

|  |
| --- |
|  |
| 1. 弄清楚你在哪里。 |
|  |
| 2. 朝着你想要达到的目标迈出最小且有意义的一步。 |
|  |
| 3. 评估你最终的结果，并修复你所破坏的一切。 |
|  |

<a id="d24e25597"></a>
重复这些步骤直到完成。并在您所做的每件事的每个级别递归地使用它们。

<a id="d24e25599"></a>
有时，当您收集反馈时，即使是看似最微不足道的决定也变得很重要。

<a id="d24e25603"></a>
<a id="d24e25611"></a>
<a id="d24e25625"></a>
“现在我的代码需要获取帐户所有者。

```
let user = accountOwner(accountID);
```

嗯……用户是个无用的名字。我会让它成为主人。

```
let owner = accountOwner(accountID);
```

但现在感觉有点多余。我到底想在这里做什么？该故事称我正在向此人发送一封电子邮件，因此我需要找到他们的电子邮件地址。也许我根本不需要整个帐户所有者。

```
let email = emailOfAccountOwner(accountID);
```

<a id="d24e25634"></a>
通过在非常低的级别（变量的命名）应用反馈循环，我们实际上改进了整个系统的设计，减少了该代码与处理帐户的代码之间的耦合。

<a id="d24e25645"></a>
反馈循环也适用于项目的最高级别。当我们开始满足客户的需求，迈出一步，并意识到我们要做的事情是不必要的，最好的解决方案甚至不涉及软件时，我们最成功的工作就发生了。

<a id="d24e25647"></a>
此循环适用于单个项目的范围之外。团队应该应用它来审查他们的流程及其运作情况。不不断试验其流程的团队不是敏捷团队。

### 这推动了设计

<a id="d24e25652"></a>
在主题 8 [*优秀设计的本质*](<../02 Pragmatic Approach/08 The Essence of Good Design - essence_of_design.md#essence_of_design>) 中，我们断言设计的衡量标准是设计结果更改的难易程度：好的设计比坏的设计更容易更改。

<a id="d24e25660"></a>
关于敏捷性的讨论解释了为什么会出现这种情况。

<a id="d24e25665"></a>
你做出改变，却发现你不喜欢它。我们列表中的第三步表示我们必须能够修复我们所遇到的问题。为了使我们的反馈循环高效，此修复必须尽可能轻松。如果不是，我们就会想耸耸肩，不去修复它。我们在主题 3，[*软件熵*](<../01 Pragmatic Philosophy/03 Software Entropy - no_broken_windows.md#no_broken_windows>) 中讨论这种效果。为了使整个敏捷工作发挥作用，我们需要实践良好的设计，因为良好的设计使事情易于改变。如果改变很容易，我们就可以毫不犹豫地在各个层面进行调整。

<a id="d24e25669"></a>
这就是敏捷性。

### 挑战

<a id="d24e25688"></a>
简单的反馈循环不仅仅适用于软件。想想你最近做出的其他决定。如果事情没有把你引向你想要的方向，你可以通过思考如何撤销它们来改进其中的任何一个吗？您能想出通过收集反馈并采取行动来改进工作的方法吗？
