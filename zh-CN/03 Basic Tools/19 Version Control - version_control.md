## 主题 19. 版本控制

> 进步远不在于改变，而是取决于保持力。那些不记得过去的人注定要重蹈覆辙。
>
> 乔治·桑塔亚纳《理性的生活》

<a id="d24e7614"></a>
我们在用户界面中寻找的重要内容之一是撤消键——一个可以原谅我们错误的按钮。如果环境支持多个级别的撤消和重做，那就更好了，这样您就可以返回并从几分钟前发生的事情中恢复。

<a id="d24e7628"></a>
但是，如果错误发生在上周，并且此后您已打开和关闭计算机十次怎么办？嗯，这是使用版本控制系统 (VCS) 的众多好处之一：它是一个巨大的撤消键 - 一个项目范围的时间机器，可以让您回到上周代码实际编译和运行时的宁静日子。

<a id="d24e7637"></a>
对于许多人来说，这就是他们使用 VCS 的限制。这些人错过了一个更大的协作、部署管道、问题跟踪和一般团队交互的世界。

<a id="d24e7643"></a>
因此，让我们来看看 VCS，首先将其作为更改存储库，然后将其作为团队及其代码的中央会议场所。

<a id="d24e7661"></a>

共享目录不是版本控制

我们仍然偶尔会遇到通过网络共享项目源文件的团队：无论是在内部还是使用某种云存储。

这是不可行的。

这样做的团队不断地搞乱彼此的工作、丢失变更、破坏构建以及在停车场打架。这就像编写具有共享数据且没有同步机制的并发代码。使用版本控制。

但还有更多！有些人确实使用版本控制，并将其主存储库保存在网络或云驱动器上。他们认为这是两全其美的：他们的文件可以在任何地方访问，并且（在云存储的情况下）它可以异地备份。

事实证明，这更糟，你可能会失去一切。版本控制软件使用一组交互的文件和目录。如果两个实例同时进行更改，则整体状态可能会被破坏，并且无法确定会造成多大的损害。没有人喜欢看到开发人员哭泣。

### 从源头开始

<a id="d24e7685"></a>
版本控制系统会跟踪您在源代码和文档中所做的每一个更改。通过正确配置的源代码控制系统，您始终可以返回到软件的先前版本。

<a id="d24e7693"></a>
但版本控制系统的作用远不止于消除错误。好的 VCS 可以让您跟踪更改，回答以下问题：谁对这行代码进行了更改？当前版本和上周的有什么区别？在此版本中我们更改了多少行代码？哪些文件最常更改？此类信息对于错误跟踪、审计、性能和质量目的非常宝贵。

<a id="d24e7719"></a>
VCS 还可以让您识别软件的版本。一旦确定，您将始终能够返回并重新生成版本，而与以后可能发生的更改无关。

<a id="d24e7725"></a>
版本控制系统可以将它们维护的文件保存在中央存储库中——这是归档的绝佳选择。

<a id="d24e7736"></a>
最后，版本控制系统允许两个或更多用户同时处理同一组文件，甚至可以同时对同一文件进行更改。然后，当文件发送回存储库时，系统会管理这些更改的合并。尽管看似有风险，但此类系统在各种规模的项目实践中都运行良好。

**提示 28：始终使用版本控制**

<a id="d24e7751"></a>
总是。 Even if you are a single-person team on a one-week project.即使它是一个“扔掉”的原型。即使你正在处理的东西不是源代码。确保一切都在版本控制之下：文档、电话号码列表、给供应商的备忘录、makefile、构建和发布程序、整理日志文件的小 shell 脚本——一切。我们通常对我们键入的所有内容（包括本书的文本）使用版本控制。即使我们不从事一个项目，我们的日常工作也受到安全保护。存储库。

### 拓展业务

<a id="d24e7768"></a>
版本控制系统不仅仅保留项目的单一历史记录。它们最强大和最有用的功能之一是它们让您将开发岛隔离成称为分支的东西。您可以在项目历史记录中的任何时间点创建分支，并且您在该分支中所做的任何工作都将与所有其他分支隔离。将来的某个时候，您可以将正在处理的分支合并回另一个分支，因此目标分支现在包含您在分支中所做的更改。多人甚至可以在一个分支上工作：在某种程度上，分支就像小克隆项目。

<a id="d24e7781"></a>
分支机构的好处之一是它们为您提供隔离。如果您在一个分支中开发功能 A，而队友在另一个分支中开发功能 B，那么你们不会互相干扰。

<a id="d24e7787"></a>
第二个好处可能令人惊讶，那就是分支通常是团队项目工作流程的核心。

<a id="d24e7793"></a>
这就是事情变得有点混乱的地方。版本控制分支和测试组织有一些共同点：他们都有成千上万的人告诉你应该如何做。这些建议基本上毫无意义，因为他们真正想说的是“这对我有用”。

<a id="d24e7795"></a>
因此，在项目中使用版本控制，如果遇到工作流程问题，请搜索可能的解决方案。当你获得经验时，请记住回顾和调整你正在做的事情。

将一整杯茶（英式早餐，加一点牛奶）洒在笔记本电脑键盘上。把机器带到聪明人酒吧，让他们皱起眉头。买一台新电脑。把它带回家。

需要多长时间才能使该计算机恢复到您第一次举起那个决定命运的杯子时的相同状态（包括所有 SSH 密钥、编辑器配置、shell 设置、安装的应用程序等）？这是我们最近面临的一个问题。

几乎所有定义原始计算机的配置和使用的内容都存储在版本控制中，包括：

- 所有用户首选项和点文件
- 编辑器配置
- 使用 Homebrew 安装的软件列表
- 用于配置应用程序的 Ansible 脚本
- 所有当前项目

到了下午，机器就恢复了。

### 作为项目中心的版本控制

<a id="d24e7837"></a>
尽管版本控制对于个人项目非常有用，但在与团队合作时它才真正发挥作用。其中大部分价值来自于您托管存储库的方式。

<a id="d24e7853"></a>
现在，许多版本控制系统不需要任何托管。它们是完全去中心化的，每个开发人员都在点对点的基础上进行合作。但即使有了这些系统，建立一个中央存储库也是值得的，因为一旦你这样做了，你就可以利用大量的集成来使项目流程变得更容易。

<a id="d24e7864"></a>
许多存储库系统都是开源的，因此您可以在公司中安装和运行它们。但这并不是您真正的业务范围，因此我们建议大多数人通过第三方托管。寻找以下功能：

- 良好的安全性和访问控制
- 直观的用户界面
- 也能够从命令行执行所有操作（因为您可能需要自动化它）
- 自动化构建和测试
- 对分支合并（有时称为拉取请求）的良好支持
- 问题管理（最好集成到提交和合并中，这样您就可以保留指标）
- 良好的报告（类似看板的待处理问题和任务的显示非常有用）
- 良好的团队沟通：电子邮件或其他变更通知、维基百科等

<a id="d24e7948"></a>
许多团队都配置了 VCS，以便推送到特定分支将自动构建系统、运行测试，如果成功，则将新代码部署到生产中。

<a id="d24e7954"></a>
听起来很可怕吗？当您意识到自己正在使用版本控制时就不会了。您随时可以将其回滚。

- 知道可以使用 VCS 回滚到之前的任何状态是一回事，但您真的能做到吗？您知道正确执行此操作的命令吗？现在就学习它们，而不是在灾难发生并且您面临压力时。
- 花一些时间考虑在发生灾难时恢复您自己的笔记本电脑环境。你需要什么来恢复？您需要的许多东西只是文本文件。如果它们不在 VCS（托管在您的笔记本电脑上）中，请找到添加它们的方法。然后考虑其他事情：安装的应用程序、系统配置等等。如何在文本文件中表达所有这些内容，以便也可以保存它们？

一旦你取得了一些进展，一个有趣的实验就是找到一台你不再使用的旧计算机，看看你的新系统是否可以用来设置它。
- 有意识地探索当前未使用的 VCS 和托管提供商的功能。如果您的团队没有使用功能分支，请尝试引入它们。与拉取/合并请求相同。持续集成。建设管道。甚至持续部署。还要研究团队沟通工具：维基、看板等。

您不必使用其中任何一个。但您确实需要知道它的作用，以便做出决定。
