## 主题 20. 调试

> 这是一件痛苦的事情，看看你自己的麻烦，并知道你自己，没有其他人已经成功了。
>
> 索福克勒斯、阿贾克斯

<a id="d24e8028"></a>
自 14 世纪起，“bug”一词就被用来描述“恐怖的物体”。COBOL 的发明者、海军少将格蕾丝·霍珀 (Grace Hopper) 博士被认为观察到了第一个计算机错误（字面意思是，一只飞蛾被困在早期计算机系统的继电器中）。当被要求解释为什么机器没有按预期运行时，一名技术人员报告说，“系统中存在一个错误”，并尽职尽责地将其（翅膀和所有内容）记录在日志中。

<a id="d24e8038"></a>
遗憾的是，我们的系统仍然存在错误，尽管不是飞行的错误。但十四世纪的含义——妖怪——现在可能比当时更适用。软件缺陷以多种方式表现出来，从误解需求到编码错误。不幸的是，现代计算机系统仍然仅限于执行您告诉它们执行的操作，而不一定执行您希望它们执行的操作。

<a id="d24e8046"></a>
没有人能编写出完美的软件，因此调试将占据您一天的大部分时间。让我们看看调试中涉及的一些问题以及寻找难以捉摸的错误的一些一般策略。

### 调试心理学

<a id="d24e8051"></a>
对于许多开发人员来说，调试是一个敏感且情绪化的话题。你可能会遇到否认、指责、蹩脚的借口，或者只是简单的冷漠，而不是把它当作一个需要解决的难题来攻击。

<a id="d24e8062"></a>
接受调试只是解决问题这一事实，并以此来攻击它。

<a id="d24e8076"></a>
发现别人的错误后，您可以花时间和精力将责任归咎于创造该错误的罪魁祸首。在一些工作场所，这是文化的一部分，并且可能是一种宣泄。然而，在技术领域，你要集中精力解决问题，而不是指责。

**提示 29：解决问题，而不是指责**

<a id="d24e8089"></a>
bug 是你的错还是别人的错并不重要。这仍然是你的问题。

### 调试心态

<a id="d24e8102"></a>
在开始调试之前，采用正确的心态很重要。你需要关闭每天用来保护你的自我的许多防御措施，消除你可能面临的任何项目压力，让自己感到舒服。最重要的是，请记住调试的第一条规则：

**提示 30：不要惊慌**

<a id="d24e8116"></a>
人们很容易陷入恐慌，尤其是当您面临最后期限，或者当您试图找到错误原因时，紧张的老板或客户会紧盯着您。但退后一步并真正思考可能导致您认为表明存在错误的症状的原因非常重要。

<a id="d24e8121"></a>
如果您在目睹错误或看到错误报告时的第一反应是“这不可能”，那么您显然是错误的。不要把任何一个神经元浪费在以“但这不可能发生”开始的思路上，因为很明显它可以而且已经发生了。

<a id="d24e8126"></a>
调试时谨防近视。抵制只修复您看到的症状的冲动：更可能的是，实际的错误可能与您所观察到的情况相去甚远，并且可能涉及许多其他相关的事情。始终尝试发现问题的根本原因，而不仅仅是问题的具体表现。

### 从哪里开始

<a id="d24e8131"></a>
在开始查看错误之前，请确保您正在编写干净构建的代码 - 没有警告。我们通常将编译器警告级别设置为尽可能高。浪费时间试图找到计算机可以为您找到的问题是没有意义的！我们需要集中精力解决手头更困难的问题。

<a id="d24e8145"></a>
当尝试解决任何问题时，您需要收集所有相关数据。不幸的是，错误报告并不是一门精确的科学。很容易被巧合所误导，而且你不能浪费时间去调试巧合。你首先需要准确地观察。

<a id="d24e8147"></a>
当错误报告来自第三方时，其准确性会进一步降低 - 您实际上可能需要观察报告错误的用户，以获得足够的详细信息。

<a id="stroke"></a>
安迪曾经开发过一个大型图形应用程序。临近发布时，测试人员报告说，每次他们使用特定画笔绘制笔画时，应用程序都会崩溃。负责的程序员辩称这没有任何问题；他曾尝试用它作画，效果很好。这样的对话一连好几天，脾气都急速上升。

<a id="d24e8168"></a>
最后，我们把他们聚在同一个房间里。测试人员选择画笔工具，从右上角到左下角画了一笔。该应用程序爆炸了。 “哦。”程序员小声说道，然后不好意思地承认，他只是从左下到右上进行了测试，并没有暴露出错误。

<a id="d24e8170"></a>
这个故事有两点：

<a id="d24e8174"></a>
<a id="d24e8177"></a>
- 您可能需要采访报告该错误的用户，以便收集比最初提供的更多数据。
- 人工测试（例如程序员从下到上的单笔划动）不足以对应用程序进行测试。您必须残酷地测试边界条件和实际的最终用户使用模式。您需要系统地执行此操作（请参阅<a href="../09%20Pragmatic%20Projects/51%20Pragmatic%20Starter%20Kit%20-%20starter_kit#testing">无情且持续的测试</a>）。

### 调试策略

<a id="d24e8201"></a>
一旦您认为您知道发生了什么，就该了解程序认为发生了什么。

#### 重现错误

<a id="d24e8216"></a>
不，我们的错误并没有真正繁殖（尽管其中一些可能已经足够老到可以合法地繁殖）。我们正在谈论一种不同类型的繁殖。

<a id="d24e8222"></a>
开始修复错误的最佳方法是使其可重现。毕竟，如果您无法重现它，您如何知道它是否已修复？

<a id="d24e8224"></a>
但我们想要的不仅仅是一个可以通过执行一系列长步骤来重现的错误；我们想要一个可以用单个命令重现的错误。如果您必须经过 15 个步骤才能发现错误，那么修复错误就会困难得多。

<a id="d24e8229"></a>
所以这是最重要的调试规则：

**提示 31：修复代码之前测试失败**

<a id="d24e8241"></a>
有时，通过强迫自己隔离显示错误的环境，您甚至可以深入了解如何修复它。编写测试的行为告知了解决方案。

<a id="readerror"></a>
### 异国他乡的编码员

<a id="d24e8246"></a>
所有这些关于隔离 bug 的讨论都很好，当面对 50,000 行代码和滴答作响的时钟时，一个糟糕的程序员该怎么办？

<a id="d24e8248"></a>
首先，看问题。这是崩溃吗？当我们教授涉及编程的课程时，有多少开发人员看到红色弹出的异常并立即跳到代码，这总是令人惊讶。

**提示 32：阅读该死的错误消息**

<a id="d24e8270"></a>
”努夫说。

#### 糟糕的结果

<a id="d24e8275"></a>
如果不是车祸怎么办？如果只是一个不好的结果怎么办？

<a id="d24e8277"></a>
使用调试器进入那里并使用失败的测试来触发问题。

<a id="d24e8279"></a>
首先，请确保您在调试器中也看到了不正确的值。我们都浪费了很多时间试图追踪错误，结果却发现这段特定的代码运行得很好。

<a id="d24e8281"></a>
有时问题很明显：利率是 4.5，应该是 0.045。更多时候，您必须更深入地了解该值最初为何是错误的。确保您知道如何在调用堆栈中上下移动并检查本地堆栈环境。

<a id="d24e8296"></a>
我们发现把笔和纸放在身边通常很有帮助，这样我们就可以记下笔记。尤其是我们经常会遇到一条线索，去追查，却发现没有成功。如果我们在开始追逐时没有记下我们所在的位置，我们可能会浪费很多时间回到那里。

<a id="d24e8302"></a>
有时您会看到似乎永远滚动的堆栈跟踪。在这种情况下，通常有一种比检查每个堆栈帧更快的方法来找到问题：使用二进制砍伐。但在我们讨论这个问题之前，让我们先看看另外两个常见的错误场景。

#### 对输入值的敏感性

<a id="d24e8317"></a>
你去过那里。您的程序可以很好地处理所有测试数据，并顺利地度过了生产的第一周。然后，当输入特定数据集时，它突然崩溃。

<a id="d24e8323"></a>
您可以尝试查看崩溃的位置并逆向工作。但有时从数据入手会更容易。获取数据集的副本并通过本地运行的应用程序副本提供数据，确保它仍然崩溃。然后对数据进行二进制切割，直到准确隔离哪些输入值导致崩溃。

#### 跨版本的回归

<a id="d24e8328"></a>
您在一个优秀的团队中，并将您的软件发布到生产环境中。在某个时候，一周前运行正常的代码中会出现一个错误。如果您能够确定引入它的具体更改，不是很好吗？你猜怎么着？二进制斩波时间。

### 二进制印章

<a id="d24e8347"></a>
每个计算机科学本科生都被迫编写二分法（有时称为二分搜索）。这个想法很简单。您正在查找排序数组中的特定值。您可以依次查看每个值，但最终您会平均查看大约一半的条目，直到找到所需的值，或者找到大于该值的值，这意味着该值不在数组中。

<a id="d24e8356"></a>
但使用分而治之的方法会更快。选择数组中间的一个值。如果这是您要寻找的人，请停下来。否则你可以将数组切成两半。如果您找到的值大于目标，那么您就知道它一定位于数组的前半部分，否则它位于数组的后半部分。在适当的子数组中重复该过程，很快您就会得到结果。 （正如我们在讨论 <a href="../07%20While%20Coding/39%20Algorithm%20Speed%20-%20algorithm_speed#big-o">大O符号</a> 时所看到的，线性搜索是 $ O(n) $，二元斩波是 $ O(log(n)) $）。

<a id="d24e8369"></a>
因此，对于任何规模相当大的问题，二进制斩波都要快得多。让我们看看如何将其应用到调试中。

<a id="d24e8371"></a>
当您面对大量堆栈跟踪并且试图准确找出哪个函数损坏了错误的值时，您可以通过选择中间某处的堆栈帧并查看错误是否在那里明显来进行切割。如果是，那么您就知道要关注之前的帧，否则问题出在之后的帧上。再砍一下。即使堆栈跟踪中有 64 个帧，这种方法最多也会在尝试六次后给出答案。

<a id="d24e8373"></a>
如果您发现某些数据集上出现错误，您也许可以做同样的事情。将数据集一分为二，看看通过应用程序提供其中一个数据集是否会出现问题。继续划分数据，直到获得显示问题的最小值集。

<a id="d24e8375"></a>
如果您的团队在一系列版本中引入了错误，您可以使用相同类型的技术。创建导致当前版本失败的测试。然后选择从现在到最后一个已知工作版本之间的中间版本。再次运行测试，并决定如何缩小搜索范围。能够做到这一点只是在项目中拥有良好版本控制的众多好处之一。事实上，许多版本控制系统会更进一步，并将该过程自动化，根据测试结果为您选择版本。

#### 记录和/或跟踪

<a id="d24e8404"></a>
<a id="FNPTR-25"></a>
调试器现在通常关注程序的状态。有时您需要更多 - 您需要随着时间的推移观察程序或数据结构的状态。查看堆栈跟踪只能告诉您如何直接到达这里。它通常无法告诉您在此调用链之前您正在做什么，尤其是在基于事件的系统中。<a href="22%20Engineering%20Daybooks%20-%20daybook#FOOTNOTE-25">[25]</a>

<a id="d24e8429"></a>
跟踪语句是打印到屏幕或文件的那些小诊断消息，其中包含诸如“到达此处”和“x 的值 = 2”之类的内容。与 IDE 风格的调试器相比，这是一种原始技术，但它在诊断调试器无法诊断的几类错误方面特别有效。在时间本身就是一个因素的任何系统中，跟踪都是非常宝贵的：并发进程、实时系统和基于事件的应用程序。

<a id="d24e8437"></a>
您可以使用跟踪语句深入了解代码。也就是说，您可以在下降调用树时添加跟踪语句。

<a id="d24e8439"></a>
跟踪消息应该采用常规、一致的格式，因为您可能希望自动解析它们。例如，如果您需要跟踪资源泄漏（例如不平衡的文件打开/关闭），您可以在日志文件中跟踪每次打开和每次关闭。通过使用文本处理工具或 shell 命令处理日志文件，您可以轻松识别发生违规打开的位置。

<a id="rubber-ducking"></a>
#### 橡皮鸭

<a id="d24e8457"></a>
<a id="FNPTR-26"></a>
查找问题原因的一个非常简单但特别有用的技术就是向其他人解释它。对方应该越过你的肩膀看着屏幕，并不断点头（就像一只橡皮鸭在浴缸里上下浮动）。他们不需要说一句话；一步步解释代码应该做什么的简单行为通常会导致问题跳出屏幕并自行宣布。<a href="22%20Engineering%20Daybooks%20-%20daybook#FOOTNOTE-26">[26]</a>

<a id="d24e8474"></a>
<a id="FNPTR-27"></a>
这听起来很简单，但是在向其他人解释问题时，您必须明确说明自己在查看代码时可能认为理所当然的事情。通过用语言表达其中一些假设，您可能会突然对问题有新的见解。如果你没有人，橡皮鸭、泰迪熊或盆栽植物也可以。<a href="22%20Engineering%20Daybooks%20-%20daybook#FOOTNOTE-27">[27]</a>

#### 消除过程

<a id="d24e8485"></a>
在大多数项目中，您正在调试的代码可能是您和项目团队中其他人编写的应用程序代码、第三方产品（数据库、连接、Web 框架、专用通信或算法等）和平台环境（操作系统、系统库和编译器）的混合体。

<a id="d24e8494"></a>
操作系统、编译器或第三方产品中可能存在错误，但这不应该是您的第一个想法。该错误更有可能存在于正在开发的应用程序代码中。通常，假设应用程序代码错误地调用库比假设库本身已损坏更有利可图。即使问题确实出在第三方身上，您仍然必须在提交错误报告之前消除代码。

<a id="d24e8499"></a>
我们参与的一个项目中，一位高级工程师确信 Unix 系统上的 select 系统调用被破坏了。再多的说服或逻辑也无法改变他的想法（盒子上的所有其他网络应用程序都运行良好这一事实无关紧要）。他花了几周的时间编写变通办法，但由于某种奇怪的原因，这些变通办法似乎并没有解决问题。当最终被迫坐下来阅读 select 的文档时，他发现了问题并在几分钟内纠正了它。现在，每当我们中的一个人开始将可能是我们自己的错误归咎于系统时，我们都会使用“选择已损坏”这句话作为温和的提醒。

**提示 33：“select”没有被破坏**

<a id="d24e8515"></a>
请记住，如果您看到蹄印，请想到马，而不是斑马。操作系统可能没有损坏。选择可能就可以了。

<a id="d24e8520"></a>
如果你“只改变了一件事”而系统停止工作，那么无论看起来多么牵强，那一件事很可能直接或间接负责。有时，改变的事情超出了你的控制范围：新版本的操作系统、编译器、数据库或其他第三方软件可能会对以前正确的代码造成严重破坏。新的错误可能会出现。你有解决方法的错误得到修复，破坏了解决方法。API的更改，功能更改；简而言之，这是一个全新的游戏，您必须在这些新条件下重新测试系统，因此在考虑升级时请密切关注时间表；您可能需要等到下一个版本之后。

### 惊喜元素

<a id="d24e8538"></a>
当您发现自己对错误感到惊讶时（甚至可能在我们听不到的情况下低声嘀咕“这不可能”），您必须重新评估您所珍视的事实。在那个折扣计算算法中——你知道那个算法是无懈可击的，不可能是这个错误的原因——你测试了所有的边界条件吗？您已经使用多年的另一段代码 — 它不可能仍然存在错误。可以吗？

<a id="d24e8552"></a>
当然可以。当出现问题时，您感到惊讶的程度与您对正在运行的代码的信任程度成正比。这就是为什么，当面对“令人惊讶的”失败时，您必须接受您的一个或多个假设是错误的。不要掩盖错误中涉及的例程或代码，因为您“知道”它有效。证明它。在这种情况下，用这些数据，用这些边界条件证明它。

**提示 34：不要假设——证明它**

<a id="d24e8575"></a>
当您遇到意外错误时，除了修复它之外，您还需要确定为什么没有及早发现此故障。考虑是否需要修改单元或其他测试，以便他们能够发现它。

<a id="d24e8577"></a>
另外，如果错误是由于在导致爆炸之前通过几个级别传播的不良数据造成的，请查看这些例程中更好的参数检查是否会更早地隔离它（分别参见有关早期崩溃以及断言 <a href="../04%20Pragmatic%20Paranoia/24%20Dead%20Programs%20Tell%20No%20Lies%20-%20crash_early#crash_discuss">这里</a> 和 <a href="../04%20Pragmatic%20Paranoia/25%20Assertive%20Programming%20-%20assertions#assertions">这里</a> 的讨论）。

<a id="d24e8592"></a>
当您这样做时，代码中是否还有其他地方可能容易受到同样的错误的影响？现在是找到并修复它们的时候了。确保无论发生什么，如果再次发生，您都会知道。

<a id="d24e8597"></a>
如果花了很长时间才修复这个错误，问问自己为什么。您可以做些什么来让下次更轻松地修复此错误吗？也许您可以构建更好的测试挂钩，或者编写日志文件分析器。

<a id="d24e8608"></a>
最后，如果错误是某人错误假设造成的，请与整个团队讨论该问题：如果一个人误解了，那么可能很多人都会误解。

<a id="d24e8611"></a>
完成这一切，希望下次你不会感到惊讶。
