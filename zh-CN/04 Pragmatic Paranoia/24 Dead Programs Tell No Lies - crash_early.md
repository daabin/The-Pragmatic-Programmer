<a id="crash_early"></a>
## 主题 24. 死掉的程序不会说谎

<a id="d24e9942"></a>
您是否注意到，有时在您自己意识到问题之前，其他人就可以发现您的情况不太好？和别人的代码是一样的。如果我们的某个程序开始出现问题，有时是库或框架例程首先捕获它。也许我们传入了一个 nil 值，或者一个空列表。也许该散列中缺少一个键，或者我们认为包含散列的值实际上包含一个列表。也许存在我们没有捕获的网络错误或文件系统错误，并且我们的数据为空或损坏。几百万条指令前的逻辑错误意味着 case 语句的选择器不再是预期的 1、2 或 3。我们会意外地遇到默认 case。这也是每个 case/switch 语句都需要有一个 default 子句的原因之一：我们想知道“不可能”何时发生。

<a id="d24e9962"></a>
人们很容易陷入“这不可能发生”的心态。我们大多数人编写的代码都没有检查文件是否成功关闭，或者跟踪语句是否按我们的预期编写。在所有条件相同的情况下，我们很可能不需要这样做——相关代码在任何正常情况下都不会失败。但我们正在防御性地编码。我们确保数据就是我们认为的那样，生产中的代码就是我们认为的代码。我们正在检查是否实际加载了正确版本的依赖项。

<a id="d24e9968"></a>
所有错误都会为您提供信息。您可以说服自己该错误不会发生，并选择忽略它。相反，务实的程序员告诉自己，如果出现错误，则表明发生了非常非常糟糕的事情。不要忘记阅读该死的错误消息（请参阅[*异国他乡的编码员*](<../03 Basic Tools/20 Debugging - debug.md#readerror>)）。

### 捕获和释放是为了鱼

<a id="d24e9989"></a>
一些开发人员认为捕获或拯救所有异常并在编写某种消息后重新引发它们是一种很好的风格。他们的代码充满了这样的东西（其中一个简单的 raise 语句重新引发当前异常）：

```
try do
   add_score_to_board(score);
rescue InvalidScore
   Logger.error("Can't add invalid score. Exiting");
   raise
rescue BoardServerDown
   Logger.error("Can't add score: board is down. Exiting");
   raise
rescue StaleTransaction
   Logger.error("Can't add score: stale transaction. Exiting");
   raise
end
```

<a id="d24e10057"></a>
务实的程序员会这样写：

```
add_score_to_board(score);
```

<a id="d24e10063"></a>
我们更喜欢它有两个原因。首先，应用程序代码不会因错误处理而黯然失色。其次，也许更重要的是，代码的耦合性较低。在详细示例中，我们必须列出 add\_score\_to\_board 方法可能引发的每个异常。如果该方法的编写者添加了另一个异常，那么我们的代码就已经过时了。在更实用的第二个版本中，新的异常会自动传播。

**提示 38：尽早崩溃**

<a id="crash_discuss"></a>
### 崩溃，不要垃圾

<a id="d24e10088"></a>
尽快发现问题的好处之一是可以更早地崩溃，而崩溃通常是您能做的最好的事情。另一种选择可能是继续，将损坏的数据写入某些重要数据库或命令洗衣机进入第二十个连续旋转周期。

<a id="d24e10090"></a>
Erlang 和 Elixir 语言都遵循这一理念。 Joe Armstrong，Erlang 的发明者和 [*Erlang 编程：并发世界的软件* [Arm07]](<../A2 Exercise Answers/README.md#d6040e93>) 的作者，经常被引用说：“防御性编程是浪费时间。让它崩溃吧！”在这些环境中，程序被设计成会失败，但这种失败是由主管来管理的。主管负责运行代码，并知道在代码失败时该怎么做，这可能包括在代码失败后进行清理、重新启动等等。当主管本身失败时会发生什么？它自己的主管管理该事件，从而形成由主管树组成的设计。该技术非常有效，有助于解释这些语言在高可用性、容错系统中的使用。

<a id="d24e10122"></a>
在其他环境中，简单地退出正在运行的程序可能是不合适的。您可能已经声明了可能不会被释放的资源，或者您可能需要编写日志消息、整理打开的事务或与其他进程交互。

<a id="d24e10124"></a>
然而，基本原理保持不变——当你的代码发现一些原本不可能的事情发生了，你的程序就不再可行了。从此时起它所做的任何事情都会变得可疑，因此请尽快终止它。

<a id="d24e10126"></a>
一个死程序通常比一个瘫痪的程序造成的损害要小得多。
