## 主题 25. 自信式编程

> 自责是一种奢侈。当我们责备自己时，我们觉得没有人有权责备我们。
>
> 奥斯卡·王尔德《道林·格雷的画像》

<a id="d24e10166"></a>
似乎有一个咒语是每个程序员在其职业生涯的早期都必须记住的。这是计算的基本原则，是我们学习将其应用于需求、设计、代码、注释以及我们所做的一切的核心信念。它去

<a id="d24e10198"></a>
> 这永远不会发生……

<a id="d24e10200"></a>
“这个应用程序永远不会在国外使用，那为什么要国际化呢？” “计数不能为负数。” “记录不能失败。”

<a id="d24e10205"></a>
我们不要练习这种自欺欺人的做法，尤其是在编码时。

**技巧 39：使用断言来防止不可能的事情发生**

<a id="d24e10215"></a>
<a id="FNPTR-31"></a>
每当您发现自己在想“但这当然永远不会发生”时，请添加代码来检查它。最简单的方法是使用断言。在许多语言实现中，您会发现某种形式的断言来检查布尔条件。[[31]](<27 Don't Outrun Your Headlights - headlights.md#FOOTNOTE-31>) 这些检查非常宝贵。如果参数或结果不应该为空，则显式检查它：

```
assert (result != null);
```

<a id="d24e10270"></a>
在 Java 实现中，您可以（并且应该）添加描述性字符串：

```
assert result != null  result.size() > 0 : "Empty result from XYZ";
```

<a id="d24e10287"></a>
断言对于算法操作的检查也是有用的。也许您已经编写了一个聪明的排序算法，名为 my\_sort。检查它是否有效：

```
books = my_sort(find("scifi"))
assert(is_sorted?(books))
```

<a id="d24e10305"></a>
不要使用断言来代替真正的错误处理。断言检查不应该发生的事情：您不想编写如下代码：

```
puts("Enter 'Y' or 'N': ")
ans = gets[0] # Grab first character of response
assert((ch == 'Y') || (ch == 'N'))    # Very bad idea!
```

<a id="d24e10338"></a>
正因为大多数断言实现都会在断言失败时终止进程，所以您编写的版本没有理由应该终止。如果您需要释放资源，请捕获断言的异常或捕获退出，然后运行您自己的错误处理程序。只要确保您在这几毫秒内执行的代码不依赖于首先触发断言失败的信息即可。

### 断言和副作用

<a id="d24e10346"></a>
当我们添加的用于检测错误的代码实际上最终创建了新的错误时，这是​​令人尴尬的。如果评估条件有副作用，则断言可能会发生这种情况。例如，编写如下代码是一个坏主意

```
while (iter.hasMoreElements()) {
  assert(iter.nextElement() != null);
  Object obj = iter.nextElement();
  // ....
}
```

<a id="d24e10388"></a>
断言中的 .nextElement() 调用具有将迭代器移过正在获取的元素的副作用，因此循环将仅处理集合中的一半元素。最好写成

```
while (iter.hasMoreElements()) {
  Object obj = iter.nextElement();
  assert(obj != null);
  // ....
}
```

<a id="d24e10421"></a>
<a id="FNPTR-32"></a>
这个问题是一种 Heisenbug[[32]](<27 Don't Outrun Your Headlights - headlights.md#FOOTNOTE-32>) — 调试会更改正在调试的系统的行为。

<a id="d24e10435"></a>
（我们还相信，如今，当大多数语言都对集合上的迭代函数有很好的支持时，这种显式循环是不必要的，也是不好的形式。）

### 启用断言

<a id="d24e10442"></a>
关于断言存在一个常见的误解。事情是这样的：

<a id="d24e10449"></a>
> 断言会增加代码的一些开销。因为他们会检查东西
> 这永远不会发生，它们只会被错误触发
> 代码。一旦代码经过测试并交付，它们就不再是
> 需要，并且应该关闭以使代码运行得更快。
> 断言是一种调试工具。

<a id="d24e10451"></a>
这里有两个明显错误的假设。首先，他们假设测试发现了所有错误。实际上，对于任何复杂的程序，您都不太可能测试代码将要经历的排列的一小部分。其次，乐观主义者忘记了你的程序运行在一个危险的世界中。在测试过程中，老鼠可能不会咬断通信电缆，玩游戏的人可能不会耗尽内存，日志文件也不会填满存储分区。当您的程序在生产环境中运行时，可能会发生这些情况。您的第一道防线是检查任何可能的错误，第二道防线是使用断言来尝试检测您错过的错误。

<a id="d24e10462"></a>
当您将程序交付生产时关闭断言就像跨越没有网的高空钢丝，因为您曾经在实践中跨越过它。它具有巨大的价值，但很难获得人寿保险。

<a id="d24e10465"></a>
即使您确实存在性能问题，也只关闭那些真正影响您的断言。上面的排序示例可能是您的应用程序的关键部分，并且可能需要快速。添加检查意味着再次传递数据，这可能是不可接受的。将该特定检查设为可选，但保留其余部分。

<a id="d24e10510"></a>
<a id="d24e10532"></a>
<a id="d24e10534"></a>
在生产中使用断言，赚大钱

安迪的一位前邻居领导了一家制造网络设备的小型初创公司。他们成功的秘诀之一是决定在生产版本中保留断言。这些断言经过精心设计，可以报告导致失败的所有相关数据，并通过漂亮的 UI 呈现给最终用户。这种来自真实用户在实际情况下的反馈水平，使开发人员能够堵塞漏洞并修复这些模糊的、难以重现的错误，从而产生非常稳定、防弹的软件。

这家不知名的小公司拥有如此扎实的产品，很快就被以数亿美元收购。

只是说说而已。
