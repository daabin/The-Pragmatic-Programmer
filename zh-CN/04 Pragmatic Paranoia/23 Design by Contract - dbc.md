## 主题 23. 契约式设计

> 没有什么比常识和诚实的待人接物更让人们感到惊讶的了。
>
> 拉尔夫·沃尔多·爱默生，散文

<a id="d24e9081"></a>
处理计算机系统很困难。与人打交道更是难上加难。但作为一个物种，我们有更长的时间来解决人类互动的问题。我们在过去几千年提出的一些解决方案也可以应用于编写软件。确保公平交易的最佳解决方案之一是合同。

<a id="d24e9095"></a>
合同定义了您以及另一方的权利和责任。此外，双方还就任何一方不遵守合同的后果达成了协议。

<a id="d24e9097"></a>
也许您有一份雇佣合同，其中规定了您的工作时间以及您必须遵守的行为规则。作为回报，公司向您支付薪水和其他福利。各方履行其义务，各方受益。

<a id="d24e9099"></a>
这是一个在世界各地正式和非正式地使用的想法来帮助人类互动。我们可以使用相同的概念来帮助软件模块交互吗？答案是“是的”。

### DBC

<a id="d24e9106"></a>
<a id="FNPTR-30"></a>
Bertrand Meyer ([*面向对象的软件构建* [Mey97]](<../A2 Exercise Answers/README.md#d6040e783>)) 为 Eiffel 语言开发了契约设计的概念。[[30]](<27 Don't Outrun Your Headlights - headlights.md#FOOTNOTE-30>) 这是一种简单而强大的技术，专注于记录（并同意）软件模块的权利和责任，以确保程序的正确性。什么是正确的程序？一个所做的事情不比它声称的多也不少。记录和验证该声明是契约设计（简称 DBC）的核心。

<a id="d24e9130"></a>
软件系统中的每个函数和方法都会做一些事情。在开始某件事之前，该函数可能会对世界的状态有一些期望，并且它可能能够在结束时对世界的状态做出声明。迈耶将这些期望和主张描述如下：

<a id="d24e9151"></a>
<a id="d24e9167"></a>
<a id="d24e9187"></a>
先决条件：为了调用例程必须满足什么条件；例程的要求。当例程的先决条件被违反时，永远不应该调用例程。调用者有责任传递良好的数据（参见框[这里](#sb-preconditions)）。

后置条件：例程保证做什么；例行公事完成后的世界状态。该例程具有后置条件的事实意味着它将得出结论：不允许无限循环。

类不变量：类确保从调用者的角度来看此条件始终为真。在例程的内部处理期间，不变量可能不成立，但是当例程退出并且控制权返回到调用者时，不变量必须为真。 （请注意，类不能向参与不变量的任何数据成员提供不受限制的写入访问权限。）

<a id="d24e9203"></a>
因此，例程和任何潜在调用者之间的契约可以读作

<a id="d24e9206"></a>
> 如果调用者满足例程的所有先决条件，
> 例程应保证所有后置条件和不变量
> 当它完成时将是真实的。

<a id="d24e9208"></a>
如果任何一方未能遵守合同条款，则将调用补救措施（之前已同意）——可能会引发例外，或者计划终止。无论发生什么，毫无疑问，未能履行合同就是一个错误。这不是应该发生的事情，这就是为什么不应该使用前提条件来执行诸如用户输入验证之类的事情。

<a id="d24e9210"></a>
有些语言比其他语言对这些概念有更好的支持。例如，Clojure 支持前置条件和后置条件以及规范提供的更全面的检测。以下是使用简单前置条件和后置条件进行存款的银行功能示例：

```
(defn accept-deposit [account-id amount]
   { :pre [  (> amount 0.00)
             (account-open? account-id) ]
     :post [ (contains? (account-transactions account-id) %) ] }
   "Accept a deposit and return the new transaction id"
   ;; Some other processing goes here...
   ;; Return the newly created transaction:
   (create-transaction account-id :deposit amount))
```

<a id="d24e9265"></a>
接受存款功能有两个前提条件。第一个是金额大于零，第二个是帐户已打开且有效，由某个名为 account-open? 的函数确定。还有一个后置条件：该函数保证可以在该账户的交易中找到新交易（该函数的返回值，此处用‘%’表示）。

<a id="d24e9273"></a>
如果您使用正数存款金额和有效帐户调用 Accept-Deposit，它将继续创建适当类型的交易并执行它所做的任何其他处理。但是，如果程序中存在错误并且您以某种方式传递了负数的存款，您将收到运行时异常：

```
Exception in thread "main"...
Caused by: java.lang.AssertionError: Assert failed: (> amount 0.0)
```

<a id="d24e9284"></a>
同样，该功能要求指定账户已开立且有效。如果不是，您将看到该异常：

```
Exception in thread "main"...
Caused by: java.lang.AssertionError: Assert failed: (account-open? account-id)
```

<a id="d24e9292"></a>
其他语言的一些功能虽然不是 DBC 特有的，但仍然可以发挥良好的效果。例如，Elixir 使用保护子句来针对多个可用主体分派函数调用：

```
defmodule Deposits do
  def accept_deposit(account_id, amount) when (amount > 100000) do
    # Call the manager!
  end
  def accept_deposit(account_id, amount) when (amount > 10000) do
    # Extra Federal requirements for reporting
    # Some processing...
  end
  def accept_deposit(account_id, amount) when (amount > 0) do
    # Some processing...
  end
end
```

<a id="d24e9376"></a>
在这种情况下，以足够大的金额调用accept_deposit可能会触发额外的步骤和处理。但是，尝试使用小于或等于零的金额来调用它，您会收到一个异常，通知您不能：

```
** (FunctionClauseError) no function clause matching in Deposits.accept_deposit/2
```

<a id="d24e9385"></a>
这是比简单地检查您的输入更好的方法；在这种情况下，如果您的参数超出范围，您将无法调用此函数。

**技巧 37：用契约进行设计**

<a id="d24e9396"></a>
在主题 10 [*正交性*](<../02 Pragmatic Approach/10 Orthogonality - orthogonality.md#orthogonality>) 中，我们建议编写“害羞”代码。这里，重点是“惰性”代码：在开始之前严格遵守您将接受的内容，并承诺尽可能少的回报。请记住，如果您的合同表明您将接受任何东西并向世界做出回报，那么您就需要编写大量代码！

<a id="d24e9400"></a>
在任何编程语言中，无论是函数式、面向对象还是过程式，DBC 都会迫使您思考。

DBC 和测试驱动开发

在开发人员实践单元测试、测试驱动开发 (TDD)、基于属性的测试或防御性编程的世界中，是否需要按合同设计？

简短的回答是“是”。

DBC 和测试是解决更广泛的程序正确性主题的不同方法。它们都有价值，并且在不同情况下都有用途。与特定测试方法相比，DBC 具有多种优势：

- DBC 不需要任何设置或模拟
- DBC 定义了所有情况下成功或失败的参数，而测试一次只能针对一种特定情况
- TDD 和其他测试仅在构建周期内的“测试时间”进行。但 DBC 和断言是永恒的：在设计、开发、部署和维护期间
- TDD 并不专注于检查被测代码中的内部不变量，它更采用黑盒风格来检查公共接口
- DBC 比防御性编程更有效（并且DRY-er），在防御性编程中，每个人都必须验证数据，以防其他人验证数据。

TDD 是一项伟大的技术，但与许多技术一样，它可能会邀请您专注于“快乐之路”，而不是充满不良数据、不良参与者、不良版本和不良规范的现实世界。

#### 类不变量和函数式语言

<a id="d24e9484"></a>
这是一个命名的事情。 Eiffel 是一种面向对象的语言，因此 Meyer 将这个想法命名为“类不变式”。但实际上，它比这更普遍。这个想法真正指的是状态。在面向对象的语言中，状态与类的实例相关联。但其他语言也有状态。

<a id="d24e9509"></a>
在函数式语言中，您通常将状态传递给函数并接收更新后的状态。不变量的概念在这些情况下同样有用。

### 实施DBC

<a id="d24e9535"></a>
在编写代码之前，简单地枚举输入域范围是什么、边界条件是什么以及例程承诺提供的内容（或者更重要的是，它不承诺提供的内容）是编写更好的软件的巨大飞跃。如果不说明这些事情，您就会巧合地回到编程（请参阅讨论[这里](<../07 While Coding/38 Programming by Coincidence - coincidence.md#coincidence>)），这是许多项目开始、结束和失败的地方。

<a id="d24e9554"></a>
对于代码中不支持 DBC 的语言，这可能是您所能做到的最远的事情，而且这还不算太糟糕。毕竟，DBC 是一种设计技术。即使没有自动检查，您也可以将合约作为注释放在代码中或放在单元测试中，仍然可以获得非常实际的好处。

#### 断言

<a id="d24e9576"></a>
虽然记录这些假设是一个很好的开始，但通过让编译器为您检查合同，您可以获得更大的好处。您可以通过使用断言在某些语言中部分模拟这一点：逻辑条件的运行时检查（请参阅主题 25，[*断言编程*](<25 Assertive Programming - assertions.md#assertions>)）。为什么只是部分？难道不能使用断言来完成 DBC 能做的所有事情吗？

<a id="d24e9597"></a>
不幸的是，答案是否定的。首先，在面向对象的语言中可能不支持沿着继承层次结构传播断言。这意味着，如果您重写具有协定的基类方法，则将无法正确调用实现该协定的断言（除非您在新代码中手动复制它们）。您必须记住在退出每个方法之前手动调用类不变量（以及所有基类不变量）。基本问题是合同不会自动执行。

<a id="d24e9613"></a>
在其他环境中，从 DBC 样式断言生成的异常可能会在代码中全局关闭或忽略。

<a id="d24e9619"></a>
另外，没有“旧”值的内置概念；也就是说，它们存在于方法入口处的值。如果您使用断言来执行契约，则必须向前置条件添加代码以保存您想要在后置条件中使用的任何信息（如果语言允许的话）。在 DBC 诞生的 Eiffel 语言中，您可以只使用旧表达式。

<a id="d24e9639"></a>
最后，传统的运行时系统和库并不是为支持合约而设计的，因此这些调用不会被检查。这是一个巨大的损失，因为大多数问题通常是在代码与其使用的库之间的边界处检测到的（有关更详细的讨论，请参阅主题 24，[*死程序不会说谎*](<24 Dead Programs Tell No Lies - crash_early.md#crash_early>)）。

<a id="sb-preconditions"></a>
<a id="d24e9655"></a>
<a id="d24e9673"></a>
<a id="d24e9694"></a>
谁负责？

谁负责检查前提条件、调用者或被调用的例程？当作为语言的一部分实现时，答案不是：在调用者调用例程之后但在进入例程本身之前，在幕后测试前提条件。因此，如果需要对参数进行任何显式检查，则必须由调用者执行，因为例程本身永远不会看到违反其前提条件的参数。 （对于没有内置支持的语言，您需要将被调用的例程与检查这些断言的前导码和/或后导码括起来。）

考虑一个从控制台读取数字、计算其平方根（通过调用 sqrt）并打印结果的程序。 sqrt 函数有一个前提条件——它的参数不能为负数。如果用户在控制台输入负数，则由调用代码来确保它永远不会传递给 sqrt。该调用代码有很多选项：它可以终止，可以发出警告并读取另一个数字，或者可以使该数字为正数并将 i 附加到 sqrt 返回的结果中。无论选择什么，这绝对不是 sqrt 的问题。

通过在 sqrt 例程的前提条件中表达平方根函数的域，您可以将正确性的负担转移给调用者（它所属的地方）。然后，您可以安全地设计 sqrt 例程，因为您知道其输入将在范围内。

### DBC 和早期崩溃

<a id="d24e9707"></a>
DBC 非常符合我们提前崩溃的概念（参见主题 24，[*死程序不会说谎*](<24 Dead Programs Tell No Lies - crash_early.md#crash_early>)）。通过使用断言或 DBC 机制来验证前置条件、后置条件和不变量，您可以尽早崩溃并报告有关问题的更准确的信息。

<a id="d24e9728"></a>
例如，假设您有一个计算平方根的方法。它需要一个 DBC 前提条件，将域限制为正数。在支持 DBC 的语言中，如果向 sqrt 传递负参数，您将收到一条信息性错误（例如 sqrt\_arg\_must\_be\_positive）以及堆栈跟踪。

<a id="d24e9736"></a>
这比 Java、C 和 C++ 等其他语言中的替代方案更好，在其他语言中，将负数传递给 sqrt 返回特殊值 NaN（非数字）。在程序中的稍后一段时间，您可能会尝试对 NaN 进行一些数学计算，并得到令人惊讶的结果。

<a id="d24e9747"></a>
通过在问题发生的地方尽早崩溃，可以更容易地发现和诊断问题。

### 语义不变量

<a id="d24e9752"></a>
您可以使用语义不变量来表达不可违反的要求，这是一种“哲学契约”。

<a id="d24e9761"></a>
我们曾经写过一个借记卡交易开关。一个主要要求是借记卡用户不得将同一交易两次应用于其帐户。换句话说，无论发生哪种故障模式，错误都应该是在不处理事务方面，而不是在处理重复事务方面。

<a id="d24e9766"></a>
事实证明，这个直接从需求驱动的简单法则对于理清复杂的错误恢复场景非常有帮助，并指导了许多领域的详细设计和实现。

<a id="d24e9768"></a>
请务必不要将固定的、不违反法律的要求与那些可能会随着新的管理制度而改变的政策相混淆。这就是为什么我们使用术语“语义不变量”——它必须是事物含义的核心，并且不受策略的影响（这就是更动态的业务规则的用途）。

<a id="d24e9790"></a>
当您发现符合条件的需求时，请确保它成为您正在生成的任何文档中众所周知的部分 - 无论它是需求文档中一式三份签署的项目符号列表，还是只是每个人都能看到的公共白板上的大注释。尝试清楚、明确地陈述它。例如，在借记卡示例中，我们可以写

<a id="d24e9797"></a>
> 犯了有利于消费者的错误。

<a id="d24e9799"></a>
这是一个清晰、简洁、明确的声明，适用于系统的许多不同领域。它是我们与所有系统用户的契约，是我们行为的保证。

### 动态合约和代理

<a id="d24e9805"></a>
到目前为止，我们一直将合约视为固定的、不可变的规范。但在自治代理的情况下，情况不一定如此。根据“自主”的定义，代理可以自由拒绝他们不想满足的请求。他们可以自由地重新谈判合同——“我不能提供这个，但如果你给我这个，那么我可能会提供别的东西。”

<a id="d24e9822"></a>
当然，任何依赖代理技术的系统都严重依赖合同安排——即使它们是动态生成的。

<a id="d24e9827"></a>
想象一下：如果有足够的组件和代理可以在彼此之间协商自己的合同以实现目标，我们可以通过让软件为我们解决软件生产力危机来解决它。

<a id="d24e9829"></a>
但如果我们不能手动使用合约，我们就无法自动使用它们。所以下次你设计一个软件时，也要设计它的合约。

<a id="d24e9931"></a>
0、5、10、15、…、100 系列中有多少个数字？
