## 主题 7. 沟通！

> 我相信，被人审视总比被忽视要好。
>
> 梅·韦斯特，九十年代美女，1934 年

<a id="d24e2054"></a>
也许我们可以向韦斯特女士学习。这不仅仅是你拥有什么，还包括你如何包装它。除非你能与其他人沟通，否则即使拥有最好的想法、最好的代码或最务实的思维，最终也是徒劳的。没有有效的沟通，再好的创意也是孤儿。

<a id="d24e2060"></a>
作为开发人员，我们必须在多个层面上进行沟通。我们花几个小时开会、倾听和交谈。我们与最终用户合作，试图了解他们的需求。我们编写代码，将我们的意图传达给机器，并为后代开发人员记录我们的想法。我们撰写提案和备忘录，请求和证明资源的合理性，报告我们的状况，并提出新方法的建议。我们每天在团队中倡导我们的想法、修改现有实践并提出新的实践。我们一天的大部分时间都花在沟通上，所以我们需要做好沟通。

<a id="d24e2062"></a>
将英语（或任何您的母语）视为另一种编程语言。像编写代码一样编写自然语言：遵循 DRY 原则、ETC、自动化等。 （我们将在下一章讨论DRY和ETC设计原则。）

**提示 11：英语只是另一种编程语言**

<a id="d24e2097"></a>
我们整理了一系列我们认为有用的其他想法。

### 了解你的受众

<a id="d24e2102"></a>
<a id="FNPTR-12"></a>
只有当你传达了你想要传达的意思时，你才算在沟通——仅仅说话是不够的。为此，您需要了解受众的需求、兴趣和能力。我们都曾参加过这样的会议：一位开发极客盯着营销副总裁的眼睛，对某些神秘技术的优点进行长篇独白。这不是交流：这只是说话，而且很烦人。[[12]](#FOOTNOTE-12)

<a id="d24e2127"></a>
假设您想要更改远程监控系统以使用第三方消息代理来传播状态通知。您可以根据您的受众以多种不同的方式展示此更新。最终用户将会意识到他们的系统现在可以与使用代理的其他服务进行互操作。您的营销部门将能够利用这一事实来促进销售。开发和运营经理会很高兴，因为系统这部分的维护和维护现在是其他人的问题了。最后，开发人员可能会喜欢获得新的 API 的体验，甚至可能能够找到消息代理的新用途。通过向每个小组进行适当的宣传，您将使他们都对您的项目感到兴奋。

<a id="d24e2129"></a>
与所有形式的沟通一样，这里的技巧是收集反馈。不要只是等待问题：主动提出问题。看看肢体语言和面部表情。神经语言编程的前提之一是“你沟通的意义就是你得到的回应”。在沟通时不断提高您对受众的了解。

### 知道你想说什么

<a id="d24e2144"></a>
在商业中使用的更正式的沟通方式中，最困难的部分可能是准确地弄清楚你想说的是什么。小说作家经常在开始之前详细地规划他们的书，但是编写技术文档的人通常很乐意坐在键盘前输入：

> 一、简介

<a id="d24e2155"></a>
然后开始输入他们接下来想到的任何内容。

<a id="d24e2157"></a>
计划好你想说的话。写一个大纲。然后问自己：“这是否能以适合观众的方式向他们传达我想要表达的内容？”精炼它直到它完成。

<a id="d24e2159"></a>
这种方法不仅仅适用于文档。当您面临重要会议或与主要客户交谈时，记下您想要传达的想法，并计划一些传达这些想法的策略。

<a id="d24e2165"></a>
现在您知道了观众想要什么，让我们来实现它。

### 选择你的时刻

<a id="d24e2170"></a>
现在是周五下午六点，审计员已经上班一周了。你老板最小的孩子住院了，外面下着倾盆大雨，回家的路上肯定会是一场噩梦。现在可能不是要求她升级笔记本电脑内存的好时机。

<a id="d24e2176"></a>
作为了解受众需要听到的内容的一部分，您需要弄清楚他们的优先事项是什么。遇到一位刚刚因为丢失一些源代码而被老板刁难的经理，您将有一个更容易接受您关于源代码存储库的想法的听众。让你所说的话与时间和内容相关。有时只需要一个简单的问题：“现在是谈论……的好时机吗？”

### 选择风格

<a id="d24e2181"></a>
调整您的演讲风格以适合您的听众。有些人希望得到正式的“事实真相”简报。另一些人则喜欢在开始正题之前进行长时间、广泛的交谈。他们在该领域的技能水平和经验如何？他们是专家吗？新手？他们需要指导还是只是快速的长篇大论？如果有疑问，请询问。

<a id="d24e2187"></a>
但请记住，您是沟通交易的一半。如果有人说他们需要一个段落来描述某件事，而你在不到几页的时间内看不到任何方法，请告诉他们。请记住，这种反馈也是一种沟通形式。

### 让它看起来不错

<a id="d24e2193"></a>
你的想法很重要。他们应该有一个漂亮的工具来将他们传达给你的观众。

<a id="d24e2199"></a>
太多的开发人员（及其经理）在生成书面文档时只关注内容。我们认为这是一个错误。任何厨师（或美食频道的观察者）都会告诉你，你可以在厨房里辛苦工作几个小时，结果却因为糟糕的展示而毁掉你的努力。

<a id="d24e2201"></a>
如今，没有任何借口可以制作出外观不佳的印刷文档。无论您是使用 Markdown 还是使用文字处理器进行写作，现代软件都可以产生令人惊叹的输出。您只需要学习一些基本命令。如果您使用文字处理程序，请使用其样式表以保持一致性。 （您的公司可能已经定义了可以使用的样式表。）了解如何设置页眉和页脚。查看包中包含的示例文档，以获得有关样式和布局的想法。首先自动检查拼写，然后手动检查拼写。锥子之后，检查员可以将它们打结成双桅船。

### 让你的观众参与进来

<a id="d24e2226"></a>
我们经常发现我们生成的文件最终不如我们生成这些文件所经历的过程重要。如果可能的话，让您的读者参与文档的早期草稿。获取他们的反馈，并听取他们的意见。您将建立良好的工作关系，并且在此过程中您可能会生成更好的文档。

### 做一个倾听者

<a id="d24e2255"></a>
如果你希望人们倾听你的意见，你必须使用一种技巧：倾听他们的意见。即使这是一个你掌握了所有信息的情况，即使这是一个你站在20个人面前的正式会议——如果你不听他们的，他们也不会听你的。

<a id="d24e2272"></a>
通过提问鼓励人们交谈，或要求他们用自己的话重述讨论内容。将会议变成对话，您将更有效地表达自己的观点。谁知道呢，你甚至可能会学到一些东西。

### 回到人身边

<a id="d24e2281"></a>
如果你问某人问题，如果他们不回答，你会觉得他们很不礼貌。但是，当人们向您发送电子邮件或备忘录询问信息或要求采取某些行动时，您是否经常无法回复他们？在忙碌的日常生活中，很容易忘记。始终回复电子邮件和语音邮件，即使回复只是“我稍后再回复您”。让人们了解情况可以让他们更加宽容偶尔的失误，并让他们觉得您没有忘记他们。

**提示 12：重要的是你所说的内容和你所说的方式**

<a id="d24e2289"></a>
除非你在真空中工作，否则你需要能够沟通。沟通越有效，你的影响力就越大。

### 文档

<a id="d24e2294"></a>
最后，还有通过文档进行沟通的问题。通常，开发人员不会过多考虑文档。充其量这只是一种不幸的必需品；在最坏的情况下，它被视为低优先级任务，希望管理层在项目结束时忘记它。

<a id="d24e2315"></a>
务实的程序员将文档视为整个开发过程的一个组成部分。通过不重复工作或浪费时间，以及将文档放在手边（在代码本身中），可以使编写文档变得更加容易。事实上，我们希望将所有务实原则应用于文档和代码。

**提示 13：构建文档，而不是将其固定**

<a id="d24e2330"></a>
从源代码中的注释生成美观的文档很容易，我们建议向模块和导出的函数添加注释，以便其他开发人员在使用它时获得帮助。

<a id="d24e2336"></a>
然而，这并不意味着我们同意人们所说的每个函数、数据结构、类型声明等都需要自己的注释。这种机械的注释编写实际上使维护代码变得更加困难：现在，当您进行更改时，有两件事需要更新。因此，将您的非 API 评论限制为讨论为什么要做某事、其目的和目标。代码已经显示了它是如何完成的，因此对此进行评论是多余的，并且违反了 DRY 原则。

<a id="d24e2356"></a>
注释源代码为您提供了绝佳的机会来记录项目中那些难以捉摸的部分，这些部分在其他任何地方都无法记录：工程权衡、为什么做出决策、放弃了哪些其他替代方案等等。

### 概括

- 知道你想说什么。
- 了解你的听众。
- 选择你的时刻。
- 选择一种风格。
- 让它看起来不错。
- 让你的观众参与进来。
- 做一个倾听者。
- 回到人们身边。
- 将代码和文档放在一起。

在线交流

我们所说的有关书面沟通的所有内容同样适用于电子邮件、社交媒体帖子、博客等。特别是电子邮件已经发展到成为企业通信的支柱。它被用来讨论合同、解决争端以及作为法庭上的证据。但出于某种原因，那些永远不会发送破烂纸质文档的人却很乐意在世界各地发送看起来令人讨厌、语无伦次的电子邮件。

我们的建议很简单：

- 在点击发送之前进行校对。
- 检查您的拼写并查找任何意外的自动更正错误。
- 保持格式简单明了。
- 尽量减少引用。没有人喜欢收到自己发来的 100 行附加“我同意”的电子邮件。
- 如果您引用其他人的电子邮件，请务必注明来源，并内嵌引用（而不是作为附件）。在社交媒体平台上引用时也是如此。
- 不要发火或表现得像个巨魔，除非你想让它稍后回来困扰你。如果你不会当面说，就不要在网上说。
- 发送前请检查您的收件人列表。通过部门电子邮件批评老板却没有意识到老板在抄送名单上，这已经成为一种陈词滥调。更好的是，不要通过电子邮件批评老板。

正如无数大公司和政客发现的那样，电子邮件和社交媒体帖子是永恒的。尝试像对待任何书面备忘录或报告一样关注和关心电子邮件。
