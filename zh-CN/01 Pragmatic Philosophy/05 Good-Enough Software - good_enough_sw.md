## 主题 5. 足够好的软件

> 努力做到更好，我们常常会破坏好的东西。
>
> 莎士比亚、李尔王 1.4

<a id="d24e1404"></a>
有一个老笑话，说的是一家公司向一家日本制造商订购了 100,000 个 IC。规格的一部分是缺陷率：万分之一芯片。几周后，订单到达：一个大盒子里装着数千个 IC，另一个小盒子里只装了 10 个。小盒子上贴着一个标签，上面写着：“这些是有缺陷的。”

<a id="d24e1418"></a>
如果我们真的有这种质量控制就好了。但现实世界不会让我们生产出真正完美的软件，尤其是没有错误的软件。时间、技术和气质都会对我们不利。

<a id="d24e1420"></a>
然而，这并不一定令人沮丧。正如 Ed Yourdon 在 IEEE Software 的一篇文章中所述，[*当足够好的软件是最好的* [You95]](<../A2 Exercise Answers/README.md#d6040e1088>) 时，您可以训练自己编写足够好的软件 — 对您的用户、未来的维护人员和您自己来说足够好。您会发现您的工作效率更高，您的用户也更满意。您可能会发现您的程序实际上由于孵化时间较短而更好。

<a id="d24e1433"></a>
在我们进一步讨论之前，我们需要先限定一下我们要说的内容。 “足够好”一词并不意味着草率或制作不良的代码。所有系统都必须满足用户的要求才能成功，并满足基本的性能、隐私和安全标准。我们只是提倡让用户有机会参与决定您所生成的内容何时足以满足他们的需求。

### 让您的用户参与权衡

<a id="d24e1440"></a>
<a id="FNPTR-8"></a>
通常你是在为其他人编写软件。通常您会记得找出他们想要什么。[[8]](<07 Communicate - communicate.md#FOOTNOTE-8>) 但是您是否问过他们希望他们的软件有多好？有时会别无选择。如果您正在开发起搏器、自动驾驶仪或将广泛传播的低级库，那么要求将更加严格，您的选择也将更加有限。

<a id="d24e1453"></a>
但是，如果您正在开发全新产品，您将面临不同的限制。营销人员必须遵守承诺，最终用户可能已经根据交付时间表制定了计划，而您的公司肯定会受到现金流限制。仅仅为了向程序添加新功能或再次完善代码而忽略这些用户的要求是不专业的。我们并不是提倡恐慌：承诺不可能的时间范围和在最后期限前偷工减料同样是不专业的。

<a id="d24e1455"></a>
您生成的系统的范围和质量应该作为该系统要求的一部分进行讨论。

**技巧 8：将质量作为需求问题**

<a id="d24e1477"></a>
通常，您会遇到需要权衡的情况。令人惊讶的是，许多用户宁愿现在使用一些粗糙的软件，也不愿等待一年才能获得闪亮的、花里胡哨的版本（事实上，无论如何，一年后他们需要的可能会完全不同）。许多预算紧张的 IT 部门都会同意这一点。今天的优秀软件往往比明天的完美软件的幻想更可取。如果您尽早为用户提供一些可以玩的东西，他们的反馈通常会引导您找到更好的最终解决方案（请参阅主题 12，[*曳光弹*](<../02 Pragmatic Approach/12 Tracer Bullets - tracer_bullets.md#tracer_bullets>)）。

### 知道何时停止

<a id="d24e1493"></a>
在某些方面，编程就像绘画。您从空白画布和某些基本原材料开始。你结合科学、艺术和工艺来决定如何处理它们。您绘制出整体形状，绘制底层环境，然后填充细节。你不断地后退一步，以批判的眼光审视自己所做的事情。有时你会扔掉画布并重新开始。

<a id="d24e1495"></a>
但艺术家会告诉你，如果你不知道何时停止，所有的努力都会付诸东流。如果你一层又一层地添加细节，那么这幅画就会消失在颜料中。

<a id="d24e1500"></a>
不要因过度修饰和过度细化而破坏一个完美的程序。继续，让你的代码独立一段时间。它可能并不完美。别担心：它永远不可能是完美的。 （在第 7 章 [*当你编码时*](<../07 While Coding/README.md#coding>) 中，我们将讨论在不完美的世界中开发代码的哲学。）

### 挑战

<a id="d24e1529"></a>
<a id="d24e1536"></a>
<a id="d24e1543"></a>
- 查看您经常使用的软件工具和操作系统。您能否找到任何证据表明这些组织和/或开发人员愿意发布他们知道不完美的软件？作为用户，您是否愿意（1）等待他们解决所有错误，（2）拥有复杂的软件并接受一些错误，还是（3）选择缺陷较少的简单软件？
- 考虑模块化对软件交付的影响。与设计为非常松散耦合的模块或微服务的系统相比，使紧密耦合的整体软件块达到所需的质量需要更多还是更少的时间？每种方法的优点或缺点是什么？
- 您能想到哪些流行软件存在功能膨胀的问题吗？也就是说，软件包含的功能远多于您使用过的功能，每个功能都会带来更多错误和安全漏洞的机会，并使您使用的功能更难查找和管理。您自己是否有落入这个陷阱的危险？
