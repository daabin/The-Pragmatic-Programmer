## 主题 38. 凭巧编程

<a id="d24e19610"></a>
你看过老黑白战争电影吗？疲惫的士兵小心翼翼地走出灌木丛。前面有一片空地：有没有地雷，或者穿越安全吗？没有任何迹象表明这是一个雷区——没有任何标志、铁丝网或弹坑。士兵用刺刀戳着前方的地面，畏缩着，期待着爆炸。没有一个。于是，他费力地在田野里走了一段时间，边走边戳戳。最终，他确信场地是安全的，他直起身子，自豪地向前迈进，结果却被炸成了碎片。

<a id="d24e19626"></a>
这名士兵最初的地雷探测没有发现任何结果，但这只是幸运的。他得出了一个错误的结论——带来了灾难性的后果。

<a id="d24e19628"></a>
作为开发人员，我们也在雷区工作。每天都有数百个陷阱等着我们。记住士兵的故事，我们应该警惕得出错误的结论。我们应该避免巧合编程——依靠运气和偶然的成功——而应该有意识地编程。

### 如何通过巧合进行编程

<a id="d24e19642"></a>
假设 Fred 被分配了一项编程任务。弗雷德输入一些代码并尝试一下，它似乎有效。 Fred 输入了更多代码，尝试了一下，它似乎仍然有效。以这种方式编码几周后，程序突然停止工作，经过几个小时的尝试修复后，他仍然不知道原因。 Fred 可能会花费大量时间来查找这段代码，但无法修复它。无论他做什么，似乎都没有效果。

<a id="d24e19644"></a>
Fred 不知道代码为何失败，因为他一开始就不知道代码为何有效。考虑到弗雷德所做的有限“测试”，这似乎有效，但这只是一个巧合。在虚假信心的鼓舞下，弗雷德冲向了遗忘。现在，大多数聪明人可能认识像弗雷德这样的人，但我们知道得更多。我们不依赖巧合，不是吗？

<a id="d24e19652"></a>
有时我们可能会。有时很容易将美好的巧合与有目的的计划混淆。让我们看几个例子。

#### 实施事故

<a id="d24e19657"></a>
实施事故是指仅仅因为当前代码的编写方式而发生的事情。您最终会依赖未记录的错误或边界条件。

<a id="d24e19676"></a>
假设您调用一个包含错误数据的例程。该例程以特定方式响应，您可以根据该响应进行编码。但作者并没有打算让这个例程以这种方式进行——甚至从未考虑过。当例程得到“修复”时，您的代码可能会中断。在最极端的情况下，您调用的例程甚至可能没有被设计为执行您想要的操作，但它似乎工作正常。以错误的顺序或在错误的上下文中调用事物是一个相关的问题。

<a id="d24e19681"></a>
看起来 Fred 正在拼命尝试使用某些特定的 GUI 渲染框架在屏幕上显示一些内容：

```
paint();
invalidate();
validate();
revalidate();
repaint();
paintImmediately();
```

<a id="d24e19697"></a>
但这些例程从来没有被设计成这样调用；尽管它们看起来有效，但这实际上只是巧合。

<a id="d24e19699"></a>
雪上加霜的是，当场景最终被绘制出来时，弗雷德不会尝试回去消除虚假呼叫。 “现在可以了，最好还是别管了……”

<a id="d24e19701"></a>
这种想法很容易被愚弄。为什么你要冒险搞乱那些正在运行的东西呢？嗯，我们可以想到几个原因：

<a id="d24e19709"></a>
<a id="d24e19712"></a>
<a id="d24e19715"></a>
<a id="d24e19718"></a>
<a id="d24e19725"></a>
- 它可能并没有真正起作用——它可能只是看起来像这样。
- 你所依赖的边界条件可能只是一个意外。在不同的情况下（不同的屏幕分辨率、更多的 CPU 核心），它的行为可能会有所不同。
- 未记录的行为可能会随着库的下一个版本而改变。
- 额外的和不必要的调用会使您的代码变慢。
- 额外的调用会增加引入新错误的风险。

<a id="d24e19736"></a>
对于您编写的其他人将调用的代码，良好的模块化和将实现隐藏在小型、文档齐全的接口后面的基本原则都会有所帮助。一份明确的合同（参见主题 23，[*按合同设计*](<../04 Pragmatic Paranoia/23 Design by Contract - dbc.md#dbc>)）可以帮助消除误解。

<a id="d24e19755"></a>
对于您调用的例程，仅依赖记录的行为。如果无论出于何种原因你不能，那么就好好记录你的假设。

#### 足够接近还不够

<a id="d24e19769"></a>
<a id="FNPTR-50"></a>
我们曾经参与过一个大型项目，该项目报告来自现场大量硬件数据收集单元的数据。这些单位跨越州和时区，并且由于各种后勤和历史原因，每个单位都设置为当地时间。[[50]](<44 Naming Things - naming.md#FOOTNOTE-50>) 由于时区解释的冲突以及夏令时政策的不一致，结果几乎总是错误的，但仅相差一个。该项目的开发人员已经养成了只加一或减一即可得到正确答案的习惯，他们认为在这种情况下只相差一。然后下一个函数会以另一种方式将该值视为关闭，并将其更改回来。

<a id="d24e19785"></a>
但有时“仅”有一个偏差这一事实纯属巧合，掩盖了更深层次、更根本的缺陷。如果没有适当的时间处理模型，随着时间的推移，整个大型代码库就会变成大量无法维持的 +1 和 -1 语句。最终，这些都不正确，该项目被废弃。

#### 幻影图案

<a id="d24e19796"></a>
<a id="FNPTR-51"></a>
人类生来就能够看到模式和原因，即使这只是巧合。例如，俄罗斯领导人总是在秃头和多毛之间交替：一位秃顶（或明显秃顶）的俄罗斯国家领导人接替了一位不秃顶（“多毛”）的国家领导人，反之亦然，持续了近 200 年。[[51]](<44 Naming Things - naming.md#FOOTNOTE-51>)

<a id="d24e19809"></a>
但是，虽然你不会编写依赖于下一任俄罗斯领导人是秃头还是多毛的代码，但在某些领域我们一直这样认为。赌徒想象彩票号码、骰子游戏或轮盘赌的模式，而实际上这些是统计上独立的事件。在金融领域，股票和债券交易同样充满了巧合，而不是实际的、可辨别的模式。

<a id="d24e19811"></a>
每 1,000 个请求显示一个间歇性错误的日志文件可能是难以诊断的竞争条件，也可能是一个普通的旧错误。似乎在您的计算机上通过但在服务器上未通过的测试可能表明两个环境之间存在差异，或者可能只是巧合。

<a id="d24e19813"></a>
不要假设它，而是证明它。

#### 上下文的意外

<a id="d24e19822"></a>
你也可能会遇到“上下文意外”。假设您正在编写一个实用程序模块。仅仅因为您当前正在为 GUI 环境编码，该模块是否必须依赖于 GUI 的存在？您是否依赖英语用户？有文化的用户？您还依赖什么得不到保证的东西？

<a id="d24e19833"></a>
您是否依赖当前目录可写？是否存在某些环境变量或配置文件？服务器上的时间是否准确——在什么容差范围内？您是否依赖网络可用性和速度？

<a id="d24e19835"></a>
<a id="FNPTR-52"></a>
当您从网上找到的第一个答案复制代码时，您确定您的上下文是相同的吗？或者您正在构建“货物崇拜”代码，只是模仿形式而没有内容？[[52]](<44 Naming Things - naming.md#FOOTNOTE-52>)

<a id="d24e19842"></a>
找到一个恰好合适的答案并不等同于正确的答案。

**提示 62：不要出于巧合而编程**

#### 隐含假设

<a id="d24e19853"></a>
巧合可能会在各个层面上产生误导——从生成需求到测试。测试尤其充满错误的因果关系和巧合的结果。很容易假设 X 导致 Y，但正如我们在主题 20 中所说的，[*调试*](<../03 Basic Tools/20 Debugging - debug.md#debug>)：不要假设它，而是证明它。

<a id="d24e19881"></a>
在各个层面上，人们在操作时都会考虑到许多假设，但这些假设很少被记录下来，并且在不同的开发人员之间经常发生冲突。不基于既定事实的假设是所有项目的祸根。

### 如何刻意编程

<a id="d24e19886"></a>
我们希望花更少的时间编写代码，在开发周期中尽早捕获并修复错误，并从一开始就产生更少的错误。如果我们能够有意识地编程，将会有所帮助：

<a id="d24e19890"></a>
<a id="d24e19895"></a>
<a id="d24e19912"></a>
<a id="d24e19915"></a>
<a id="d24e19922"></a>
<a id="d24e19934"></a>
<a id="d24e19953"></a>
<a id="d24e19998"></a>
<a id="d24e20023"></a>
<a id="FNPTR-53"></a>
- 始终意识到自己在做什么。弗雷德让事情慢慢失去控制，直到他最终像青蛙[这里](<../01 Pragmatic Philosophy/04 Stone Soup and Boiled Frogs - stone_soup.md#stone_soup>)一样被煮熟。
- 您能向初级程序员详细解释一下代码吗？如果不是，也许你只是依赖巧合。
- 不要在黑暗中编码。构建一个您没有完全掌握的应用程序，或者使用您不理解的技术，您可能会被巧合所困扰。如果你不确定它为什么有效，你就不会知道它为什么失败。
- 从计划出发，无论该计划是在您的脑海中、在鸡尾酒餐巾纸的背面还是在白板上。
- 只依赖可靠的事物。不要依赖于假设。如果您无法判断某件事是否可靠，请假设最坏的情况。
- 记录你的假设。主题 23，[*按合同设计*](<../04 Pragmatic Paranoia/23 Design by Contract - dbc.md#dbc>)，可以帮助澄清您自己心中的假设，并帮助将它们传达给其他人。
- 不要只测试您的代码，还要测试您的假设。不要猜测；实际尝试一下。编写一个断言来测试您的假设（请参阅主题 25，[*断言编程*](<../04 Pragmatic Paranoia/25 Assertive Programming - assertions.md#assertions>)）。如果您的断言是正确的，那么您已经改进了代码中的文档。如果你发现你的假设是错误的，那么你就算幸运的了。
- 优先考虑你的努力。花时间在重要的方面；这些很可能是最困难的部分。如果你没有正确的基础知识或基础设施，再出色的花哨功能也将毫无意义。
- 不要成为历史的奴隶。不要让现有的代码决定未来的代码。如果不再合适，所有代码都可以替换。即使在一个程序中，也不要让已经完成的事情限制您下一步要做的事情——准备好重构（参见主题 40，[*重构*](<40 Refactoring - refactor.md#refactor>)）。这一决定可能会影响项目进度。假设影响将小于不进行更改的成本。[[53]](<44 Naming Things - naming.md#FOOTNOTE-53>)

<a id="d24e20033"></a>
因此，下次当某件事看起来有效但你不知道为什么时，请确保这不仅仅是巧合。
