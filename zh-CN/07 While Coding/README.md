# 第 7 章 - 编码之时

<a id="coding"></a>

<a id="d24e19194"></a>
传统观点认为，一旦项目进入编码阶段，工作大部分都是机械的，将设计转录为可执行语句。我们认为这种态度是软件项目失败的最大原因，许多系统最终变得丑陋、效率低下、结构不良、难以维护，或者根本就是错误的。

<a id="d24e19196"></a>
编码不是机械的。如果是这样的话，早在 20 世纪 80 年代初人们寄希望于的所有 CASE 工具早就取代了程序员了。每分钟都要做出决定——如果最终的程序要享受长久、准确和富有成效的生活，就需要仔细思考和判断。

<a id="d24e19202"></a>
并非所有决定都是有意识的。当你学习主题 37，倾听你的蜥蜴大脑 时，你可以更好地利用你的直觉和无意识的想法。我们将了解如何更仔细地倾听，并寻找积极回应这些有时琐碎的想法的方法。

<a id="d24e19218"></a>
但倾听你的直觉并不意味着你可以自动驾驶。不积极思考代码的开发人员的编程纯属巧合——代码可能有效，但没有特殊原因。在主题 38 巧合编程 中，我们提倡更积极地参与编码过程。

<a id="d24e19236"></a>
虽然我们编写的大多数代码执行速度都很快，但我们偶尔会开发一些算法，即使是最快的处理器也有可能陷入困境。在主题 39 算法速度 中，我们讨论了估计代码速度的方法，并提供了一些关于如何在潜在问题发生之前发现它们的提示。

<a id="d24e19254"></a>
务实的程序员批判性地思考所有代码，包括我们自己的代码。我们不断发现我们的程序和设计有改进的空间。在主题 40 重构 中，我们研究了帮助我们不断修复现有代码的技术。

<a id="d24e19267"></a>
测试不是为了发现错误，而是为了获取代码的反馈：设计、API、耦合等方面。这意味着测试的主要好处发生在您思考和编写测试时，而不仅仅是在运行测试时。我们将在主题 41 测试代码 中探讨这个想法。

<a id="d24e19301"></a>
但是，当然，当您测试自己的代码时，您可能会给任务带来自己的偏见。在主题 42 基于属性的测试 中，我们将了解如何让计算机为您进行一些广泛的测试以及如何处理不可避免的出现的错误。

<a id="d24e19313"></a>
编写可读且易于推理的代码至关重要。这是一个严酷的世界，充满了不良行为者，他们积极尝试闯入您的系统并造成伤害。我们将讨论一些非常基本的技术和方法来帮助您主题 43，外出注意安全。

<a id="d24e19329"></a>
最后，软件开发中最难的事情之一是主题 44，命名事物。我们必须给很多东西命名，而在很多方面，我们选择的名称定义了我们创造的现实。在编码时，您需要注意任何潜在的语义偏差。

<a id="d24e19342"></a>
我们大多数人都可以在很大程度上依靠自动驾驶来驾驶汽车。我们不会明确命令我们的脚踩踏板，或者我们的手臂转动方向盘，我们只是想“减速并右转”。然而，优秀、安全的驾驶员会不断审视情况，检查潜在问题，并做好准备，以防意外情况发生。编码也是如此——这可能在很大程度上是例行公事，但保持警惕可以很好地防止灾难。
