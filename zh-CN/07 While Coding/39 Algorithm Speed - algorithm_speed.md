## 主题 39. 算法速度

<a id="d24e20127"></a>
在主题 15 估计 中，我们讨论了估算诸如步行穿过城镇需要多长时间，或者一个项目需要多长时间才能完成之类的事情。然而，实用程序员几乎每天都会使用另一种估计：估计算法使用的资源——时间、处理器、内存等。

<a id="d24e20150"></a>
这种估计通常至关重要。如果有两种做某事的方式可供选择，你会选择哪一种？您知道您的程序在处理 1,000 条记录时运行了多长时间，但是它将如何扩展到 1,000,000 条呢？哪些部分的代码需要优化？

<a id="d24e20152"></a>
事实证明，这些问题通常可以通过常识、一些分析以及一种称为 Big-O 表示法的近似值书写方式来回答。

### 估计算法是什么意思？

<a id="d24e20162"></a>
大多数重要的算法处理某种变量输入——对 $ n $ 字符串进行排序，反转 $ m \times n $ 矩阵，或者使用 $ n $ 位密钥解密消息。通常，该输入的大小会影响算法：输入越大，运行时间越长或使用的内存越多。

<a id="d24e20170"></a>
如果关系始终是线性的（因此时间与 $n$ 的值成正比增加），则此部分并不重要。然而，最重要的算法不是线性的。好消息是许多都是次线性的。例如，二分搜索在查找匹配项时不需要查看每个候选者。坏消息是其他算法比线性算法要差得多。运行时间或内存需求的增长速度远远快于 $ n $。需要一分钟处理 10 个项目的算法可能需要一辈子才能处理 100 个项目。

<a id="d24e20176"></a>
我们发现，每当我们编写任何包含循环或递归调用的内容时，我们都会下意识地检查运行时和内存需求。这很少是一个正式的过程，而是快速确认我们正在做的事情在这种情况下是明智的。然而，我们有时确实发现自己在进行更详细的分析。这就是 Big-O 表示法派上用场的时候。

<a id="big-o"></a>
### 大 O 表示法

<a id="d24e20193"></a>
Big-O 表示法，写作`O()`，是一种处理近似值的数学方法。当我们写到特定的排序例程在 `O(n^2)` 时间内对 `O()` 记录进行排序时，我们只是说最坏情况下所花费的时间将随着 $ n $ 的平方而变化。记录数量增加一倍，时间将增加大约四倍。将 $ O $ 视为以下含义。

<a id="d24e20210"></a>
`O()` 表示法为我们正在测量的事物（时间、内存等）的值设置了上限。如果我们说一个函数花费`O(n^2)`时间，那么我们知道它花费的时间上限不会比$n^2$增长得更快。有时我们会提出相当复杂的 `O()` 函数，但由于随着 $ n $ 的增加，最高阶项将主导该值，因此惯例是删除所有低阶项，并且不费心显示任何常数乘法因子：

```text
O(n^2 / 2 + 3n) is the same as O(n^2 / 2) is the same as O(n^2)
```

<a id="d24e20233"></a>
这实际上是 `O()` 表示法的一个特性 - 一个 `O(n^2)` 算法可能比另一个 `O(n^2)` 算法快 1,000 倍，但您不会从该表示法中知道这一点。 Big-O 永远不会为您提供时间或内存等实际数字：它只是告诉您这些值将如何随着输入的变化而变化。

<a id="d24e20241"></a>
图 3，<a href="#fig-onotation">各种算法的运行时间</a> 显示了您会遇到的几种常见的 `O()` 符号，以及比较每个类别中算法的运行时间的图表。显然，一旦我们克服了`O(n^2)`，事情很快就会开始失控。

<a id="d24e20248"></a>
例如，假设您有一个例程，需要一秒钟来处理 100 条记录。处理1,000个需要多长时间？如果你的代码是`O(1)`，那么它仍然需要一秒钟。如果是 `O(log n)`，那么您可能会等待大约三秒钟。 `O(n)` 将显示线性增加至 10 秒，而 `O(n log n)` 将需要大约 33 秒。如果您不幸拥有 `O(n^2)` 例程，请等待 100 秒，让其发挥作用。如果您使用指数算法 `O(2^n)`，您可能想泡一杯咖啡 - 您的日常工作应该在大约 `10^263` 年内完成。让我们知道宇宙如何终结。

<a id="d24e20357"></a>
`O()` 符号不仅仅适用于时间；它还适用于时间。您可以使用它来表示算法使用的任何其他资源。例如，能够对内存消耗进行建模通常很有用（请参阅练习中的示例）。

<a id="pg-common-sense"></a>
### 常识估计

<a id="d24e20428"></a>
您可以使用常识来估计许多基本算法的阶数。

<a id="d24e20434"></a>
<a id="d24e20468"></a>
<a id="d24e20497"></a>
<a id="d24e20516"></a>
<a id="d24e20534"></a>
简单循环：如果一个简单循环从$1$运行到$n$，那么算法很可能是$O(n)$——时间随着$n$线性增加。示例包括穷举搜索、查找数组中的最大值以及生成校验和。

嵌套循环：如果将一个循环嵌套在另一个循环中，那么您的算法将变为 $O(m\times n)$，其中 $m$ 和 $n$ 是两个循环的限制。这通常发生在简单的排序算法中，例如冒泡排序，其中外部循环依次扫描数组中的每个元素，内部循环计算出该元素在排序结果中的放置位置。此类排序算法往往是`O(n^2)`。

二元斩波：如果您的算法将每次循环时考虑的事物集减半，那么它很可能是对数的，`O(log n)`。排序列表的二分搜索、遍历二叉树以及查找机器字中的第一个设置位都可以是`O(log n)`。

分而治之：将输入工作独立地划分为两半，然后将结果组合起来的算法可以是$O(n\,\lg{n})$。典型的例子是快速排序，它的工作原理是将数据分为两半，然后对每一半进行递归排序。尽管从技术上讲，由于在输入排序输入时其行为会降低，所以快速排序的平均运行时间为 $O(n\,\lg{n})$。

组合：每当算法开始考虑事物的排列时，它们的运行时间可能会失控。这是因为排列涉及阶乘（从 1 到 5 的数字有 $5!= 5\times 4 \times 3 \times 2 \times 1 = 120$ 种排列）。对五个元素的组合算法进行计时：运行六个元素所需的时间要长六倍，运行七个元素所需的时间要长 42 倍。例子包括许多公认的难题的算法——旅行推销员问题、将东西最佳地包装到容器中、划分一组数字以使每组数字具有相同的总数等等。通常，启发式方法用于减少特定问题领域中此类算法的运行时间。

### 实践中的算法速度

<a id="d24e20570"></a>
在您的职业生涯中，您不太可能花费大量时间来编写排序例程。您可以使用的库中的库可能会胜过您无需付出大量努力即可编写的任何内容。然而，我们之前描述的基本算法类型一次又一次地出现。每当您发现自己正在编写一个简单的循环时，您就知道您有一个 $O(n)$ 算法。如果该循环包含内部循环，那么您将看到 $O(m \times n)$。您应该问自己这些值可以达到多大。如果数字有界，那么您就会知道代码运行需要多长时间。如果这些数字取决于外部因素（例如夜间批量运行中的记录数或人员列表中的姓名数），那么您可能需要停下来考虑大值可能对运行时间或内存消耗产生的影响。

**提示 63：估计算法的顺序**

<a id="d24e20608"></a>
您可以采取一些方法来解决潜在的问题。如果您有一个`O(n^2)`算法，请尝试找到一种分而治之的方法，将您带到`O(n log n)`。

<a id="d24e20618"></a>
如果您不确定代码将花费多长时间，或者将使用多少内存，请尝试运行它，改变输入记录计数或任何可能影响运行时的内容。然后绘制结果。您应该很快就能很好地了解曲线的形状。随着输入大小的增加，它是向上弯曲、直线还是变平？三四点应该会给你一个想法。

<a id="d24e20624"></a>
还要考虑您在代码本身中所做的事情。对于较小的 $n$ 值，简单的 `O(n^2)` 循环可能比复杂的 `O(n log n)` 循环表现得更好，特别是当 `O(n log n)` 算法具有昂贵的内部循环时。

<a id="d24e20634"></a>
在所有这些理论的中间，不要忘记也有实际的考虑。对于小输入集，运行时间可能看起来呈线性增加。但是，如果向代码提供数百万条记录，随着系统开始崩溃，时间就会突然缩短。如果您使用随机输入键测试排序例程，您可能会在第一次遇到有序输入时感到惊讶。尝试涵盖理论和实践基础。经过所有这些估计后，唯一重要的时间是在生产环境中使用真实数据运行的代码的速度。这引出了我们的下一个技巧。

**提示 64：测试您的估计**

<a id="d24e20647"></a>
如果很难获得准确的计时，请使用代码分析器来计算算法中不同步骤的执行次数，并根据输入的大小绘制这些数字。

#### 最好并不总是最好

<a id="d24e20657"></a>
您还需要务实地选择合适的算法——最快的算法并不总是最适合这项工作。给定一个小的输入集，直接插入排序的性能与快速排序一样好，并且会花费更少的时间来编写和调试。如果您选择的算法设置成本较高，您还需要小心。对于较小的输入集，此设置可能会缩短运行时间并使算法不合适。

<a id="d24e20663"></a>
还要警惕过早的优化。在投入宝贵的时间尝试改进算法之前，确保算法确实是瓶颈总是一个好主意。
