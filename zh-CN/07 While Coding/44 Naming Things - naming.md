## 主题 44. 命名之道

> 智慧的开始是用事物的专有名称来称呼它们。
>
> 孔子

<a id="d24e23783"></a>
名字里有什么？当我们编程时，答案是“一切！”

<a id="d24e23794"></a>
我们为应用程序、子系统、模块、函数、变量创建名称——我们不断地创建新事物并赋予它们名称。这些名字非常非常重要，因为它们揭示了很多关于你的意图和信念。

<a id="d24e23800"></a>
我们相信事物应该根据它们在代码中扮演的角色来命名。这意味着，每当你创造一些东西时，你需要停下来思考“我创造这个东西的动机是什么？”

<a id="d24e23802"></a>
这是一个强有力的问题，因为它让你摆脱直接解决问题的心态，让你看到更大的前景。当您考虑变量或函数的作用时，您会考虑它的特殊之处、它可以做什么以及它与什么交互。通常，我们发现自己意识到我们要做的事情毫无意义，这一切都是因为我们无法想出一个合适的名字。

<a id="d24e23804"></a>
<a id="FNPTR-67"></a>
名字具有深刻意义这一观点背后有一定的科学依据。事实证明，大脑可以非常快地阅读和理解单词：比许多其他活动都快。这意味着当我们试图理解某件事时，词语具有一定的优先性。这可以使用斯特鲁普效应来证明。<a href="#FOOTNOTE-67">[67]</a>

<a id="d24e23811"></a>
<a id="FNPTR-68"></a>
请看下面的面板。它有一个颜色名称或阴影列表，每个颜色名称或阴影都以一种颜色或阴影显示。但名称和颜色不一定匹配。这是挑战的第一部分 - 大声说出每种颜色的名称：<a href="#FOOTNOTE-68">[68]</a>

<a id="d24e23825"></a>
现在重复此操作，但大声说出用于绘制单词的颜色。更难吧？阅读时很容易流利，但在尝试识别颜色时却很难。

<a id="d24e23828"></a>
你的大脑将书面文字视为值得尊重的东西。我们需要确保我们使用的名称符合这一点。

<a id="d24e23830"></a>
让我们看几个例子：

<a id="d24e23834"></a>
<a id="d24e23840"></a>
<a id="d24e23858"></a>
<a id="d24e23879"></a>
<a id="d24e23893"></a>
<a id="d24e23911"></a>
<a id="d24e23920"></a>
<a id="d24e23924"></a>
- 我们正在对访问我们销售旧显卡制成的珠宝的网站的用户进行身份验证：

  ```
  let user = authenticate(credentials)
  ```

该变量是 user，因为它始终是 user。但为什么？这没有任何意义。客户或买家怎么样？这样，当我们编写代码时，我们就会得到不断的提醒，了解这个人正在尝试做什么，以及这对我们意味着什么。
- 我们有一个对订单进行折扣的实例方法：

  ```
  public void deductPercent(double amount)
      // ...
  ```

这里有两件事。首先，deductPercent 是它的作用，而不是它这样做的原因。那么参数数量的名称充其量是具有误导性的：它是绝对数量还是百分比？

也许这样会更好：

  ```
  public void applyDiscount(Percentage discount)
    // ...
  ```

方法名称现在清楚地表明了其意图。我们还将参数从双精度更改为百分比，这是我们定义的类型。我们不了解您的情况，但在处理百分比时，我们永远不知道该值是否应该在 0 到 100 之间或 0.0 到 1.0 之间。使用类型记录函数所期望的内容。
- 我们有一个模块可以用斐波那契数做有趣的事情。其中之一是计算序列中的第 $n^{th}$ 个数字。停下来想想你会如何称呼这个函数。

我们问的大多数人都会称之为谎言。看起来很合理，但请记住它通常会在其模块的上下文中调用，因此调用将是 Fib.fib(n)。将其称为 of 或 nth 怎么样：

  ```
  Fib.of(0)    # => 0
  Fib.nth(20)  # => 4181
  ```

<a id="d24e23954"></a>
在命名事物时，您会不断寻找澄清您的意思的方法，而这种澄清行为将使您在编写代码时更好地理解代码。

<a id="d24e23958"></a>
然而，并非所有名字都必须是文学奖的候选人。

### 尊重文化

<a id="d24e24002"></a>
<a id="FNPTR-69"></a>
大多数介绍性计算机文本都会告诫您不要使用单字母变量，例如 i、j 或 k。<a href="#FOOTNOTE-69">[69]</a>

<a id="d24e24068"></a>
我们认为他们错了。有点像。

<a id="d24e24070"></a>
事实上，这取决于特定编程语言或环境的文化。在 C 编程语言中，i、j 和 k 传统上用作循环增量变量，s 用作字符串，等等。如果您在那种环境中编程，这就是您习惯看到的情况，违反该规范将是不和谐的（因此是错误的）。另一方面，在不期望的不同环境中使用该约定同样是错误的。你永远不会做像这个 Clojure 示例这样令人发指的事情，它将一个字符串分配给变量 i：

```
(let [i "Hello World"]
        (println i))
```

<a id="d24e24103"></a>
一些语言社区更喜欢驼峰命名法，嵌入大写字母，而另一些语言社区则喜欢使用蛇\_命名法，嵌入下划线来分隔单词。语言本身当然会接受其中任何一个，但这并不意味着它就是正确的。尊重当地文化。

<a id="d24e24127"></a>
某些语言允许名称中包含 Unicode 的子集。在使用诸如 ɹǝsn 或 εxiέρχεται 这样的可爱名字之前，先了解一下社区的期望。

### 一致性

<a id="d24e24140"></a>
艾默生因写下“愚蠢的一致性是小头脑的怪物……”而闻名，但艾默生并不属于程序员团队。

<a id="d24e24149"></a>
每个项目都有自己的词汇：对团队具有特殊含义的行话。对于创建在线商店的团队而言，“秩序”意味着一回事，而对于其应用程序绘制宗教团体谱系的团队来说，“秩序”的含义则截然不同。重要的是，团队中的每个人都知道这些词的含义，并且一致地使用它们。

<a id="d24e24155"></a>
一种方法是鼓励大量沟通。如果每个人都结对编程，并且结对频繁地切换，那么行话就会渗透式传播。

<a id="d24e24161"></a>
另一种方法是建立一个项目术语表，列出对团队有特殊含义的术语。这是一份非正式文档，可能保存在 wiki 上，也可能只是某处墙上的索引卡。

<a id="d24e24180"></a>
一段时间后，项目术语将获得自己的生命。当每个人都熟悉这些词汇后，您将能够使用术语作为速记，准确而简洁地表达许多含义。 （这正是模式语言。）

### 改名更难

<a id="d24e24199"></a>
无论你前期付出多少努力，事情都会发生变化。代码被重构，用法发生变化，含义也发生了微妙的改变。如果您在更新名称时不保持警惕，您很快就会陷入比无意义名称更糟糕的噩梦：误导性名称。您是否曾经有人解释过代码中的不一致之处，例如“名为 getData 的例程确实将数据写入存档文件”？

<a id="d24e24211"></a>
正如我们在主题 3 软件熵 中讨论的那样，当您发现问题时，立即修复它。当您看到名称不再表达意图或者具有误导性或令人困惑时，请修复它。您已经进行了完整的回归测试，因此您将发现您可能错过的任何实例。

**提示 74：起个好名字；需要时重命名**

<a id="d24e24230"></a>
如果由于某种原因您无法更改现在错误的名称，那么您就会遇到更大的问题：ETC 违规（请参阅主题 8，优秀设计的本质）。先解决这个问题，然后更改有问题的名称。使重命名变得容易，并经常进行。

<a id="d24e24241"></a>
否则，您将不得不向团队中的新人解释 getData 确实将数据写入文件，并且您必须板着脸做这件事。
