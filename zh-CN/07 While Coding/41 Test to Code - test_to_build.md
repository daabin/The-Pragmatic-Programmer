## 主题 41. 用测试来思考代码

<a id="d24e21222"></a>
本书的第一版是在更原始的时代编写的，当时大多数开发人员都没有编写测试——他们认为，为什么还要这么麻烦呢，反正世界末日将在 2000 年到来。

<a id="d24e21243"></a>
在那本书中，我们有一节介绍如何构建易于测试的代码。这是说服开发人员实际编写测试的一种偷偷摸摸的方式。

<a id="d24e21245"></a>
这是更加开明的时代。如果有任何开发人员仍然没有编写测试，他们至少知道他们应该编写测试。

<a id="d24e21247"></a>
但仍然有一个问题。当我们问开发人员为什么要编写测试时，他们看着我们，就好像我们只是问他们是否仍然使用打孔卡进行编码一样，他们会说“以确保代码有效”，最后不言而喻“你这个笨蛋”。我们认为这是错误的。

<a id="d24e21252"></a>
那么我们认为测试最重要的是什么？我们认为你应该如何去做？

<a id="d24e21261"></a>
让我们从大胆的声明开始：

**提示 66：测试不是为了寻找错误**

<a id="d24e21269"></a>
我们相信，测试的主要好处是在您思考和编写测试时产生的，而不是在运行测试时产生的。

### 关于测试的思考

<a id="d24e21283"></a>
这是一个星期一的早晨，您开始编写一些新代码。您必须编写一些内容来查询数据库，以返回每周在您的“世界上最有趣的洗碗视频”网站上观看超过 10 个视频的人员列表。

<a id="d24e21285"></a>
您启动编辑器，然后开始编写执行查询的函数：

```
def return_avid_viewers do
  # ... hmmm ...
end
```

<a id="d24e21302"></a>
停止！你怎么知道你要做的事情是件好事？

<a id="d24e21304"></a>
答案是你无法知道这一点。没有人可以。但考虑一下测试可以让这种情况更有可能发生。这是它的工作原理。

<a id="d24e21306"></a>
首先想象您已经完成了该函数的编写，现在必须对其进行测试。你会怎么做？好吧，您想要使用一些测试数据，这可能意味着您想要在您控制的数据库中工作。现在，一些框架可以为您处理这个问题，针对测试数据库运行测试，但在我们的例子中，这意味着我们应该将数据库实例传递到我们的函数中，而不是使用某个全局实例，因为这允许我们在测试时更改它：

```
def return_avid_users(db) do
```

<a id="d24e21316"></a>
然后我们必须考虑如何填充测试数据。该要求要求提供“每周观看超过 10 个视频的人员名单”。因此，我们查看数据库架构以查找可能有帮助的字段。我们在谁观看了什么表中找到了两个可能的字段：opened\_video 和completed\_video。为了编写测试数据，我们需要知道要使用哪个字段。但我们不知道这个要求意味着什么，而且我们的业务联系也已中断。让我们作弊并传递字段名称（这将允许我们测试我们拥有的内容，并可能稍后更改它）：

```
def return_avid_users(db, qualifying_field_name) do
```

<a id="d24e21333"></a>
我们首先考虑我们的测试，无需编写一行代码，我们就已经有了两个发现，并使用它们来更改我们方法的 API。

### 测试驱动编码

<a id="d24e21338"></a>
在前面的示例中，考虑测试使我们减少了代码中的耦合（通过传递数据库连接而不是使用全局连接）并提高了灵活性（通过将我们测试的字段名称作为参数）。考虑为我们的方法编写测试使我们从外部看待它，就好像我们是代码的客户，而不是它的作者一样。

**提示 67：测试是代码的第一个用户**

<a id="d24e21360"></a>
我们认为这可能是测试提供的最大好处：测试是指导您编码的重要反馈。

<a id="d24e21362"></a>
与其他代码紧密耦合的函数或方法很难测试，因为您必须先设置所有环境，然后才能运行您的方法。因此，让你的东西可测试也会减少它的耦合。

<a id="d24e21364"></a>
在测试某些东西之前，您必须先了解它。这听起来很愚蠢，但实际上，我们都是基于对我们必须做什么的模糊理解而编写了一段代码。我们向自己保证，随着我们的努力，我们一定会解决这个问题。哦，我们稍后也会添加所有代码来支持边界条件。哦，还有错误处理。而且代码最终比应有的长度长了五倍，因为它充满了条件逻辑和特殊情况。但是对代码进行测试，事情就会变得更加清晰。如果您在开始编码之前考虑测试边界条件以及它如何工作，您很可能会在逻辑中找到可以简化函数的模式。如果您考虑需要测试的错误条件，您将相应地构造您的函数。

#### 测试驱动开发

<a id="d24e21381"></a>
<a id="FNPTR-58"></a>
有一个编程流派说，鉴于预先考虑测试的所有好处，为什么不继续预先编写它们呢？他们实践所谓的测试驱动开发或 TDD。您还会看到这称为测试优先开发。[[58]](<44 Naming Things - naming.md#FOOTNOTE-58>)

<a id="d24e21420"></a>
TDD的基本周期是：

<a id="d24e21424"></a>
<a id="d24e21427"></a>
<a id="d24e21430"></a>
<a id="d24e21433"></a>
<a id="d24e21436"></a>
1. 决定您要添加的一小部分功能。
2. 编写一个测试，该测试一旦实现该功能就会通过。
3. 运行所有测试。验证唯一的失败是您刚刚编写的失败。
4. 编写使测试通过所需的最少量的代码，并验证测试现在是否可以正常运行。
5. 重构您的代码：看看是否有办法改进您刚刚编写的内容（测试或函数）。确保完成后测试仍然通过。

<a id="d24e21438"></a>
我们的想法是，这个周期应该非常短：只需几分钟，这样您就可以不断地编写测试，然后让它们发挥作用。

<a id="d24e21440"></a>
我们看到 TDD 对于刚开始测试的人来说有一个重大好处。如果您遵循 TDD 工作流程，您将保证您始终对代码进行测试。这意味着您将始终考虑您的测试。

<a id="d24e21442"></a>
然而，我们也看到人们成为 TDD 的奴隶。这体现在很多方面：

<a id="d24e21446"></a>
<a id="d24e21456"></a>
<a id="d24e21468"></a>
- 他们花费大量时间来确保始终具有 100% 的测试覆盖率。
- 他们有很多多余的测试。例如，在第一次编写类之前，许多 TDD 拥护者会首先编写一个仅引用类名称的失败测试。它失败了，然后他们编写一个空的类定义并且它通过了。但现在你的测试完全没有任何作用；您编写的下一个测试也将引用该类，因此这使得第一个测试变得不必要。如果以后类名发生变化，还有更多的东西需要改变。这只是一个简单的例子。
- 他们的设计往往从底部开始，逐步向上。 （参见[*自下而上与自上而下与您应该做的方式*](#sb-butd)。）

<a id="sb-butd"></a>
<a id="d24e21482"></a>
<a id="d24e21509"></a>
<a id="d24e21516"></a>
<a id="d24e21524"></a>
自下而上与自上而下与您应该做的方式

当计算机还很年轻、无忧无虑的时候，有两种设计流派：自上而下和自下而上。自上而下的人说，你应该从你试图解决的整体问题开始，然后将其分解为几个小部分。然后将它们分成更小的部分，依此类推，直到最终得到足够小的部分，可以用代码来表达。

自下而上的人构建代码就像建造房子一样。他们从底层开始，生成一层代码，为他们提供一些更接近他们试图解决的问题的抽象。然后他们添加另一层，具有更高级别的抽象。他们继续下去，直到最后一层成为解决问题的抽象层。 “就这样吧……”

这两所学校实际上都行不通，因为两者都忽略了软件开发最重要的方面之一：当我们开始时，我们不知道我们在做什么。自上而下的人认为他们可以预先表达整个需求：但他们不能。自下而上的人假设他们可以构建一个抽象列表，最终将他们带到一个顶层解决方案，但是当他们不知道自己要去哪里时，他们如何决定层的功能呢？

**提示 68：端到端构建，而不是自上而下或自下而上**

我们坚信，构建软件的唯一方法是渐进式。构建小型的端到端功能，边做边了解问题。在继续充实代码时应用所学知识，让客户参与每个步骤，并让他们指导整个过程。

<a id="d24e21536"></a>
无论如何都要练习 TDD。但是，如果您这样做，请不要忘记时不时地停下来看看大局。人们很容易被绿色的“测试通过”消息所诱惑，编写大量代码实际上并不能让您更接近解决方案。

### TDD：你需要知道你要去哪里

<a id="d24e21545"></a>
<a id="FNPTR-59"></a>
有一个老笑话问“你怎么吃大象？”妙语：“一次一口。”这个想法经常被吹捧为 TDD 的好处。当您无法理解整个问题时，请采取小步骤，一次测试一个。然而，这种方法可能会误导您，鼓励您专注于并不断完善简单的问题，而忽略编码的真正原因。一个有趣的例子发生在 2006 年，当时敏捷运动的领军人物 Ron Jeffries 发表了一系列博客文章，记录了他对 Sudoko 求解器的测试驱动编码。[[59]](<44 Naming Things - naming.md#FOOTNOTE-59>) 在发表了五篇文章后，他改进了底层板的表示，进行了多次重构，直到他对对象模型感到满意为止。但后来他放弃了这个项目。按顺序阅读博客文章是很有趣的，观察一个聪明的人如何会因细节而分心，而通过测试的光辉又会加剧这种情况。

<a id="d24e21555"></a>
<a id="FNPTR-60"></a>
作为对比，Peter Norvig 描述了一种替代方法[[60]](<44 Naming Things - naming.md#FOOTNOTE-60>)，这种方法在性质上感觉非常不同：他不是由测试驱动，而是从对传统上如何解决此类问题（使用约束传播）的基本了解开始，然后专注于改进他的算法。他用十几行代码解决了棋盘表示问题，这些代码直接源于他对符号的讨论。

<a id="d24e21564"></a>
测试绝对可以帮助推动开发。但是，就像每次开车一样，除非您心里有目的地，否则您最终可能会原地踏步。

### 返回代码

<a id="d24e21576"></a>
<a id="FNPTR-61"></a>
基于组件的开发长期以来一直是软件开发的崇高目标。[[61]](<44 Naming Things - naming.md#FOOTNOTE-61>) 这个想法是通用软件组件应该像组合常见集成电路 (IC) 一样容易地可用和组合。但只有当您使用的组件已知是可靠的，并且具有通用电压、互连标准、时序等时，这种方法才有效。

<a id="d24e21598"></a>
芯片设计用于测试——不仅在工厂、安装时进行测试，而且在部署时也在现场进行测试。更复杂的芯片和系统可能具有完整的内置自测试 (BI​​ST) 功能，可在内部运行一些基本级诊断，或者具有测试访问机制 (TAM)，可提供测试工具，允许外部环境提供激励并收集芯片的响应。

<a id="d24e21609"></a>
我们可以在软件中做同样的事情。与我们的硬件同事一样，我们需要从一开始就在软件中构建可测试性，并在尝试将它们连接在一起之前彻底测试每个部分。

### 单元测试

<a id="d24e21614"></a>
硬件的芯片级测试大致相当于软件中的单元测试——对每个模块单独进行测试，以验证其行为。一旦我们在受控（甚至是人为的）条件下对其进行了彻底的测试，我们就可以更好地了解模块在广阔的世界中将如何反应。

<a id="d24e21628"></a>
软件单元测试是执行模块的代码。通常，单元测试将建立某种人工环境，然后调用被测试模块中的例程。然后，它根据已知值或先前运行相同测试（回归测试）的结果检查返回的结果。

<a id="d24e21630"></a>
稍后，当我们将“软件 IC”组装成一个完整的系统时，我们将确信各个部分按预期工作，然后我们可以使用相同的单元测试设施来测试整个系统。我们在[*无情且持续的测试*](<../09 Pragmatic Projects/51 Pragmatic Starter Kit - starter_kit.md#testing>)中讨论这种对系统的大规模检查。

<a id="d24e21641"></a>
然而，在我们做到这一点之前，我们需要决定在单元级别测试什么。从历史上看，程序员在代码中添加一些随机数据，查看打印语句，然后将其称为测试过的。我们可以做得更好。

### 根据合同进行测试

<a id="d24e21648"></a>
我们喜欢将单元测试视为针对契约的测试（参见主题 23，[*按合同设计*](<../04 Pragmatic Paranoia/23 Design by Contract - dbc.md#dbc>)）。我们希望编写测试用例来确保给定单位履行其合同。这将告诉我们两件事：代码是否符合契约，以及契约是否意味着我们认为的意思。我们想要测试该模块是否在广泛的测试用例和边界条件下提供了它所承诺的功能。

<a id="d24e21669"></a>
这在实践中意味着什么？让我们从一个简单的数值示例开始：平方根例程。其书面合同很简单：

```
pre-conditions:
  argument >= 0;

post-conditions:
  ((result * result) - argument).abs
```

<a id="d24e21682"></a>
这告诉我们要测试什么：

<a id="d24e21686"></a>
<a id="d24e21689"></a>
<a id="d24e21692"></a>
- 传递一个否定参数并确保它被拒绝。
- 传入零参数以确保它被接受（这是边界值）。
- 传入零和最大可表达参数之间的值，并验证结果的平方与原始参数之间的差值小于参数的某个小部分 (epsilon)。

<a id="d24e21694"></a>
有了这个合同，并假设我们的例程会进行自己的前置条件和后置条件检查，我们就可以编写一个基本的测试脚本来执行平方根函数。

<a id="d24e21696"></a>
然后我们可以调用这个例程来测试我们的平方根函数：

```
assertWithinEpsilon(my_sqrt(0), 0)
assertWithinEpsilon(my_sqrt(2.0),   1.4142135624)
assertWithinEpsilon(my_sqrt(64.0),  8.0)
assertWithinEpsilon(my_sqrt(1.0e7), 3162.2776602)
assertRaisesException fn =>  my_sqrt(-4.0) end
```

<a id="d24e21716"></a>
这是一个非常简单的测试；在现实世界中，任何重要的模块都可能依赖于许多其他模块，那么我们如何着手测试组合呢？

<a id="d24e21718"></a>
假设我们有一个使用 DataFeed 和 LinearRegression 的模块 A。按照顺序，我们将测试：

1. DataFeed 的完整合同
2. LinearRegression 的完整合约
3. A的合约，依赖于其他合约但不直接暴露它们

<a id="d24e21746"></a>
这种类型的测试要求您首先测试模块的子组件。一旦子组件经过验证，就可以测试模块本身。

<a id="d24e21748"></a>
如果 DataFeed 和 LinearRegression 的测试通过，但 A 的测试失败，我们可以非常确定问题出在 A 中，或者问题出在 A 对这些子组件之一的使用中。这种技术是减少调试工作的好方法：我们可以快速集中于模块 A 内问题的可能根源，而不是浪费时间重新检查其子组件。

<a id="d24e21776"></a>
为什么我们要这么麻烦呢？最重要的是，我们希望避免制造一颗“定时炸弹”，即那些不被注意的东西，在项目后期的尴尬时刻爆炸。通过强调针对合同的测试，我们可以尽力避免尽可能多的下游灾难。

**技巧 69：为测试而设计**

### 临时测试

<a id="d24e21789"></a>
不要与“奇怪的黑客”混淆，临时测试是指我们手动运行 poke 代码。这可能像 console.log() 一样简单，也可能是在调试器、IDE 环境或 REPL 中交互式输入的一段代码。

<a id="d24e21809"></a>
在调试会话结束时，您需要正式化此临时测试。如果代码被破坏一次，它很可能会再次被破坏。不要直接丢弃您创建的测试；将其添加到现有的单元测试库中。

<a id="pg-test_window"></a>
### 构建测试窗口

<a id="d24e21814"></a>
即使是最好的测试集也不太可能发现所有错误；生产环境的潮湿、温暖的条件似乎让他们脱离了木制品。

<a id="d24e21827"></a>
这意味着您通常需要在部署软件后对其进行测试，并让真实世界的数据流经其血管。与电路板或芯片不同，我们在软件中没有测试引脚，但我们可以提供模块内部状态的各种视图，而无需使用调试器（这在生产应用程序中可能不方便或不可能）。

<a id="d24e21844"></a>
包含跟踪消息的日志文件就是这样一种机制。日志消息应采用常规、一致的格式；您可能希望自动解析它们以推断程序所采用的处理时间或逻辑路径。格式不良或不一致的诊断信息就像“溢出”一样，难以阅读且难以解析。

<a id="d24e21863"></a>
进入正在运行的代码的另一种机制是“热键”序列或魔术URL。当按下这个特定的按键组合，或者访问 URL 时，会弹出一个诊断控制窗口，其中包含状态消息等。这不是您通常会向最终用户透露的内容，但它对于帮助台来说非常方便。

<a id="d24e21882"></a>
更一般地说，您可以使用功能开关为特定用户或用户类别启用额外的诊断。

<a id="d24e21892"></a>
<a id="d24e21894"></a>
<a id="d24e21896"></a>
<a id="d24e21898"></a>
<a id="d24e21913"></a>
<a id="d24e21918"></a>
<a id="d24e21920"></a>
忏悔

我（戴夫）曾告诉人们我不再编写测试。我这样做的部分原因是为了动摇那些将测试变成宗教的人的信仰。我这样说的部分原因是它（在某种程度上）是正确的。

我已经编码了 45 年，并为其中的 30 多年编写了自动化测试。对测试的思考是我编码方式的一部分。感觉很舒服。我的性格坚持认为，当某件事开始让我感到舒服时，我应该转向其他事情。

在这种情况下，我决定停止编写测试几个月，看看它对我的代码做了什么。令我惊讶的是，答案是“不多”。所以我花了一些时间找出原因。

我相信答案是（对我来说）测试的大部分好处来自于思考测试及其对代码的影响。而且，在做了这么长时间之后，我可以在不实际编写测试的情况下进行这种思考。我的代码仍然可以测试；只是没有经过测试。

但这忽略了这样一个事实，即测试也是与其他开发人员沟通的一种方式，因此我现在确实对与其他人共享的代码或依赖于外部依赖项的特殊性的代码编写测试。

安迪说我不应该包含这个侧边栏。他担心这会诱使缺乏经验的开发人员不进行测试。这是我的妥协：

你应该写测试吗？是的。但当你已经这样做了 30 年之后，请随意尝试一下，看看对你有什么好处。

### 测试文化

<a id="d24e21925"></a>
您编写的所有软件都将经过测试（如果不是由您和您的团队进行测试，则由最终用户进行测试），因此您不妨计划对其进行彻底测试。稍微深思熟虑可以大大减少维护成本和帮助台呼叫。

<a id="d24e21939"></a>
你实际上只有几个选择：

- 首先测试
- 测试期间
- 从不测试

<a id="d24e21965"></a>
在大多数情况下，测试优先（包括测试驱动设计）可能是您的最佳选择，因为它可以确保测试的发生。但有时这并不方便或有用，因此编码期间测试可能是一个很好的后备，您可以编写一些代码，摆弄它，为其编写测试，然后继续进行下一步。最糟糕的选择通常被称为“稍后测试”，但你在开玩笑吗？ “稍后测试”实际上意味着“从不测试”。

<a id="d24e21977"></a>
测试文化意味着所有测试始终通过。忽略大量“总是失败”的测试会更容易忽略所有测试，恶性循环就开始了（参见主题 3，[*软件熵*](<../01 Pragmatic Philosophy/03 Software Entropy - no_broken_windows.md#no_broken_windows>)）。

<a id="d24e21994"></a>
像任何生产代码一样对待测试代码。保持其解耦、干净和健壮。不要依赖不可靠的东西（参见主题 38，[*巧合编程*](<38 Programming by Coincidence - coincidence.md#coincidence>)），比如 GUI 系统中小部件的绝对位置，或者服务器日志中的确切时间戳，或者错误消息的确切措辞。对这类事情的测试将导致脆弱的测试。

**提示 70：测试您的软件，否则您的用户将会**

<a id="d24e22028"></a>
毫无疑问，测试是编程的一部分。这不是留给其他部门或员工的事情。

<a id="d24e22030"></a>
测试、设计、编码——这都是编程。
