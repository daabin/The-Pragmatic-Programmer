## 主题 40. 重构

> 我看到周围一切的变化和衰败......
>
> H. F. Lyte，与我同在

<a id="d24e20835"></a>
随着程序的发展，有必要重新考虑早期的决策并修改部分代码。这个过程是完全自然的。代码需要不断发展；这不是一个静态的事情。

<a id="d24e20851"></a>
<a id="FNPTR-55"></a>
不幸的是，软件开发最常见的比喻是建筑施工。 Bertrand Meyer 的经典著作 [*面向对象的软件构造* [Mey97]](<../A2 Exercise Answers/README.md#d6040e783>) 使用术语“软件构造”，甚至您谦虚的作者也在 2000 年代初编辑了 IEEE 软件的软件构造专栏。[[55]](<44 Naming Things - naming.md#FOOTNOTE-55>)

<a id="d24e20870"></a>
但使用构造作为指导隐喻意味着以下步骤：

<a id="d24e20874"></a>
<a id="d24e20877"></a>
<a id="d24e20880"></a>
1. 建筑师绘制蓝图。
2. 承包商挖掘地基、建造上部结构、电线和铅锤，并进行收尾工作。
3. 租户们搬进来，从此过上了幸福的生活，并打电话给大楼维修人员来解决任何问题。

<a id="d24e20882"></a>
嗯，软件并不完全是这样工作的。与建筑相比，软件更像是园艺——它比混凝土更有机。您根据最初的计划和条件在花园里种植许多东西。有些会茁壮成长，有些则注定会成为堆肥。您可以相对移动植物，以利用光与影、风和雨的相互作用。过度生长的植物会被分裂或修剪，并且冲突的颜色可能会被转移到更美观的位置。你拔除杂草，为需要额外帮助的植物施肥。您不断监测花园的健康状况，并根据需要进行调整（土壤、植物、布局）。

<a id="d24e20889"></a>
商界人士对建筑的比喻很满意：它比园艺更科学，它是可重复的，有严格的管理报告层次结构，等等。但我们不是在建造摩天大楼——我们不受物理和现实世界界限的限制。

<a id="d24e20891"></a>
园艺比喻更接近软件开发的现实。也许某个例程已经变得太大，或者试图完成太多的事情——它需要被分成两部分。那些没有按计划进行的事情需要被除草或修剪。

<a id="d24e20893"></a>
重写、重新设计和重新架构代码统称为重组。但该活动的一部分已被实践为重构。

<a id="d24e20903"></a>
[*重构* [Fow19]](<../A2 Exercise Answers/README.md#d6040e418>) 由 Martin Fowler 定义为：

<a id="d24e20917"></a>
> 用于重组现有代码体的严格技术，
> 改变其内部结构而不改变其外部
> 行为。

<a id="d24e20919"></a>
该定义的关键部分是：

<a id="d24e20923"></a>
<a id="d24e20926"></a>
1. 活动是有纪律的，不是自由活动
2. 外在行为没有改变；现在不是添加功能的时候

<a id="d24e20928"></a>
重构并不是一种特殊的、隆重的、偶尔进行的活动，就像在整个花园里犁地以便重新种植一样。相反，重构是一项日常活动，采取低风险的小步骤，更像是除草和耙草。它不是对代码库进行免费的大规模重写，而是一种有针对性的精确方法，有助于保持代码易于更改。

<a id="d24e20934"></a>
为了保证外部行为没有改变，您需要良好的自动化单元测试来验证代码的行为。

### 你什么时候应该重构？

<a id="d24e20939"></a>
当你学到一些东西时，你就进行重构；当你对某件事的理解比去年、昨天、甚至十分钟前更好时。

<a id="d24e20945"></a>
也许您遇到了一个绊脚石，因为代码不再适合，或者您注意到两件事确实应该合并，或者任何其他事情让您觉得“错误”，请毫不犹豫地更改它。没有比现在更好的时间了。许多因素都可能导致代码符合重构条件：

<a id="d24e20954"></a>
<a id="d24e20968"></a>
<a id="d24e20980"></a>
<a id="d24e20989"></a>
<a id="d24e20998"></a>
<a id="d24e21008"></a>
重复：您发现违反了 DRY 原则。

非正交设计：您发现了一些可以变得更加正交的东西。

过时的知识：事情发生变化，需求发生变化，并且您对问题的了解增加。代码需要跟上。

用法：当系统在实际情况下被真人使用时，您会意识到某些功能现在比以前想象的更重要，而“必须具备”的功能可能并非如此。

性能：您需要将功能从系统的一个区域移动到另一区域以提高性能。

测试通过：是的。严重地。我们确实说过，重构应该是小规模的活动，并有良好的测试支持。因此，当您添加了少量代码并且通过了一项额外的测试时，您现在就有一个很好的机会深入研究并整理您刚刚编写的内容。

<a id="d24e21014"></a>
重构代码——移动功能并更新早期决策——实际上是一种痛苦管理的练习。让我们面对现实吧，更改源代码可能会非常痛苦：它正在工作，也许最好不要管它。许多开发人员不愿意进入并重新打开一段代码，只是因为它不太正确。

#### 现实世界的并发症

<a id="d24e21022"></a>
因此，你去找你的队友或客户说：“这段代码可以工作，但我还需要一周的时间来完全重构它。”

<a id="d24e21024"></a>
我们无法打印他们的回复。

<a id="d24e21026"></a>
时间压力经常被用作不重构的借口。但这个借口根本站不住脚：如果现在不进行重构，那么当有更多的依赖项需要考虑时，将来会花费更多的时间来解决问题。到时候会有更多的时间吗？没有。

<a id="d24e21042"></a>
您可能想用医学类比向其他人解释这一原则：将需要重构的代码视为“增长”。 Removing it requires invasive surgery.你现在就可以进去，趁它还小的时候把它拿出来。或者，你可以等待它生长和扩散，但随后将其去除会更昂贵且更危险。等待更长时间，你可能会完全失去病人。

**技巧 65：尽早重构，经常重构**

<a id="d24e21050"></a>
随着时间的推移，代码中的附带损害也可能同样致命（请参阅主题 3，[*软件熵*](<../01 Pragmatic Philosophy/03 Software Entropy - no_broken_windows.md#no_broken_windows>)）。与大多数事情一样，当问题很小时，重构会更容易完成，因为它是编码时的一项持续活动。您不应该需要“一周来重构”一段代码——这是一次全面的重写。如果这种程度的破坏是必要的，那么您很可能无法立即做到这一点。相反，请确保将其列入日程表中。确保受影响代码的用户知道该代码将被重写以及这可能会对他们产生怎样的影响。

### 你如何重构？

<a id="d24e21069"></a>
重构始于 Smalltalk 社区，当我们编写本书第一版时，重构刚刚开始获得更广泛的受众，这可能要归功于第一本关于重构的主要书籍（[*重构：改进现有代码的设计* [Fow19]](<../A2 Exercise Answers/README.md#d6040e418>)，现在是第二版）。

<a id="d24e21078"></a>
从本质上讲，重构就是重新设计。您或您团队中的其他人设计的任何内容都可以根据新的事实、更深入的理解、不断变化的需求等进行重新设计。但是，如果您继续疯狂地撕毁大量代码，您可能会发现自己的处境比开始时更糟糕。

<a id="d24e21089"></a>
<a id="FNPTR-56"></a>
显然，重构是一项需要缓慢、谨慎、谨慎地进行的活动。 Martin Fowler 提供了以下关于如何重构而不弊大于利的简单技巧：[[56]](<44 Naming Things - naming.md#FOOTNOTE-56>)

<a id="d24e21100"></a>
<a id="d24e21103"></a>
<a id="d24e21110"></a>
<a id="FNPTR-57"></a>
1. 不要尝试同时重构和添加功能。
2. 在开始重构之前，请确保您有良好的测试。尽可能频繁地运行测试。这样您就能很快知道您的更改是否破坏了任何内容。
3. 采取简短而深思熟虑的步骤：将字段从一个类移动到另一个类、拆分方法、重命名变量。重构通常涉及进行许多局部更改，从而导致更大规模的更改。如果您保持较小的步骤，并在每个步骤后进行测试，您将避免长时间的调试。[[57]](<44 Naming Things - naming.md#FOOTNOTE-57>)

<a id="d24e21149"></a>
<a id="d24e21166"></a>
自动重构

早在第一版中我们就指出，“这项技术尚未出现在 Smalltalk 世界之外，但这很可能会改变……”事实上，它确实做到了，因为许多 IDE 和大多数主流语言都可以使用自动重构。

这些 IDE 可以重命名变量和方法、将长例程拆分为较小的例程、自动传播所需的更改、拖放以帮助您移动代码等等。

<a id="d24e21168"></a>
我们将在主题 41 [*测试代码*](<41 Test to Code - test_to_build.md#test_to_build>) 中详细讨论此级别的测试，并在 [*无情且持续的测试*](<../09 Pragmatic Projects/51 Pragmatic Starter Kit - starter_kit.md#testing>) 中讨论更大规模的测试，但 Fowler 先生认为保持良好的回归测试是安全重构的关键。

<a id="d24e21174"></a>
如果您必须超越重构并最终更改外部行为或接口，那么故意破坏构建可能会有所帮助：此代码的旧客户端应该无法编译。这样您就会知道哪些内容需要更新。下次当您看到一段代码不完全符合其应有的样子时，请修复它。控制疼痛：如果现在很痛，但以后会更痛，你最好还是结束它。记住主题 3 [*软件熵*](<../01 Pragmatic Philosophy/03 Software Entropy - no_broken_windows.md#no_broken_windows>) 的教训：不要生活在破损的窗户中。
