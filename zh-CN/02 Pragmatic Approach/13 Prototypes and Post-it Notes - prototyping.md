## 主题 13. 原型与便利贴

<a id="d24e5260"></a>
许多行业使用原型来尝试特定的想法；原型制作比大规模生产便宜得多。例如，汽车制造商可能会为新车设计制造许多不同的原型。每一项都旨在测试汽车的特定方面——空气动力学、造型、结构特征等。老派人士可能​​会使用粘土模型进行风洞测试，也许轻木和胶带模型适合艺术部门，等等。不太浪漫的人会在电脑屏幕或虚拟现实中进行建模，从而进一步降低成本。通过这种方式，可以尝试有风险或不确定的元素，而无需承诺构建真实的项目。

<a id="d24e5271"></a>
我们以同样的方式构建软件原型，出于同样的原因——分析和暴露风险，并以大大降低的成本提供纠正的机会。与汽车制造商一样，我们可以针对原型来测试项目的一个或多个特定方面。

<a id="d24e5277"></a>
我们倾向于认为原型是基于代码的，但它们并不总是必须如此。像汽车制造商一样，我们可以用不同的材料构建原型。便利贴非常适合制作动态事物的原型，例如工作流程和应用程序逻辑。用户界面可以原型化为白板上的绘图、使用绘图程序或界面生成器绘制的非功能性模型。

<a id="d24e5279"></a>
原型的设计目的只是回答几个问题，因此它们比投入生产的应用程序开发起来更便宜、更快。代码可以忽略不重要的细节——目前对您来说不重要，但以后可能对用户非常重要。例如，如果您正在设计 UI 原型，则可能会得到不正确的结果或数据。另一方面，如果您只是研究计算或性能方面，则可能会遇到相当糟糕的 UI，甚至可能根本没有 UI。

<a id="d24e5285"></a>
但如果你发现自己处于一个不能放弃细节的环境中，那么你需要问问自己是否真的在构建原型。也许曳光弹式的开发在这种情况下更合适（参见主题 12，[*曳光弹*](<12 Tracer Bullets - tracer_bullets.md#tracer_bullets>)）。

### 原型化的东西

<a id="d24e5304"></a>
您可能会选择使用原型来研究哪些类型的事情？任何有风险的事情。任何以前没有尝试过的东西，或者对最终系统绝对重要的东西。任何未经证实的、实验性的或可疑的事情。任何你不舒服的事情。您可以制作原型：

- 建筑学
- 现有系统中的新功能
- 外部数据的结构或内容
- 第三方工具或组件
- 性能问题
- 用户界面设计

<a id="d24e5349"></a>
原型设计是一种学习经历。它的价值不在于产生的代码，而在于吸取的教训。这确实是原型设计的重点。

### 如何使用原型

<a id="d24e5364"></a>
构建原型时，哪些细节是可以忽略的？

<a id="d24e5371"></a>
<a id="d24e5379"></a>
<a id="d24e5387"></a>
<a id="d24e5395"></a>
正确性：您可以在适当的情况下使用虚拟数据。

完整性：原型可能仅在非常有限的意义上发挥作用，也许只有一项预选的输入数据和一个菜单项。

稳健性：错误检查可能不完整或完全缺失。如果偏离预定义的路径，原型可能会崩溃并燃烧，呈现出绚丽的烟火效果。没关系。

风格：原型代码不应该有太多注释或文档（尽管您可能会根据原型的经验生成大量文档）。

<a id="d24e5411"></a>
原型掩盖了细节，并专注于正在考虑的系统的特定方面，因此您可能希望使用高级脚本语言来实现它们 - 高于项目的其余部分（可能是 Python 或 Ruby 等语言），因为这些语言可能会妨碍您。您可以选择继续使用原型所使用的语言进行开发，也可以切换；毕竟，无论如何你都会扔掉原型。

<a id="d24e5422"></a>
要对用户界面进行原型设计，请使用可让您专注于外观和/或交互而无需担心代码或标记的工具。

<a id="d24e5433"></a>
脚本语言还可以很好地充当“粘合剂”，将低级部分组合成新的组合。使用这种方法，您可以快速将现有组件组装成新的配置，以了解其工作原理。

### 原型架构

<a id="d24e5438"></a>
许多原型都是为了对所考虑的整个系统进行建模而构建的。与曳光弹相反，原型系统中的各个模块都不需要具有特别的功能。事实上，您甚至可能不需要编写代码来构建原型架构 - 您可以使用便利贴或索引卡在白板上进行原型设计。您要寻找的是系统如何作为一个整体连接在一起，再次推迟细节。以下是您可能想要在架构原型中查找的一些特定区域：

- 主要领域的职责是否明确且适当？
- 主要组件之间的协作是否明确定义？
- 耦合是否最小化？
- 您能识别潜在的重复来源吗？
- 接口定义和约束是否可以接受？
- 每个模块是否都有执行期间所需数据的访问路径？它在需要时是否具有该访问权限？

<a id="d24e5508"></a>
最后一项往往会从原型设计经验中产生最大的惊喜和最有价值的结果。

### 如何不使用原型

<a id="d24e5516"></a>
在开始任何基于代码的原型设计之前，请确保每个人都明白您正在编写一次性代码。对于那些不知道它们只是原型的人来说，原型可能具有欺骗性的吸引力。你必须说得很清楚，这段代码是一次性的、不完整的、无法完成的。

<a id="d24e5525"></a>
演示原型的明显完整性很容易被误导，如果您没有设定正确的期望，项目发起人或管理层可能会坚持部署原型（或其后代）。提醒他们，您可以用轻木和胶带建造一辆很棒的新车原型，但您不会尝试在高峰时段驾驶它！

<a id="d24e5527"></a>
如果您认为在您的环境或文化中原型代码的目的很可能被误解，那么使用曳光弹方法可能会更好。您最终将获得一个坚实的框架，作为未来开发的基础。

<a id="d24e5538"></a>
正确使用原型可以通过在开发周期的早期识别和纠正潜在的问题点（此时修复错误既便宜又容易）来为您节省大量时间、金钱和痛苦。
