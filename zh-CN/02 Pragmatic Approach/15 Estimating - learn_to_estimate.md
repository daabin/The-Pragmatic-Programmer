## 主题 15. 估算

<a id="d24e6398"></a>
位于华盛顿特区的国会图书馆目前拥有约 75 TB 的在线数字信息。快的！通过 1Gbps 网络发送所有这些信息需要多长时间？一百万个姓名和地址需要多少存储空间？压缩 100Mb 的文本需要多长时间？交付您的项目需要几个月的时间？

<a id="d24e6409"></a>
在某种程度上，这些都是毫无意义的问题——它们都缺少信息。然而，只要您愿意估计，这些问题都可以得到答案。而且，在进行估算的过程中，您将更多地了解您的程序所处的世界。

<a id="d24e6411"></a>
通过学习估计，并将这种技能发展到对事物的大小有直观感觉的程度，你将能够表现出一种明显的神奇能力来确定其可行性。当有人说“我们将通过网络连接将备份发送到 S3”时，您将能够直观地知道这是否可行。当您编码时，您将能够知道哪些子系统需要优化以及哪些子系统可以保留。

**提示 23：估算以避免意外**

<a id="d24e6419"></a>
作为奖励，在本节末尾，我们将在有人要求您进行估算时提供唯一的正确答案。

### 多准确才算足够准确？

<a id="d24e6424"></a>
在某种程度上，所有答案都是估计。只是有些比其他更准确。因此，当有人要求您进行估算时，您必须问自己的第一个问题是您的答案将在什么背景下进行。他们需要高精度，还是正在寻找一个大概的数字？

<a id="d24e6435"></a>
估算的有趣之处之一是您使用的单位会对结果的解释产生影响。如果你说某件事需要大约 130 个工作日，那么人们会期望它会非常接近。然而，如果你说“哦，大约六个月”，那么他们就知道从现在起五到七个月内的任何时间都会寻找它。这两个数字代表相同的持续时间，但“130 天”可能意味着比您想象的更准确。我们建议您按如下方式调整时间估计：

| | 期间 | 报价估计在 |
| --- | --- | --- |
| | 1–15 天 | 天 |
| | 3-6周 | 周数 |
| | 8–20 周 | 几个月 |
| | 20+周 | 在给出估计之前要仔细考虑 |

<a id="d24e6484"></a>
因此，如果在完成所有必要的工作后，您决定项目需要 125 个工作日（25 周），您可能需要提供“大约六个月”的估计。

<a id="d24e6486"></a>
相同的概念适用于任何数量的估计：选择答案的单位以反映您想要传达的准确性。

### 估算从何而来？

<a id="d24e6491"></a>
所有估计均基于问题模型。但在我们深入了解构建模型的技术之前，我们必须提到一个总是能给出良好答案的基本估计技巧：询问已经做过这件事的人。在您过于致力于模型构建之前，请先寻找过去遇到过类似情况的人。看看他们的问题是如何解决的。您不太可能找到完全匹配的内容，但您会惊讶地发现您可以成功借鉴他人的经验多少次。

#### 了解所问的内容

<a id="d24e6503"></a>
任何估算练习的第一部分都是了解所要求的内容。除了上面讨论的准确性问题之外，您还需要掌握域的范围。这通常隐含在问题中，但您需要养成在开始猜测之前考虑范围的习惯。通常，您选择的范围将构成您给出的答案的一部分：“假设没有交通事故并且车里有汽油，我应该在 20 分钟内到达那里。”

#### 构建系统模型

<a id="d24e6512"></a>
这是估算的有趣部分。根据您对所提出问题的理解，建立一个粗略且现成的基本心理模型。如果您要估计响应时间，您的模型可能涉及服务器和某种到达流量。对于项目，模型可能是您的组织在开发过程中使用的步骤，以及系统如何实施的非常粗略的描述。

<a id="d24e6514"></a>
从长远来看，模型构建既具有创造性又很有用。通常，构建模型的过程会导致表面上不明显的潜在模式和过程的发现。你甚至可能想重新审视原来的问题：“你要求对执行 X 进行估计。然而，看起来 Y（X 的变体）可以在大约一半的时间内完成，而且你只失去一个功能。”

<a id="d24e6525"></a>
构建模型会给估计过程带来不准确性。这是必然的，也是有益的。您需要牺牲模型的简单性来换取准确性。加倍模型上的努力可能只会略微提高准确性。您的经验会告诉您何时停止精炼。

#### 将模型分解为组件

<a id="d24e6534"></a>
一旦有了模型，您就可以将其分解为组件。您需要发现描述这些组件如何交互的数学规则。有时，组件会贡献一个添加到结果中的值。一些组件可能提供倍增因子，而其他组件可能更复杂（例如模拟流量到达节点的组件）。

<a id="d24e6538"></a>
您会发现每个组件通常都有一些参数，这些参数会影响它对整个模型的贡献。在此阶段，只需识别每个参数即可。

#### 为每个参数指定一个值

<a id="d24e6543"></a>
一旦分解了参数，您就可以仔细检查并为每个参数分配一个值。您预计会在此步骤中引入一些错误。诀窍是找出哪些参数对结果影响最大，并集中精力使它们正确。通常，其值添加到结果中的参数不如相乘或相除的参数重要。线路速度加倍可能会使一小时内接收的数据量加倍，而增加 5 毫秒的传输延迟不会产生明显影响。

<a id="d24e6554"></a>
您应该有一个合理的方法来计算这些关键参数。对于排队的例子，你可能想测量现有系统的实际交易到达率，或者找一个类似的系统来测量。同样，您可以测量当前处理请求所需的时间，或者使用本节中描述的技术进行估计。事实上，您经常会发现自己的估计基于其他子估计。这就是你犯最大错误的地方。

#### 计算答案

<a id="d24e6559"></a>
只有在最简单的情况下，估计才会有单一答案。您可能会很高兴地说“我可以在 15 分钟内步行穿过城镇的五个街区。”然而，随着系统变得更加复杂，您将需要对冲您的答案。运行多次计算，改变关键参数的值，直到找出哪些参数真正驱动模型。电子表格可以提供很大帮助。然后根据这些参数来表达你的答案。 “如果系统配备 SSD 和 32GB 内存，响应时间大约为四分之三秒；如果系统配备 16GB 内存，则响应时间为一秒。” （请注意“四分之三秒”与 750 毫秒所传达的准确度不同。）

<a id="d24e6561"></a>
在计算阶段，你会得到看起来很奇怪的答案。不要太快地解雇他们。如果你的算术是正确的，那么你对问题或模型的理解可能是错误的。这是有价值的信息。

#### 记录你的估算能力

<a id="d24e6573"></a>
我们认为记录您的估计是个好主意，这样您就可以看到您的估计有多接近。如果总体估计涉及计算子估计，也请跟踪这些。通常你会发现你的估计相当不错——事实上，过了一段时间，你就会开始期待这一点。

<a id="d24e6579"></a>
当估计结果错误时，不要只是耸耸肩走开——找出原因。也许您选择的一些参数与问题的实际情况不相符。也许你的模型是错误的。无论原因是什么，请花一些时间来弄清楚发生了什么。如果你这样做，你的下一个估计会更好。

<a id="sec-iterative"></a>
### 估算项目进度

<a id="d24e6584"></a>
通常，您会被要求估计某件事需要多长时间。如果这个“东西”很复杂，估计就很难进行。在本节中，我们将研究两种减少不确定性的技术。

#### 绘制导弹

<a id="d24e6589"></a>
<a id="d24e6597"></a>
“粉刷房子需要多长时间？”

<a id="d24e6600"></a>
“好吧，如果一切顺利，而且这种涂料具有他们声称的覆盖范围，那么时间可能只有 10 小时。但这不太可能：我猜更现实的数字应该接近 18 小时。当然，如果天气变坏，时间可能会延长到 30 小时或更长。”

<a id="d24e6603"></a>
这就是人们在现实世界中的估计。不是用一个数字（除非你强迫他们给你一个），而是用一系列场景。

<a id="d24e6605"></a>
当美国海军需要规划北极星潜艇项目时，他们采用了这种估算方式，采用了一种被称为项目评估审查技术（PERT）的方法。

<a id="d24e6613"></a>
每个 PERT 任务都有一个乐观估计、一个最有可能估计和一个悲观估计。这些任务被安排到一个依赖网络中，然后您使用一些简单的统计数据来确定整个项目可能的最佳和最差时间。

<a id="d24e6624"></a>
使用这样的一系列值是避免估计错误的最常见原因之一的好方法：因为不确定而填充数字。相反，PERT 背后的统计数据会为您分散不确定性，让您更好地估计整个项目。

<a id="d24e6626"></a>
然而，我们对此并不热衷。人们倾向于制作一个项目中所有任务的墙壁大小的图表，并且隐含地相信，仅仅因为他们使用了公式，他们就有了准确的估计。他们很可能不会这样做，因为他们以前从未这样做过。

#### 吃掉大象

<a id="d24e6634"></a>
我们发现，确定项目时间表的唯一方法通常是获得同一项目的经验。如果您练习增量开发，并使用非常薄的功能片段重复以下步骤，那么这不一定是一个悖论：

- 检查要求
- 分析风险（并尽早确定风险最高的项目的优先级）
- 设计、实施、集成
- 与用户验证

<a id="d24e6658"></a>
最初，您可能对需要多少次迭代或迭代需要多长时间只有一个模糊的概念。有些方法要求您将其确定为初始计划的一部分；然而，对于除了最琐碎的项目之外的所有项目来说，这是一个错误。除非您正在使用相同的团队和相同的技术来开发与以前的应用程序类似的应用程序，否则您只是在猜测。

<a id="d24e6660"></a>
因此，您完成了初始功能的编码和测试，并将其标记为第一次迭代的结束。根据该经验，您可以完善对迭代次数以及每次迭代中可以包含的内容的初步猜测。每次改进都变得越来越好，对日程安排的信心也随之增强。这种估计通常是在每个迭代周期结束时团队评审期间完成的。

<a id="d24e6666"></a>
这也是老笑话所说的“吃大象”：一次咬一口。

**提示 24：用代码迭代时间表**

<a id="d24e6674"></a>
这可能不受管理层欢迎，他们通常在项目开始之前就想要一个单一的、固定的数字。您必须帮助他们了解团队、他们的生产力和环境将决定时间表。通过将其形式化，并在每次迭代中细化计划，您将为他们提供最准确的计划估计。

### 当被要求估价时该怎么说

<a id="d24e6679"></a>
你说：“我会回复你的。”

<a id="d24e6683"></a>
如果您放慢进程并花一些时间完成我们在本节中描述的步骤，您几乎总是会得到更好的结果。咖啡机给出的估计（就像咖啡一样）会回来困扰你。
