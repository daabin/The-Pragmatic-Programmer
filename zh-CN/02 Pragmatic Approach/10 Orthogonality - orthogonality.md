<a id="orthogonality"></a>
## 主题 10. 正交性

<a id="d24e4175"></a>
如果您想要生产易于设计、构建、测试和扩展的系统，正交性是一个关键概念。然而，正交性的概念很少被直接教授。通常，它是您学习的各种其他方法和技术的隐含特征。这是一个错误。一旦您学会直接应用正交性原理，您就会注意到您所生产的系统的质量立即得到改善。

### 什么是正交性？

<a id="d24e4193"></a>
![A graph is shown at a different viewpoint. The horizontal axis represents east and the vertical axis represents north. Line 1 is drawn parallel to the vertical axis and line 2 is drawn parallel to the horizontal axis.](https://panzhongxian.cn/images/the-pragmatic-programmer/orthogonality.png)

<a id="d24e4194"></a>
“正交”是借用几何学的术语。如果两条线以直角相交，例如图上的轴，则它们是正交的。用向量术语来说，这两条线是独立的。当图上的数字 1 向北移动时，它不会改变它向东或向西移动的距离。数字 2 向东移动，但不向北或向南移动。

<a id="d24e4199"></a>
在计算中，这个术语已经意味着一种独立或解耦。如果一个事物的变化不影响其他事物，则两个或多个事物是正交的。在设计良好的系统中，数据库代码将与用户界面正交：您可以在不影响数据库的情况下更改界面，并且可以在不更改界面的情况下交换数据库。

<a id="d24e4201"></a>
在我们了解正交系统的优点之前，让我们首先看一下非正交系统。

#### 非正交系统

<a id="d24e4206"></a>
当你乘坐直升飞机游览大峡谷时，飞行员犯了明显的错误，午餐吃鱼，突然呻吟并晕倒。幸运的是，他让你在离地 100 英尺的高空盘旋。

<a id="d24e4208"></a>
幸运的是，您前一天晚上阅读了有关直升机的维基百科页面。您知道直升机有四个基本控制装置。循环杆是你右手拿着的棍子。移动它，直升机就会向相应的方向移动。您的左手握着集体变桨杆。拉起它，你就会增加所有叶片的螺距，从而产生升力。变桨杆的末端是油门。最后，你有两个脚踏板，它们可以改变尾桨推力的大小，从而帮助直升机转动。

<a id="d24e4222"></a>
“简单！”你想。 “轻轻降低集体变桨杆，你就会优雅地降落到地面，英雄。”然而，当你尝试过之后，你就会发现生活并没有那么简单。直升机的机头下降，你开始向左盘旋下降。突然间，您发现您正在驾驶的系统中，每个控制输入都会产生辅助效果。降低左手操纵杆，您需要向右手操纵杆添加补偿性向后移动并踩下右踏板。但随后这些更改中的每一个都会再次影响所有其他控件。突然之间，您就需要处理一个极其复杂的系统，其中的每一个变化都会影响所有其他输入。你的工作量是惊人的：你的手和脚不断移动，试图平衡所有相互作用的力量。

<a id="d24e4224"></a>
直升机控制显然不是正交的。

### 正交性的好处

<a id="d24e4229"></a>
正如直升机的例子所示，非正交系统本质上更难以改变和控制。当任何系统的组件高度相互依赖时，就不存在本地修复之类的东西。

**技巧 17：消除不相关事物之间的影响**

<a id="d24e4241"></a>
我们希望设计独立的组件：独立且具有单一、明确的目的（Yourdon 和 Constantine 在 [*结构化设计：计算机程序和系统设计学科的基础知识* [YC79]](<../A2 Exercise Answers/README.md#d6040e1054>) 中称之为内聚）。当组件彼此隔离时，您知道可以更改其中一个而不必担心其余组件。只要不更改该组件的外部接口，您就可以确信不会引起波及整个系统的问题。

<a id="d24e4254"></a>
如果您编写正交系统，您将获得两个主要好处：提高生产力和降低风险。

#### 提高生产力

<a id="d24e4261"></a>
<a id="d24e4283"></a>
<a id="d24e4295"></a>
- 更改是本地化的，因此减少了开发时间和测试时间。编写相对较小的独立组件比编写单个大代码块更容易。简单的组件可以被设计、编码、测试，然后被遗忘——添加新代码时无需不断更改现有代码。
- 正交方法还可以促进重用。如果组件具有特定的、明确定义的职责，那么它们可以以原始实现者未预见到的方式与新组件组合。系统耦合越松散，重新配置和重新设计就越容易。
- 当您组合正交组件时，生产力会得到相当微妙的提高。假设一个组件执行 $ M $ 种不同的操作，而另一个组件执行 $ N $ 种操作。如果它们是正交的并且将它们组合起来，则结果会执行 $ M \times N $ 件事。但是，如果两个分量不正交，就会出现重叠，结果就会少一些。通过组合正交组件，您可以在每单位努力中获得更多功能。

#### 降低风险

<a id="d24e4306"></a>
正交方法可以降低任何开发中固有的风险。

<a id="d24e4314"></a>
<a id="d24e4321"></a>
<a id="d24e4324"></a>
<a id="d24e4331"></a>
- 有病的代码部分被隔离。如果某个模块出现问题，则不太可能将症状传播到系统的其他部分。将其切掉并移植到新的、健康的东西中也更容易。
- 由此产生的系统不那么脆弱。对特定区域进行小的更改和修复，您产生的任何问题都将仅限于该区域。
- 正交系统可能会得到更好的测试，因为在其组件上设计和运行测试会更容易。
- 您不会与特定供应商、产品或平台紧密联系，因为这些第三方组件的接口将被隔离到整个开发的较小部分。

<a id="d24e4337"></a>
让我们看看可以将正交原理应用到您的工作中的一些方法。

### 设计

<a id="d24e4342"></a>
大多数开发人员都熟悉设计正交系统的需要，尽管他们可能会使用模块化、基于组件和分层等词语来描述该过程。系统应该由一组协作模块组成，每个模块独立于其他模块实现功能。有时，这些组件被组织成层，每个层提供一个抽象级别。这种分层方法是设计正交系统的有效方法。由于每一层仅使用其下层提供的抽象，因此您可以非常灵活地更改底层实现，而不会影响代码。分层还可以降低模块之间依赖关系失控的风险。您经常会看到用图表表示的分层：

<a id="d24e4357"></a>
<a id="alayer-diagram"></a>
![Address representation is shown.](https://panzhongxian.cn/images/the-pragmatic-programmer/layer-diagram.png)

图中显示了地址表示。第一层是用户界面。第二层分为三个部分：数据库访问、授权和业务逻辑。第三层代表应用程序框架，其中有一个部分：标准库。最后一部分代表容器服务。

<a id="d24e4358"></a>
<a id="FNPTR-16"></a>
正交设计有一个简单的测试。规划好组件后，问问自己：如果我大幅改变特定功能背后的需求，有多少模块会受到影响？在正交系统中，答案应该是“一个”。[[16]](<15 Estimating - learn_to_estimate.md#FOOTNOTE-16>) 在 GUI 面板上移动按钮不应要求更改数据库架构。添加上下文相关帮助不应更改计费子系统。

<a id="d24e4367"></a>
让我们考虑一个用于监视和控制供热厂的复杂系统。最初的需求需要图形用户界面，但需求发生了变化，添加了一个移动界面，让工程师可以监控关键值。在正交设计的系统中，您只需更改与用户界面相关的模块即可处理此问题：控制工厂的底层逻辑将保持不变。事实上，如果您仔细构建系统，您应该能够使用相同的底层代码库支持这两个接口。

<a id="d24e4369"></a>
还要问问自己，您的设计与现实世界的变化的脱钩程度如何。您是否使用电话号码作为客户标识符？当电话公司重新分配区号时会发生什么？邮政编码、社会安全号码或政府身份证、电子邮件地址和域名都是您无法控制的外部标识符，并且可能因任何原因随时更改。不要依赖你无法控制的事物的特性。

### 工具包和库

<a id="d24e4376"></a>
在引入第三方工具包和库时，请小心保持系统的正交性。明智地选择您的技术。

<a id="d24e4387"></a>
当您引入一个工具包（甚至是团队其他成员的库）时，问问自己它是否对您的代码施加了不应该存在的更改。如果对象持久化方案是透明的，那么它就是正交的。如果它要求您以特殊方式创建或访问对象，那么它就不是。将这些细节与代码隔离还有一个额外的好处，那就是将来更容易更换供应商。

<a id="d24e4389"></a>
Enterprise Java Beans (EJB) 系统是正交性的一个有趣的例子。在大多数面向事务的系统中，应用程序代码必须描述每个事务的开始和结束。使用 EJB，此信息在执行工作的方法之外以声明方式表示为注释。相同的应用程序代码可以在不同的 EJB 事务环境中运行，无需进行任何更改。

<a id="d24e4396"></a>
在某种程度上，EJB 是装饰器模式的一个示例：向事物添加功能而不更改它们。这种编程风格几乎可以用于所有编程语言，并且不一定需要框架或库。编程时只需要一点纪律。

### 编码

<a id="d24e4408"></a>
每次编写代码时，您都会面临降低应用程序正交性的风险。除非您不仅不断监控正在做的事情，而且还监控应用程序的更大上下文，否则您可能会无意中重复其他模块中的功能，或者两次表达现有知识。

<a id="d24e4410"></a>
您可以使用多种技术来保持正交性：

<a id="d24e4416"></a>
<a id="d24e4438"></a>
<a id="d24e4453"></a>
<a id="d24e4474"></a>
保持代码解耦：编写害羞的代码 - 模块不会向其他模块透露任何不必要的内容，并且不依赖于其他模块的实现。尝试一下我们在主题 28 [*解耦*](<../05 Bend or Break/28 Decoupling - coupling.md#coupling>) 中讨论的德墨忒耳定律。如果您需要更改对象的状态，请让该对象为您执行此操作。这样，您的代码就可以与其他代码的实现保持隔离，并增加保持正交的机会。

避免全局数据：每次代码引用全局数据时，它都会将自己绑定到共享该数据的其他组件中。即使您只想读取的全局变量也可能会导致麻烦（例如，如果您突然需要将代码更改为多线程）。一般来说，如果您将任何所需的上下文显式传递到模块中，您的代码会更容易理解和维护。在面向对象的应用程序中，上下文通常作为参数传递给对象的构造函数。在其他代码中，您可以创建包含上下文的结构并传递对它们的引用。 ：[*设计模式：可重用面向对象软件的元素* [GHJV95]](<../A2 Exercise Answers/README.md#d6040e452>)中的单例模式是一种确保特定类的对象只有一个实例的方法。许多人将这些单例对象用作一种全局变量（特别是在 Java 等不支持全局概念的语言中）。小心单例——它们也可能导致不必要的链接。

避免类似的函数：通常，您会遇到一组看起来相似的函数 - 也许它们在开头和结尾共享公共代码，但每个函数都有不同的中心算法。重复代码是结构问题的症状。查看设计模式中的策略模式以获得更好的实现。

<a id="d24e4496"></a>
养成不断批评代码的习惯。寻找任何机会对其进行重组，以改善其结构和正交性。这个过程称为重构，它非常重要，因此我们专门专门用一节来介绍它（请参阅主题 40，[*重构*](<../07 While Coding/40 Refactoring - refactor.md#refactor>)）。

### 测试

<a id="d24e4510"></a>
正交设计和实现的系统更容易测试。由于系统组件之间的交互是形式化且有限的，因此可以在单个模块级别执行更多的系统测试。这是个好消息，因为模块级（或单元）测试比集成测试更容易指定和执行。事实上，我们建议将这些测试作为常规构建过程的一部分自动执行（请参阅主题 41，[*测试代码*](<../07 While Coding/41 Test to Code - test_to_build.md#test_to_build>)）。

<a id="d24e4523"></a>
编写单元测试本身就是一个有趣的正交性测试。构建和运行单元测试需要什么？您是否必须导入大部分系统代码的其余部分？如果是这样，您就发现了一个与系统其余部分没有很好解耦的模块。

<a id="d24e4525"></a>
错误修复也是评估整个系统正交性的好时机。当您遇到问题时，评估修复的本地化程度。您只更改一个模块，还是将更改分散到整个系统？当你做出改变时，它会解决所有问题，还是会神秘地出现其他问题？这是实施自动化的好机会。如果您使用版本控制系统（阅读主题 19，[*版本控制*](<../03 Basic Tools/19 Version Control - version_control.md#version_control>) 后您将使用），则在测试后重新签入代码时标记错误修复。然后，您可以运行每月报告，分析受每个错误修复影响的源文件数量的趋势。

### 文档

<a id="d24e4541"></a>
<a id="FNPTR-17"></a>
也许令人惊讶的是，正交性也适用于文档。轴是内容和呈现。有了真正的正交文档，您应该能够在不更改内容的情况下显着改变外观。文字处理器提供了有用的样式表和宏。我们个人更喜欢使用标记系统，例如 Markdown：在编写时，我们只关注内容，并将演示文稿留给我们用来渲染它的任何工具。[[17]](<15 Estimating - learn_to_estimate.md#FOOTNOTE-17>)

### 正交生活

<a id="d24e4564"></a>
正交性与[DRY原理](<09 DRY - The Evils of Duplication - dry.md#dry>)密切相关。使用DRY，您希望最大限度地减少系统内的重复，而使用正交性，您可以减少系统组件之间的相互依赖性。这可能是一个笨拙的词，但是如果你使用正交原则，与DRY原则紧密结合，你会发现你开发的系统更灵活，更容易理解，并且更容易调试、测试和维护。

<a id="d24e4577"></a>
如果你参与的项目中，人们拼命努力做出改变，而每一次改变似乎都会导致其他四件事出错，请记住直升机的噩梦。该项目可能不是正交设计和编码的。是时候重构了。

面向对象语言和函数式语言之间的正交性有什么区别？这些差异是语言本身固有的，还是只是人们使用语言的方式所固有的？
