## 主题 11. 可逆性

> 如果你只有一个想法，那么没有什么比它更危险的了。
>
> 埃米尔-奥古斯特·沙蒂埃（阿兰），《宗教提案》，1938 年

<a id="d24e4780"></a>
工程师更喜欢简单、单一的问题解决方案。数学测试可以让你充满信心地宣布$ x = 2 $，这比关于法国大革命的无数原因的模糊而热情的文章要舒服得多。管理层倾向于同意工程师的观点：单一、简单的答案非常适合电子表格和项目计划。

<a id="d24e4796"></a>
要是现实世界能够合作就好了！不幸的是，虽然今天 $ x $ 是 $2$，但明天可能需要 $5$，下周需要 $3$。没有什么是永远的——如果你严重依赖某个事实，你几乎可以保证它会改变。

<a id="d24e4813"></a>
总是有不止一种方法来实现某件事，并且通常有不止一个供应商可以提供第三方产品。如果你在参与一个项目时受到“只有一种方法可以实现”的短视观念的阻碍，那么你可能会遇到不愉快的意外。随着未来的展开，许多项目团队被迫睁开眼睛：

<a id="d24e4823"></a>
> “但是你说过我们会使用数据库 XYZ！我们已经完成了 85% 的编码
> 项目，我们现在不能改变！”程序员
> 抗议道。 “抱歉，我们公司决定标准化
> 而是使用数据库 PDQ——适用于所有项目。它不在我手中。
> 我们只需要重新编码。周末大家都会加班
> 直至另行通知。”

<a id="d24e4825"></a>
改变不必那么严厉，甚至不必那么直接。但随着时间的推移和项目的进展，你可能会发现自己陷入了一个难以为继的境地。对于每一个关键决策，项目团队都会致力于实现一个更小的目标——一个具有更少选择的更窄的现实版本。

<a id="d24e4827"></a>
<a id="FNPTR-18"></a>
当做出许多关键决定时，目标变得如此之小，以至于如果它移动，或者风向改变，或者东京的蝴蝶扇动翅膀，你就会错过。[[18]](<15 Estimating - learn_to_estimate.md#FOOTNOTE-18>) 而且你可能会错过很多。

<a id="d24e4835"></a>
问题是关键决策不容易逆转。

<a id="d24e4837"></a>
一旦您决定使用该供应商的数据库，或该架构模式，或某种部署模型，您就必须采取无法撤消的行动方案，除非付出巨大的代价。

### 可逆性

<a id="d24e4846"></a>
本书中的许多主题都旨在开发灵活、适应性强的软件。通过坚持他们的建议（尤其是 [DRY原理](<09 DRY - The Evils of Duplication - dry.md#dry>)、[解耦](<../05 Bend or Break/28 Decoupling - coupling.md#coupling>) 和 [外部配置](<../05 Bend or Break/32 Configuration - configuration.md#configuration>) 的使用），我们不必做出那么多关键的、不可逆转的决定。这是一件好事，因为我们并不总是在第一次就做出最好的决定。我们致力于某种技术，却发现我们无法雇用足够的具有必要技能的人员。我们在某个第三方供应商被竞争对手收购之前锁定他们。需求、用户和硬件的变化速度比我们开发软件的速度还要快。

<a id="d24e4857"></a>
假设您在项目早期决定使用供应商 A 的关系数据库。很久以后，在性能测试期间，您发现该数据库太慢，但供应商 B 的文档数据库速度更快。对于大多数传统项目来说，你会运气不佳。大多数时候，对第三方产品的调用在整个代码中纠缠在一起。但是，如果您真正将数据库的概念抽象出来，使其仅提供持久性作为服务，那么您就可以灵活地在中途更换马匹。

<a id="d24e4862"></a>
同样，假设该项目一开始是基于浏览器的应用程序，但在游戏后期，营销人员决定他们真正想要的是移动应用程序。这对你来说有多难？在理想的情况下，它不会对您产生太大影响，至少在服务器端是如此。您将删除一些 HTML 渲染并将其替换为 API。

<a id="d24e4864"></a>
错误在于假设任何决定都是一成不变的，并且没有为可能出现的意外情况做好准备。不要把决定刻在石头上，而应该把它们想象成写在海滩的沙子上。巨浪随时可能袭来，将他们淹没。

**提示 18：没有最终决定**

### 灵活的架构

<a id="d24e4880"></a>
虽然许多人试图保持代码的灵活性，但您还需要考虑在架构、部署和供应商集成方面保持灵活性。

<a id="d24e4899"></a>
我们是在 2019 年写这篇文章的。自世纪之交以来，我们已经看到了以下“最佳实践”服务器端架构：

- 一大块铁
- 大铁联合会
- 商用硬件的负载平衡集群
- 运行应用程序的基于云的虚拟机
- 基于云的虚拟机运行服务
- 上述的容器化版本
- 云支持的无服务器应用程序
- 并且，不可避免地，在某些任务中明显会回归到大块铁

<a id="d24e4926"></a>
继续将最新、最流行的时尚添加到这个列表中，然后怀着敬畏之心看待它：任何事情都能奏效，这都是一个奇迹。

<a id="d24e4928"></a>
您如何规划这种架构的波动性？你不能。

<a id="d24e4930"></a>
你能做的就是让它变得容易改变。将第三方 API 隐藏在您自己的抽象层后面。将代码分解为组件：即使您最终将它们部署在单个大型服务器上，这种方法也比采用整体应用程序并将其拆分要容易得多。 （我们有伤疤来证明这一点。）

<a id="d24e4941"></a>
而且，尽管这并不是一个可逆性问题，但还是有最后一条建议。

**提示 19：放弃追随时尚**

<a id="d24e4953"></a>
没有人知道未来会怎样，尤其是我们！因此，让你的代码能够摇滚起来：可以的时候“摇滚”，必须的时候全力以赴。

### 挑战

<a id="d24e4985"></a>
<a id="d24e4994"></a>
<a id="d24e5002"></a>
<a id="d24e5004"></a>
<a id="d24e5006"></a>
- 是时候和薛定谔的猫一起了解一下量子力学了。

假设你有一只猫在一个封闭的盒子里，还有一个放射性粒子。该粒子恰好有 50% 的几率裂变成两半。如果这样做，猫就会被杀死。如果没有的话，猫就没事了。那么，猫是死是活呢？根据薛定谔的说法，正确答案是两者（至少在盒子保持关闭状态时）。每当发生有两种可能结果的亚核反应时，宇宙就会被克隆。在其中一个事件发生了，在另一个事件中却没有发生。猫在一个宇宙中活着，在另一个宇宙中死了。只有当你打开盒子时，你才知道你身处哪个宇宙。

难怪未来的编码是困难的。

但是，可以将代码演化想象为装满薛定谔的猫的盒子：每个决定都会导致未来的不同版本。您的代码可以支持多少种可能的未来？哪些可能性更大？到时候支持他们会有多困难？

你敢打开盒子吗？
