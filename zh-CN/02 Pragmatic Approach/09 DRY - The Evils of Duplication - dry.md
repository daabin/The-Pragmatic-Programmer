## 主题 9. DRY——重复的弊端

<a id="d24e2866"></a>
向计算机提供两个相互矛盾的知识是詹姆斯·T·柯克船长最喜欢的方式来禁用掠夺性的人工智能。不幸的是，同样的原则也可以有效地降低你的代码。

<a id="d24e2880"></a>
作为程序员，我们收集、组织、维护和利用知识。我们在规范中记录知识，在运行代码中使其活跃起来，并使用它来提供测试期间所需的检查。

<a id="d24e2882"></a>
不幸的是，知识并不稳定。它变化——通常很快。在与客户会面后，您对需求的理解可能会发生变化。政府改变了法规，一些商业逻辑已经过时。测试可能表明所选算法不起作用。所有这些不稳定性意味着我们将大部分时间花费在维护模式上，重新组织和重新表达系统中的知识。

<a id="d24e2884"></a>
大多数人认为维护是在应用程序发布时开始的，维护意味着修复错误和增强功能。我们认为这些人是错误的。程序员始终处于维护模式。我们的理解每天都在变化。当我们专注于该项目时，新的需求会出现，现有的需求也会不断发展。也许环境改变了。无论出于何种原因，维护都不是一项独立的活动，而是整个开发过程的例行组成部分。

<a id="d24e2900"></a>
当我们进行维护时，我们必须找到并改变事物的表示——那些嵌入在应用程序中的知识胶囊。问题在于，我们开发的规范、流程和程序中的知识很容易重复，当我们这样做时，我们就会引发维护噩梦——一场在应用程序发布之前就开始的噩梦。

<a id="d24e2902"></a>
我们认为可靠地开发软件并使我们的开发更易于理解和维护的唯一方法是遵循我们所说的 DRY 原则：

<a id="pg-dry"></a>
每一条知识在系统中都必须有一个单一的、明确的、权威的表示。

<a id="d24e2907"></a>
为什么我们称之为DRY？

**提示 15：DRY — 不要重复自己**

<a id="d24e2915"></a>
另一种方法是在两个或多个地方表达相同的事物。如果你改变了其中一个，你必须记住改变其他的，否则，就像外星计算机一样，你的程序将因矛盾而崩溃。这不是你是否记得的问题：而是你什么时候会忘记的问题。

<a id="d24e2918"></a>
您会发现DRY原则在本书中一次又一次地出现，通常是在与编码无关的上下文中。我们认为它是实用程序员工具箱中最重要的工具之一。

<a id="d24e2920"></a>
在本节中，我们将概述重复问题并提出处理重复问题的一般策略。

### DRY 不仅仅是代码

<a id="d24e2925"></a>
让我们提前解决一些问题。在本书的第一版中，我们没有很好地解释“不要重复自己”的含义。许多人认为它仅指代代码：他们认为 DRY 的意思是“不要复制和粘贴源代码行”。

<a id="d24e2934"></a>
这是 DRY 的一部分，但它是一个很小且相当微不足道的部分。

<a id="d24e2939"></a>
DRY 是关于知识和意图的重复。这是在两个不同的地方，可能以两种完全不同的方式表达同一件事。

<a id="d24e2956"></a>
这是严峻的考验：当代码的某些方面必须更改时，您是否发现自己在多个地方以多种不同的格式进行更改？您是否必须更改代码和文档，或者数据库模式和保存它的结构，或者……？如果是这样，您的代码不是 DRY。

<a id="d24e2958"></a>
那么让我们看一些典型的重复示例。

### 代码重复

<a id="d24e2967"></a>
这可能是微不足道的，但是代码重复是很常见的。这是一个例子：

```
def print_balance(account)
  printf "Debits:  %10.2f\n", account.debits
  printf "Credits: %10.2f\n", account.credits
  if account.fees
```

<a id="d24e3097"></a>
现在请忽略我们犯了将货币存储在浮动货币中的新手错误的暗示。相反，看看您是否可以发现此代码中的重复项。 （我们至少可以看到三件事，但您可能会看到更多。）

<a id="d24e3099"></a>
你发现了什么？这是我们的清单。

<a id="d24e3101"></a>
首先，显然存在处理负数的复制和粘贴重复。我们可以通过添加另一个函数来解决这个问题：

```
def format_amount(value)
  result = sprintf("%10.2f", value.abs)
  if value
```

<a id="d24e3210"></a>
另一种重复是所有 printf 调用中字段宽度的重复。我们可以通过引入一个常量并将其传递给每个调用来解决这个问题，但为什么不直接使用现有的函数呢？

```
def format_amount(value)
  result = sprintf("%10.2f", value.abs)
  if value
```

<a id="d24e3329"></a>
还有什么吗？那么，如果客户要求标签和数字之间有额外的空格怎么办？我们必须改变五行。让我们删除重复项：

```
def format_amount(value)
  result = sprintf("%10.2f", value.abs)
  if value
```

<a id="d24e3461"></a>
如果我们必须更改金额的格式，我们可以更改 format\_amount。如果我们想改变标签格式，我们改变report\_line。

<a id="d24e3469"></a>
仍然存在隐式 DRY 违规：分隔线中的连字符数量与金额字段的宽度有关。但这不是完全匹配：目前它短了一个字符，因此任何尾随的减号都会超出该列。这是客户的意图，与实际金额格式不同。

#### 并非所有代码重复都是知识重复

<a id="d24e3474"></a>
作为在线葡萄酒订购应用程序的一部分，您将捕获并验证用户的年龄以及他们订购的数量。根据网站所有者的说法，它们都应该是数字，并且都大于零。所以你编写了验证代码：

```
def validate_age(value):
    validate_type(value, :integer)
    validate_min_integer(value, 0)

def validate_quantity(value):
    validate_type(value, :integer)
    validate_min_integer(value, 0)
```

<a id="d24e3515"></a>
在代码审查期间，常驻万事通会退回此代码，声称这是 DRY 违规：两个函数体是相同的。

<a id="d24e3517"></a>
他们错了。代码是一样的，但是它们所代表的知识是不同的。这两个函数验证两个恰好具有相同规则的独立事物。这是巧合，不是重复。

### 文档重复

<a id="d24e3525"></a>
不知怎的，一个神话诞生了，你应该评论你的所有函数。那些相信这种疯狂的人会产生这样的东西：

```
# Calculate the fees for this account.
#
# * Each returned check costs $20
# * If the account is in overdraft for more than 3 days,
#   charge $10 for each day
# * If the average account balance is greater that $2,000
#   reduce the fees by 50%

def fees(a)
  f = 0
  if a.returned_check_count > 0
    f += 20 * a.returned_check_count
  end
  if a.overdraft_days > 3
    f += 10*a.overdraft_days
  end
  if a.average_balance > 2_000
    f /= 2
  end
  f
end
```

<a id="d24e3636"></a>
该函数的意图给出了两次：一次在注释中，另一次在代码中。客户更改了费用，我们必须更新两者。只要有时间，我们几乎可以保证注释和代码会不一致。

<a id="d24e3638"></a>
问问自己注释给代码添加了什么。从我们的角度来看，它只是弥补了一些糟糕的命名和布局。就这样怎么样：

```
def calculate_account_fees(account)
  fees  = 20 * account.returned_check_count
  fees += 10 * account.overdraft_days  if account.overdraft_days > 3
  fees /= 2                            if account.average_balance > 2_000
  fees
end
```

<a id="d24e3677"></a>
名字说明了它的作用，如果有人需要详细信息，可以在源代码中找到。那是DRY！

#### DRY 数据违规

<a id="d24e3682"></a>
我们的数据结构代表知识，它们可能与 DRY 原则相冲突。让我们看一下代表一条线的类：

```
class Line {
  Point  start;
  Point  end;
  double length;
};
```

<a id="d24e3715"></a>
乍一看，这个类可能看起来很合理。一条线显然有起点和终点，并且总是有长度（即使它为零）。但我们有重复。长度由起点和终点定义：改变其中一个点，长度就会改变。最好将长度设置为计算字段：

```
class Line {
  Point  start;
  Point  end;
  double length() { return start.distanceTo(end); }
};
```

<a id="d24e3743"></a>
在稍后的开发过程中，出于性能原因，您可能会选择违反 DRY 原则。当您需要缓存数据以避免重复昂贵的操作时，经常会发生这种情况。诀窍在于将影响本地化。违规行为不会暴露给外界：只有类内的方法才需要担心保持事情正常：

```
class Line {
  private double length;
  private Point  start;
  private Point  end;

  public Line(Point start, Point end) {
    this.start = start;
    this.end   = end;
    calculateLength();
  }

  // public
  void setStart(Point p) { this.start = p; calculateLength(); }
  void setEnd(Point p)   { this.end   = p; calculateLength(); }

  Point getStart()       { return start; }
  Point getEnd()         { return end;   }

  double getLength()     { return length; }

  private void calculateLength() {
    this.length  = start.distanceTo(end);
  }
};
```

<a id="d24e3895"></a>
此示例还说明了一个重要问题：每当模块公开数据结构时，您就会将使用该结构的所有代码耦合到该模块的实现。如果可能，请始终使用访问器函数来读取和写入对象的属性。这将使将来添加功能变得更加容易。

<a id="d24e3914"></a>
访问器函数的这种使用与 [*面向对象的软件构造* [Mey97]](<../A2 Exercise Answers/README.md#d6040e783>) 中描述的 Meyer 的统一访问原则相关，该原则指出

<a id="d24e3931"></a>
> 模块提供的所有服务都应该是
> 通过统一的符号可用，这不会背叛
> 无论是通过存储还是通过
> 计算。

### 代表性复制

<a id="d24e3936"></a>
您的代码与外部世界的接口：通过 API 的其他库、通过远程调用的其他服务、外部源中的数据等等。几乎每次这样做，您都会引入某种 DRY 违规：您的代码必须具有也存在于外部事物中的知识。它需要知道 API、模式、错误代码的含义等等。这里的重复是两件事（您的代码和外部实体）必须了解其接口的表示。一端改变，另一端就断了。

<a id="d24e3950"></a>
这种重复是不可避免的，但可以减轻。这里有一些策略。

#### 内部 API 之间的重复

<a id="d24e3955"></a>
对于内部 API，寻找可让您以某种中性格式指定 API 的工具。这些工具通常会生成文档、模拟 API、功能测试和 API 客户端，后者采用多种不同的语言。理想情况下，该工具会将所有 API 存储在中央存储库中，从而允许它们在团队之间共享。

#### 跨外部 API 的重复

<a id="d24e3979"></a>
<a id="FNPTR-15"></a>
您会越来越多地发现公共 API 使用 OpenAPI 之类的方式正式记录。[[15]](<15 Estimating - learn_to_estimate.md#FOOTNOTE-15>) 这允许您将 API 规范导入到本地 API 工具中，并更可靠地与服务集成。

<a id="d24e3988"></a>
如果您找不到这样的规范，请考虑创建一个并发布它。不仅其他人会发现它有用；而且您甚至可能会得到维护方面的帮助。

#### 与数据源重复

<a id="d24e3993"></a>
许多数据源允许您反思其数据模式。这可以用来消除它们和您的代码之间的大部分重复。您可以直接从架构生成容器，而不是手动创建代码来包含此存储的数据。许多持久性框架将为您完成这项繁重的工作。

<a id="d24e4007"></a>
还有另一种选择，也是我们经常喜欢的一种。不要编写以固定结构（例如结构或类的实例）表示外部数据的代码，而只需将其粘贴到键/值数据结构中（您的语言可能将其称为映射、哈希、字典甚至对象）。

<a id="d24e4011"></a>
就其本身而言，这是有风险的：您会失去很多了解自己正在使用哪些数据的安全性。因此，我们建议在此解决方案中添加第二层：一个简单的表驱动验证套件，用于验证您创建的地图是否至少包含您需要的数据（采用您需要的格式）。您的 API 文档工具也许能够生成此内容。

### 开发者间重复

<a id="d24e4020"></a>
也许最难检测和处理的重复类型发生在项目的不同开发人员之间。整套功能可能会无意中重复，并且这种重复可能多年都未被发现，从而导致维护问题。我们亲耳听说美国某个州的政府计算机系统接受了 Y2K 合规性调查。审计发现了 10,000 多个程序，每个程序都包含不同版本的社会保障号验证代码。

<a id="d24e4051"></a>
在高层，通过建立一支强大、紧密、沟通良好的团队来解决问题。

<a id="d24e4053"></a>
然而，在模块级别，问题更加隐蔽。不属于明显责任范围的常用功能或数据可以多次实现。

<a id="d24e4055"></a>
我们认为解决这个问题的最佳方法是鼓励开发人员之间积极、频繁的沟通。

<a id="d24e4076"></a>
也许每天召开一次 scrum 站立会议。建立论坛（例如 Slack 频道）来讨论常见问题。这提供了一种非侵入式的通信方式（甚至跨多个站点），同时保留所有所说内容的永久历史记录。

<a id="d24e4091"></a>
指定一名团队成员作为项目馆员，其工作是促进知识交流。在源代码树中拥有一个可以存放实用程序和脚本的中心位置。并重视阅读其他人的源代码和文档，无论是非正式的还是在代码审查期间。你不是在窥探——你是在向他们学习。请记住，访问是相互的——也不要因为其他人仔细研究（摸索？）你的代码而感到扭曲。

**提示 16：使其易于重用**

<a id="d24e4135"></a>
您想要做的是营造一个环境，在该环境中查找和重用现有内容比自己编写更容易。如果这件事不容易，人们就不会这么做。如果你不能重用，你就会面临重复知识的风险。
