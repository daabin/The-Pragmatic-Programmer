## 主题 8. 优秀设计的本质

<a id="d24e2670"></a>
世界上有很多专家和专家，他们都渴望在如何设计软件方面分享他们来之不易的智慧。有首字母缩略词、列表（似乎有五个条目）、模式、图表、视频、演讲，以及（互联网就是互联网）可能是一个很酷的关于德墨忒尔定律的系列，用解释性舞蹈来解释。

<a id="d24e2684"></a>
我们，你们温柔的作者，也对此感到内疚。但我们想通过解释一些最近才变得明显的事情来弥补。首先，总体声明：

**提示 14：好的设计比坏的设计更容易改变**

<a id="d24e2701"></a>
如果一个东西适合使用它的人，那么它就被设计得很好。对于代码来说，这意味着它必须通过更改来适应。所以我们相信 ETC 原则：更容易改变。 ETC。就是这样。

<a id="d24e2709"></a>
据我们所知，每一个设计原则都有一个 ETC 的特例。

<a id="d24e2711"></a>
为什么解耦是好的？因为通过隔离关注点，我们可以让每个关注点更容易改变。 ETC。

<a id="d24e2717"></a>
为什么单一责任原则有用？因为需求的变化仅反映在一个模块的变化中。 ETC。

<a id="d24e2726"></a>
为什么命名很重要？因为好的名称使代码更易于阅读，并且您必须阅读它才能更改它。 ETC！

### ETC 是一种价值，而不是规则

<a id="d24e2735"></a>
价值观是帮助你做出决定的东西：我应该这样做还是那样做？在考虑软件时，ETC 是一个指南，可以帮助您在路径之间进行选择。就像你所有其他价值观一样，它应该漂浮在你的意识思想后面，巧妙地推动你走向正确的方向。

<a id="d24e2744"></a>
但如何才能做到这一点呢？我们的经验是，它需要一些最初的有意识的强化。你可能需要花一周左右的时间故意问自己“我刚刚做的事情是否使整个系统更容易改变还是更难改变？”保存文件时执行此操作。当你编写测试时就这样做。修复错误时执行此操作。

<a id="d24e2746"></a>
ETC 有一个隐含的前提。它假设一个人可以分辨出许多路径中哪一条在未来更容易改变。很多时候，常识是正确的，你可以做出有根据的猜测。

<a id="d24e2748"></a>
但有时，你不会有任何线索。没关系。在这种情况下，我们认为您可以做两件事。

<a id="d24e2750"></a>
首先，鉴于您不确定将采取什么形式的更改，您总是可以退回到最终的“易于更改”路径：尝试使您编写的内容可替换。这样，无论将来发生什么，这段代码都不会成为障碍。这看起来很极端，但实际上无论如何，这都是你应该一直做的事情。它实际上只是考虑保持代码解耦和内聚。

<a id="d24e2756"></a>
其次，将其视为培养本能的一种方式。请注意您的工程日记中的情况：您拥有的选择以及对变化的一些猜测。在源中留下标签。然后，当此代码必须更改时，您将能够回顾并给自己反馈。当您下次遇到类似的岔路口时，它可能会有所帮助。
