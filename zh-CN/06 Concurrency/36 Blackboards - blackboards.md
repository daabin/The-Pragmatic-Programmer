## 主题 36. 黑板系统

> 文字就在墙上……
>
> 但以理书 5 章（参考）

<a id="d24e18872"></a>
考虑侦探如何使用黑板来协调和解决谋杀案调查。总督察首先在会议室里立了一块大黑板。她在上面写了一个问题：

<a id="d24e18896"></a>
> H. Dumpty（男，蛋）：意外？谋杀？

<a id="d24e18898"></a>
汉普蒂到底是真的摔倒了，还是被推了？每个侦探都可以通过添加事实、证人的陈述、可能出现的任何法医证据等来为这个潜在的谋杀之谜做出贡献。随着数据的积累，侦探可能会注意到其中的联系并发布该观察或推测。这个过程在所有轮班中持续进行，涉及许多不同的人和代理人，直到案件结案。 [图](#fg-blackboard) 中显示了一个示例黑板。

<a id="fg-blackboard"></a>
<a id="d24e18909"></a>
<a id="ablackboard"></a>
![A blackboard shows the clues to case: Humpty Dumpty.](https://panzhongxian.cn/images/the-pragmatic-programmer/blackboard.png)

图 2. 有人发现了 Humpty 的赌债和电话记录之间的联系。也许他接到了威胁电话。

图中显示了一块黑板，上面有主题“Humpty Dumpty”（男性，鸡蛋）的线索。根据以下细节，案件可以以事故或谋杀结案。详细信息是，照片，国王的手下，目击证人（由福尔摩斯侦探收集）；贝壳碎片、赌债、墙上的涂鸦（马普尔侦探收集）；电话记录和有关妻子不在场的信息（由斯佩德警探收集）。

<a id="d24e18910"></a>
黑板方法的一些主要特点是：

<a id="d24e18914"></a>
<a id="d24e18917"></a>
<a id="d24e18920"></a>
<a id="d24e18923"></a>
- 没有一个侦探需要知道任何其他侦探的存在——他们观察面板以获取新信息，并添加他们的发现。
- 这些侦探可能接受过不同学科的培训，可能具有不同的教育水平和专业知识，甚至可能不在同一辖区工作。他们都有解决这个案子的愿望，但仅此而已。
- 在整个过程中，不同的侦探可能会来来去去，并且可能会进行不同的轮班。
- 黑板上可以写的内容没有任何限制。可能是图片、句子、物证等等。

<a id="d24e18925"></a>
这是一种自由放任并发的形式。侦探是独立的过程、代理人、参与者等等。有些将事实存储在黑板上。其他人则将事实从黑板上删除，可能会组合或处理它们，并向黑板上添加更多信息。董事会逐渐帮助他们得出结论。

<a id="d24e18940"></a>
基于计算机的黑板系统最初用于人工智能应用，其中要解决的问题庞大且复杂——语音识别、基于知识的推理系统等。

<a id="d24e18946"></a>
最早的黑板系统之一是 David Gelernter 的 Linda。它将事实存储为类型元组。应用程序可以将新元组写入 Linda，并使用模式匹配的形式查询现有元组。

<a id="d24e18959"></a>
后来出现了类似黑板的分布式系统，例如 JavaSpaces 和 T Spaces。使用这些系统，您可以在黑板上存储活动的 Java 对象（而不仅仅是数据），并通过部分匹配字段（通过模板和通配符）或按子类型来检索它们。例如，假设您有一个 Author 类型，它是 Person 的子类型。您可以使用lastName 值为“Shakespeare”的Author 模板来搜索包含Person 对象的黑板。您会得到作者Bill Shakespeare，但找不到园丁Fred Shakespeare。

<a id="d24e18982"></a>
我们认为，这些系统从未真正起飞，部分原因是对并发协作处理的需求尚未发展。

<a id="mort"></a>
### 行动中的黑板

<a id="d24e18987"></a>
假设我们正在编写一个程序来接受和处理抵押或贷款申请。管理这一领域的法律极其复杂，联邦、州和地方政府都有自己的发言权。贷款人必须证明他们已经披露了某些事情，并且必须要求提供某些信息，但不得询问某些其他问题，等等。

<a id="d24e18992"></a>
除了适用法律的混乱之外，我们还需要应对以下问题：

<a id="d24e18996"></a>
<a id="d24e19003"></a>
<a id="d24e19006"></a>
<a id="d24e19009"></a>
<a id="d24e19012"></a>
- 响应可以按任意顺序到达。例如，信用检查或产权搜索的查询可能需要花费大量时间，而诸如姓名和地址之类的项目可能会立即可用。
- 数据收集可能由分布在不同办公室、不同时区的不同人员完成。
- 一些数据收集可能由其他系统自动完成。该数据也可能异步到达。
- 尽管如此，某些数据可能仍然依赖于其他数据。例如，在获得所有权或保险证明之前，您可能无法开始对汽车进行所有权搜索。
- 新数据的到来可能会引发新的问题和政策。假设信用检查结果显示一份不太乐观的报告；现在您需要这五份额外表格，也许还需要一份血液样本。

<a id="d24e19014"></a>
您可以尝试使用工作流程系统来处理每种可能的组合和情况。存在许多这样的系统，但它们可能很复杂并且需要大量程序员。随着法规的变化，工作流程必须重新组织：人们可能必须改变他们的程序，并且可能必须重写硬连线代码。

<a id="d24e19025"></a>
黑板与封装法律要求的规则引擎相结合，是解决此处遇到的困难的优雅解决方案。数据到达的顺序无关紧要：当事实被发布时，它可以触发适当的规则。反馈也很容易处理：任何一组规则的输出都可以发布到黑板上并触发更适用的规则。

### 消息系统可以像黑板一样

<a id="d24e19043"></a>
在我们编写第二版时，许多应用程序都是使用小型、解耦的服务构建的，所有应用程序都通过某种形式的消息传递系统进行通信。这些消息传递系统（例如 Kafka 和 NATS）不仅仅只是将数据从 A 发送到 B。特别是，它们提供持久性（以事件日志的形式）以及通过模式匹配形式检索消息的能力。这意味着您可以将它们用作黑板系统和/或作为可以运行一群演员的平台。

### 但事情没那么简单……

<a id="d24e19063"></a>
参与者和/或黑板和/或微服务架构方法消除了应用程序中的一整类潜在的并发问题。但这种好处是有代价的。这些方法更难以推理，因为很多行动都是间接的。您会发现保留消息格式和/或 API 的中央存储库很有帮助，特别是如果存储库可以为您生成代码和文档的话。您还需要良好的工具来跟踪消息和事实在系统中的进展情况。 （一种有用的技术是在启动特定业务功能时添加唯一的跟踪 ID，然后将其传播到涉及的所有参与者。然后您将能够从日志文件中重建发生的情况。）

<a id="d24e19114"></a>
最后，这类系统的部署和管理可能会比较麻烦，因为有更多的移动部件。在某种程度上，这一事实被系统更加细化这一事实所抵消，并且可以通过替换单个参与者而不是整个系统来更新。
